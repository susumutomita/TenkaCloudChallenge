## ストーリー

この問題に暗号は出てきません。それが狙いです。

このトラックの以降の問題は、3 つのことを同時に要求します。走らせる前に何が起きるかを言うこと、
trace を読んで最初に壊れた場所を指すこと、そして見ていないパラメータでも成り立つものを書くこと。
この 3 つを初めてやるのが、初めて constraint system に向き合う日と同じ日になると、いい午後が
悪い午後に変わります。

なので、ここでは 3 つだけを、紙の上で追える題材で扱います。題材は、一定の step で進み、窓の中に
保たれるカウンタです。

## 何がデプロイされるか

コンテナ 1 つだけです。AWS アカウントもクラウドリソースもインストール作業も要りません。コンテナの
中に、このデプロイ専用の数値 (per-deploy の `FLAG_SEED` から導出するので他の人とは違います) と、
それを遊ぶための `counter` コマンドが入っています。公開されるポートは、提出した flag を platform が
POST するための loopback `/verify` だけで、参加者が触ることはありません。

## 遊び方

portal で問題を起動し、**コンテナのターミナルに接続**してください。すべてそこで、1 行ずつ進みます。
編集するファイルはなく、エディタも clone も要りません。

```bash
counter                 # コマンド一覧
counter show            # 題材、あなたの数値、各段階で打つコマンド
counter predict <数値>
counter locate <index>
counter rule "<式>"
counter transfer predict=<数値> locate=<index>
counter status          # クリア済みの段階
counter flag            # 4 段階とも通ったら TC{...}
```

`python /problem/counter.py <command>` でも同じです。

`counter show` は「これだけ読めば足りる」ように書いてあります。迷ったら何度でも打ってください。

### 題材

```text
1 round:  value <- value + step し、窓 [0, modulus) に戻す
約束:     カウンタが取る値は必ず [0, modulus) の中にある
```

この約束 1 つが、4 段階すべての中身です。

### `predict` ── 見る前に言う

最後の round のあとカウンタがどこにいるかを紙で出して、提出してください。**trace が出るのは予測が
当たったあとで、それより前には出ません。** 外したときに出るのは 1 round 分の計算だけです。自分の
計算とカウンタがどこで分かれたかを探すには足りますが、残りを飛ばすには足りません。答えを見てから
写した数値は何も測らない、というのが順番にこだわる理由です。

### `locate` ── **最初に**壊れた場所

`counter show` が出す trace は、別の壊れた実装が出したものです。`[0, modulus)` を**最初に**外れた
entry の index を答えてください。entry は 0 から数えます。

この trace は意図的に 2 回以上窓を出ます。1 回しか出ないなら「最初に約束を破った entry」と
「約束を破った entry」は同じ問いになってしまうからです ── 経緯は「作問者向け」にあります。

### `rule` ── 見えないパラメータのための 1 行

最終値を与える式を書きます。使えるのは名前 `start`, `step`, `rounds`, `modulus` と演算子
`+ - * % ( )` です。

```bash
counter rule "<式>"
```

引用符で囲んでください。`*` はシェルの glob です。採点は、目の前の case との一致ではなく
**パラメータ族との一致**で行います。目の前の case だけなら、その答えを定数で書けば通ってしまう
からです。族には 負の step・step 0・modulus より大きい step・窓の外の start・rounds 0 が入って
います。

一致する式ならどう書いても通ります。特定の書き方を探しているわけではありません。

### `transfer` ── 同じ読みを、逆向きで

前の 3 段階が通ると、`counter show` に 4 つめの case が出ます。同じカウンタを逆向きに走らせた
ものです。その予測と、その trace の最初の破綻位置を、1 行で両方答えます。

新しい種類の問いを足していないのは意図的です。見たいのは「読み方が別のパラメータでも通用するか」
であって、5 つ目を覚えたかどうかではありません。

## 採点

| | |
|---|---:|
| flag 正解 | **100** |
| 誤答 | 1 回 −5 |
| hint 1 | −20 |
| hint 2 | −30 |

hint を両方開いても 100 点中 50 点が残ります。flag はこのデプロイの seed から導出される `TC{...}`
で、他人の実行結果を暗記しても当て推量でも通りません。

## 進捗はコンテナの中にあります

`counter status` は `/tmp` 配下のファイルを読みます。コンテナ内で書き込めるのはそこだけです
(他はすべて read-only)。コンテナを作り直すと 4 段階は最初からになります。読み方が分かっていれば
数分でやり直せますし、永続ボリュームは壊れうるものが 1 つ増えるだけです。

## 講座との関係

これは `diagnostic` です。教材に併走するのではなく、教材の**前**に置かれ、トラックの入口を担い
ます。上流の `sources` を pin していないのもそのためです ── 特定の講義や課題に対して書かれた問題
ではなく、欄を埋めるために commit SHA を捏造するのは空欄より悪いからです (`CATALOG.md` の
`courseAlignment` の節)。

講座の式・fixture・solution は一切転載していません。そもそもこの問題に暗号は出てきません
(`GOVERNANCE.md` §2 および §4)。

## 保証範囲

ローカル実行は**自習用の honor-system 検証**です。マシンも Docker デーモンも image もあなたの管理下に
あるので、image の中身はあなたに対して秘匿されていません。具体的に書きます。

- flag の導出元である `FLAG_SEED` はコンテナの環境変数に入っています。どの段階も通さずに flag は
  計算できます。
- `fixtures/generate.py` は image の中にあります (`counter show` の表示がそこから作られるためです)。
  そこには正しい trace と最初の破綻位置を求める処理が書かれており、読めば 4 つのうち 3 つの答えが
  手に入ります。

4 つの段階は解錠すべき鍵ではなく順路であり、飛ばして困るのはあなただけです。`author` stage の分離が
買っているのはもっと狭いことです。reference の解答とそれを採点する suite があなたの動かす image に
入っていないので、問題を解いてしまうファイルから目を逸らす必要がありません。seed が買っているのは
本物です。数値も flag もこのデプロイ由来なので、他人の実行結果を暗記しても持ち越せません。そして
判定は特定の 1 文字列との一致ではなく構造的です ── `counter rule` は、カウンタと一致する式なら誰も
書いたことのない書き方でも受理します。

これは自習と誠実な練習を支えます。競技順位・試験・修了判定は**支えません**。
それらには participant が管理しない verifier が必要で、
[#271](https://github.com/susumutomita/TenkaCloudChallenge/issues/271) で追跡しています。

## 作問者向け

この問題はコンテナのターミナルから遊ぶので、参加者が編集するファイルを一切持ちません。
[`TEMPLATE.md`](../../docs/curricula/advanced-cryptography-2026/TEMPLATE.md) の 4 target の参加者
契約には違反しているのではなく、その対象外にいます。Makefile は作問者の道具で、参加者の目に触れる
ことはありません。`make play` は participant image の中でシェルを開きます (portal のターミナルが
繋がるのと同じ場所です)。`make test` は公開の自己検査 (インタフェースの性質だけで、答えは含みません)
を実行します。

本命は `make reference-test` です。8 つの seed で reference の解答を通し、惜しい誤答のカタログを
全部拒否し、そのうえで判定器を 1 要件ずつ壊してそのカタログが壊れた版を全部殺せることを確認し、
さらに CLI 経由で 2 つの gate を確認します。transfer の case は前 3 段階が通るまで表示も受理も
されないこと、そして flag が 4 段階の 16 通りの進捗状態のうちちょうど 1 つでのみ出ることです。

この suite は問題そのものの形も決めました。壊れた trace は当初 1 回しか窓を出ておらず、判定器から
「**最初の** entry かどうか」の要件を外しても、どの回答の verdict も変わりませんでした。採点できない
問いを訊いていたわけです。いまの trace は 2 回破綻します。
