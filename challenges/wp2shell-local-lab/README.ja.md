# 予行演習 — 経路を再現し、 直したことを証明する

> TenkaCloud Challenge · `challenges/wp2shell-local-lab` · 難易度 4 · 約 90 分 · `multi-verify` 採点 (8 チェックポイント、 300 点)

[`wp2shell-friday-night-patch`](../wp2shell-friday-night-patch/) (本番の AWS インシデント) と対になる、 **安全なリハーサル**側の問題。 セキュリティベンダーの勧告は、 WordPress 風の REST API のバッチ (まとめ) 経路解決と、 データ問い合わせの組み立て方の間の連鎖を指摘している ── 実在の WordPress インシデントの背景にあるのと同じ種類のバグだ。 本番を誰かが触る前に、 CTO は使い捨ての 1 コンテナ・ラボで安全に再現しろと言う ── 自分の手で攻め、 自分の手で直し、 直したことが再現攻撃に耐えることまで証明する。

**ここにあるのはすべて自作のシミュレータだ。** これは WordPress ではなく、 WordPress のコードを一切取り込んでいないし、 特定の CVE の手口をそのまま再現したものでもない ── 教えているのは、 このバグの系統が持つ 「形」 (バッチディスパッチャを経由する未認証の経路が、 データ問い合わせの組み立ての欠陥に繋がる) を、 約 300 行のオリジナルの Node.js で表現したものだ。 具体的にどう機械的に強制しているかは下の 「安全境界」 を参照。

## 2 つの段階

| | 第 1 段階 ── 攻める | 第 2 段階 ── 守る |
| --- | --- | --- |
| 開始状態 | 未認証 | SRE コンソールのトークンを保持 |
| やること | まとめ処理の経路の混乱を SQL の欠陥に繋げて、 合言葉を 2 つ回収する | 2 つの根本原因を直し、 後片付けをし、 鍵をローテーションしたうえで、 攻撃を再現してもう通らないことを確認する |
| 証明の仕方 | 見つけた文字列 | **実際に動いているアプリの状態**を再確認 ── 提出された建前ではない |

**順番が大事だ。** 第 2 段階に進む前に第 1 段階を終わらせること ── 経路のバグを直すと、 第 1 段階の合言葉に届く唯一の経路が閉じてしまう。 順番を 「ズル」 する方法は無い ── 仕組みそのものが順番を強制する。

## チェックポイント (multi-verify)

| チェックポイント | 何を証明するか | 点数 |
| --- | --- | ---: |
| `chain-discovery` | まとめ処理経路の混乱を使って、 内部専用のレポートに未認証で届いたこと。 | 35 |
| `compromise-proof` | それを SQL の欠陥に繋げて、 金庫テーブルの行を読み出せたこと。 | 45 |
| `fix-route` | バッチディスパッチャの権限判定が単体アクセスと統一されたこと (2 種類のペイロードで再実地検証)。 | 40 |
| `fix-query` | レポート取得のクエリがパラメータ化 + カテゴリのホワイトリスト化されたこと (設定値ではなく実地で再検証)。 | 40 |
| `cleanup-persistence` | あらかじめ仕込まれていた不正な管理者と居座り用の目印が、 両方とも消えたこと。 | 35 |
| `rotate-secrets` | 署名用の鍵が実際にローテーションされ、 古い SRE トークンが認証に使えなくなったこと。 | 35 |
| `replay-blocked` | **元とまったく同じ攻撃**を最初から最後まで再現しても、 今度は失敗すること。 | 40 |
| `site-healthy` | トップページ・通常の投稿一覧・正規のトークン付きリクエストが、 すべて引き続き 200 で返ること。 | 30 |

`fix-route` と `fix-query` はあえて独立に採点する。 経路のバグだけを直しても、 このラボでは入り口自体が閉じるので特定の再現テストは通ってしまう ── だが問い合わせの文字列連結はまだ残っている。 このカタログが自らに課している設計の基準は、 URL だけの表面的なブロックや設定値だけの見た目の修正に満点の是正点を与えることを明確に禁じている。 だから `fix-query` は、 `replay-blocked` の結果がどうであれ、 経路の修正だけでは絶対に通らない。

## 何がデプロイされるか

Docker コンテナ 1 つ、 ループバックのポート 2 つ、 別プロセスの DB も無い (アプリの中にインメモリの SQLite がある)、 他のサービスも無い:

| 場所 | 内容 |
| --- | --- |
| **自分のマシン (Docker)** | Node.js プロセス 1 つ ── シミュレータ本体とその採点器 |
| `127.0.0.1:18080` | 攻略対象の REST API + SRE コンソール (`/admin/*`) |
| `127.0.0.1:18081` | TenkaCloud の採点器が委譲する loopback `/verify` |

## 安全境界 (始める前に読むこと)

これがこの issue の核心であり、 2 通りの方法で強制されている ── 構造として、 そして片方でも壊れたら CI を落とす自動テスト (`scripts/wp2shell-local-lab.test.ts`) として:

- **シェルもコマンド実行も一切無い。** `local/app/server.mjs` は `child_process` / `exec` / `execSync` / `spawn` / `eval` を一切呼ばない ── テストは、 出荷済みソースのどこにもこれらの識別子が現れないことを検査する。
- **外向き通信は方針ではなく構造として存在しない。** `local/docker-compose.yml` はアプリを `internal: true` 宣言のある compose ネットワークに繋いでいる ── Docker はこのネットワークに、 インターネットやホストの外部インターフェースへの経路をそもそも与えない。 誤設定されうる firewall ルールではなく、 パケットの行き先自体が存在しない。 もう 1 つのネットワーク `workshop-host` は、 下のループバックポートを「そもそも公開させる」ためだけに存在する ── Docker は internal なネットワークにしか繋がっていないコンテナに対して、 ホスト側のポートバインドを一切作らないためだ。 こちらも外向きの経路は持たない: IP masquerade を無効にした bridge なので、 出ていくパケットには source NAT が付かず、 戻り経路が存在しない。 テストは、 internal 宣言があること、 全サービスがそこに繋がっていること、 そして追加のネットワークがあるなら masquerade 無効かつループバック固定の bridge であることを検査する。
- **ループバックのみ。** 公開している 2 つのポートはどちらも `127.0.0.1` にバインドされている ── テストは全ての `ports:` エントリがこの接頭辞を持つこと、 そして `privileged: true` / `cap_add` / docker.sock のバインドマウントが無いことを検査する。
- **再利用可能な実戦ペイロードは無い。** 脆弱なルート・テーブル名・ペイロードの形はすべてこのシミュレータ独自のものだ。 実在の WordPress サイトに通用する攻撃はここには無い。
- **攻撃は自分のコンテナの外に一切出ない。** 第 1 段階の攻撃も、 第 2 段階の再現検証も、 同じ箱の中の `127.0.0.1:8080` としか話さない。

## 手順

1. `make local PROBLEM=wp2shell-local-lab` でスタック・採点 API・ポータルが起動する。
2. 任意の空でないキーでポータルにログインする。
3. `docker compose logs wp2shell-local-lab` で SRE コンソールのトークンを確認する (第 2 段階で必要になるので、 今のうちに控えておく)。
4. **第 1 段階**: `curl http://127.0.0.1:18080/wp-json/` で名前空間を眺めることから始め、 まとめ (バッチ) リクエストが未認証のまま内部専用レポートに届く経路と、 レポートのカテゴリフィルタがデータ漏えいに変わる経路を見つける。 2 つの合言葉を提出する。
5. **第 2 段階**: SRE トークンを使って 2 つの根本原因の設定を両方とも直し、 あらかじめ仕込まれた不正管理者と居座り用の目印を片付け、 署名鍵をローテーションし、 最後に第 1 段階の攻撃を再現して弾かれることを確認する。 各チェックポイントには任意の合図 (例: `done`) を再提出して再スコアリングできる ── 状態系のチェックポイントに誤答減点は無いので、 何度でも確認し直してよい。

## 根本原因 (なぜそれぞれの修正が本物か)

- **経路の混乱**: バッチディスパッチャは 「ハンドラの解決」 には正規化後のパスを使い、 「権限の確認」 には正規化前の生のパスを使っていた ── そのため末尾スラッシュ付きの副リクエストは権限テーブルに一致せず、 『公開』 にフォールバックした (fail-open)。 修正は 「特定の 1 文字列を狙い撃ちで禁止する」 のではなく、 両方の参照を同じ正規化に統一することだ。
- **問い合わせの組み立て**: カテゴリフィルタが SQL 文にそのまま連結されていた。 修正はパラメータ化された文 **に加えて** カテゴリのホワイトリスト ── どちらか片方だけでは、 両方揃えるより弱い。
- **居座りと資格情報**: 根本原因を直しても、 過去の侵害が残した痕跡は自動的には片付かない。 不正管理者と居座り用の目印にはそれぞれ専用の是正手順が要り、 署名鍵もローテーションして漏れたトークンを無効化する必要がある ── 後片付けは修正そのものとは別の作業だ。

## 学習目標

- REST のバッチ経路と単体経路のパス正規化がずれると、 権限チェックをすり抜けられることを、 自分の手で再現して理解する。
- 文字列連結によるクエリ構築が、 経路の抜け道の後ろに繋がったときにどれほど被害を広げるかを体感する。
- 是正は 「提出された文字列」 や 「見た目の設定値」 ではなく、 実際の攻撃を再現して現在の状態を確認することで判定されると学ぶ。

## コスト

ローカルの Docker のみ。 AWS リソースは一切作成しない (無料)。 イメージは `node:22-alpine`。 初回のみ pull が発生する。

## 関連ファイル

- `local/docker-compose.yml` ── 単一コンテナのスタック。 `internal: true` の lab ネットワークと、 それを公開するための masquerade 無効な `workshop-host` bridge、 ループバックのみのポート。
- `local/Dockerfile` ── `node:22-alpine`、 追加パッケージなし。
- `local/app/server.mjs` ── シミュレータ本体一式: 模擬 REST サーフェス・バッチ経路のバグ・SQL の欠陥・SRE コンソール・multi-verify 採点器を 1 ファイルに実装。
- `metadata.json` ── カタログエントリ。 8 チェックポイントの採点とヒント。
- `scripts/wp2shell-local-lab.test.ts` (リポジトリルート) ── 安全境界 (exec/eval 不在・ループバックのみ・`internal: true` ネットワーク・追加ネットワークは masquerade 無効) と、 採点/テンプレートの相互参照を検査する。
