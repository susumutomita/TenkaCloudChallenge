## ストーリー

次の曲線の点は、もう 1 つの元を加えると群になる、という主張があります。

```text
y^2 = x^3 + a*x + b   (mod p)
```

スライドはそう断言します。ここでは実際に組み立てます。そして組み立ててみると、その主張は 1 つの式
ではなく 4 つの場合分けだったことが分かります。

## ブラウザでの進め方

1. Participant Portal で問題を起動し、**Browser Workbench** を開く。
2. `inspect` でこの deploy 固有の fixture と公開された証拠を読む。
3. 画面内のエディタで starter のソースを編集する。
4. `test` で公開テストを実行し、直接回答欄があれば証拠から埋める。
5. `prepare` で全 checkpoint の提出値を作り、Participant Portal へ貼る。

checkout、ターミナル、ローカルエディタは不要です。code checkpoint は編集したソースを提出します。
直接回答は `prepare` が現在の deploy seed へ結び付けるため、別 deploy からコピーした値は拒否されます。

## 1 つの式ではなく 4 つの場合

| 場合 | 結果 |
|---|---|
| どちらかが単位元 | もう一方 |
| `x` が同じで `y` が符号反転 | 単位元。`y = 0` の点の doubling を含む |
| 同じ点 | 接線の傾き `(3x² + a) / 2y` |
| それ以外 | 弦の傾き `(y₂ - y₁) / (x₂ - x₁)` |

弦の傾きに `P = Q` を代入すると `0/0` になります。doubling が別式なのは最適化のためではなく、そこに
弦が存在しないからです。

## 採点

8 つの checkpoint を独立に採点します。誤答は 1 回 15 点減点です。

| Checkpoint | 配点 | 何を検査するか |
|---|---:|---|
| `on-curve` | 30 | 全座標対の分類と、曲線外の対の拒否 |
| `identity` | 30 | 単位元と `(0, 0)` の区別、全点での `P + (-P) = O` |
| `add` | 45 | 相異なる点の全順序対 |
| `double` | 45 | 全点。垂直接線の点を含む |
| `scalar` | 45 | double-and-add。`k = 0`、`k = 1`、負の `k` |
| `trace` | 35 | 各 step の accumulator と消費済みビットの対応 |
| `properties` | 40 | 見たことのない曲線での公理と準同型性 |
| `secp256k1` | 30 | 公開された実パラメータ上での同じ抽象 |

hint は 8 つ中 5 つにあり、いずれもその checkpoint の 50% 上限内です。

## 標本ではなく全数

曲線は小さく、点は 23〜47 個です。そのため検査は標本を取りません。全座標対を分類し、相異なる点の
全順序対を足し、全点を 2 倍し、群の公理を群全体で検査します。一般ケースだけ正しく、単位元や
`P + (-P)` や `y = 0` で壊れる実装に隠れる場所はありません。

## trace がビット順を捕まえる仕組み

double-and-add は下位ビットから消費します。step `i` の直後、accumulator は「下位 `i+1` ビットが表す
数 × `P`」でなければなりません。trace checkpoint はこれを各行で検査するので、上位ビットから消費する
実装は最初の行で落ちます。最終結果だけ合っていても通りません。

## secp256k1 で何を検査しているか

検査する関係はすべて、公開パラメータの定義から従うものです。どこかから写した期待値との一致では
ありません。

- `G` が曲線上にある
- `n` は群の位数なので `n·G` は単位元
- したがって `(n-1)·G = -G`、`(n+1)·G = G`
- `(k+m)·G = k·G + m·G`

写した値が 1 つも要らないので、転記ミスや出所不明の定数が混入する余地がありません。

## constant-time ではありません

double-and-add はビットに依存して分岐し、加算の回数もビットの立ち方で変わります。実鍵に対しては、
その性質そのものが side-channel です。ここでの目的はアルゴリズムを読めるようにすることであり、
production の手本ではありません。

## 保証範囲

ローカル実行は**自習用の honor-system 検証**です。マシンも Docker デーモンも image も
あなたの管理下にあるので、 image の中身はあなたに対して秘匿されていません。
`reference/` と `tests/hidden/` を bind-mount しないのは、あなたの git checkout に
紛れ込ませないためであって、手が届かなくするためではありません。

verifier が実際に保証するのはもっと狭く、そして本物です。提出コードは verifier を
ハングさせたりクラッシュさせたりできません。 checkpoint は echo した id しか加点できません。
結果は期待値を漏らしません。 fixture はこのデプロイの seed 由来なので、暗記した答えは持ち越せません。

これは自習と誠実な練習を支えます。競技順位・試験・修了判定は**支えません**。
それらには participant が管理しない verifier が必要で、
[#271](https://github.com/susumutomita/TenkaCloudChallenge/issues/271) で追跡しています。
