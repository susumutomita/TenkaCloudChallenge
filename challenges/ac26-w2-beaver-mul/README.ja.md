## ストーリー

監査人たちは、分割した数字を会わずに足し、公開値で伸縮し、組み合わせられるようになりました。それでも
1 つだけ手に負えないものが残ります。**両方が分割されている**数同士の掛け算です。やろうとすると必ず
「では先にそちらの数を」になり、それはこの仕組みが避けるために作られたものそのものです。

誰かが指摘します。厄介な部分は数字に依存しない、と。面倒な材料は前もって ── 前の週でも、夜通しでも、
いつでも ── 挽いておける。そうすれば本番の会合は短くて済みます。

昨夜の run が狂いました。原因は 4 つの項のうち最後の 1 つです。**あなたはその party の 1 人**で、
積が本当はいくつなのかを聞かれている側です。

## 何がデプロイされるか

コンテナ 1 つだけです。AWS アカウントもクラウドリソースもインストール作業も要りません。コンテナの
中に、このデプロイ専用の field・party 数・row・三つ組 (per-deploy の `FLAG_SEED` から導出するので
他の人とは違います) と、それを遊ぶための `beaver` コマンドが入っています。公開されるポートは、提出
した flag を platform が POST するための loopback `/verify` だけで、参加者が触ることはありません。

## 構成

`c = a*b` を満たす前処理済みの三つ組 `(a, b, c)`。入力に依存せず、事前に share されています。

```text
d = X - a      e = Y - b        各 party が自分の 2 行だけで
open d, open e                  1 round: 全員が両方の row を broadcast し、全員が足し合わせる
X*Y = c + d*b + e*a + d*e
```

4 つの項のうち 3 つは share に対して線形なので、各 party は自分の row を計算するだけです。
**4 つめは share ではありません。** `d` と `e` が open された時点で `d*e` は公開スカラーであり、公開
スカラーを畳み込むのはちょうど 1 party です。全員が足すと row の総和は `X*Y + (n-1)*d*e` になります。

画面に出る `a` の row はあなたの 1 行だけです。これは意図的で、しかも確かめられます。`x = d + a` に
必要なのは `a` 全体なので、「`d` を公開しても `x` は漏れない」は信じてくださいという話ではなく、
手元の材料についての事実になります。

## 遊び方

portal で問題を起動し、**コンテナのターミナルに接続**してください。すべてそこで、1 行ずつ進みます。
編集するファイルはなく、エディタも clone も要りません。

```bash
beaver                     # コマンド一覧
beaver show                # 自分の 5 行、protocol、broadcast、publish された積
beaver open 1234,567       # round が公開する 2 つの値
beaver row 890             # 正しく組み立てた「自分の」積の row
beaver product 123         # desk が本来 publish すべきだった積
beaver transfer open=12,34 row=56 product=78
beaver status              # クリア済みの段階
beaver flag                # 4 段階とも通ったら TC{...}
```

`python /problem/beaver.py <command>` でも同じです。コンテナには python3 が入っているので、計算は
1 行で済ませられます: `python3 -c "print((1234 * 567) % 4013)"`。この問題が見ているのは推論のほうで、
掛け算の手計算ではありません。

### `open` ── 唯一の round

`d` も `e` も share です。だから各 party の row は「row から row を引いたもの」で、open するとは全員
の row を足し合わせることです。`beaver show` は他 party の broadcast を全部出しますが、自分の分だけ
は出しません。それを計算することが、この stage の言う local な一手だからです。

### `row` ── 線形結合と、線形ではない項

`X*Y` の自分の row を組み立ててください。4 つの項のうち 3 つは「何かの自分の row」ですが、4 つめは
公開スカラーです。誰が畳み込む担当かは `beaver show` に書いてあります。

### `product` ── fault を打ち消す

desk は、その公開スカラーを取り違えた run の再構成値を publish しました。何を取り違えたかは
`beaver show` が明示します。積が本当はいくつなのかを答えてください。補正に必要な材料 ── open された
2 値と party 数 ── はすべて公開情報です。

### `transfer` ── 見たことのない乗算で

上の 3 つを通すと、第 2 の run が渡されます。素数も party 数も違い、今度はあなたが担当 party の側で、
そして fault は逆向きです ── 誰も畳み込まなかった。だから第 1 の run で通った補正は、ここでは値が違う
のではなく形が違います。3 つの読みを 1 行でまとめて提出します。

hint を両方開いても 200 点中 100 点が残ります。flag はこのデプロイの seed から導出される `TC{...}`

## 進捗はコンテナの中にあります

`beaver status` は `/tmp` 配下のファイルを読みます。コンテナ内で書き込めるのはそこだけです (他は
すべて read-only)。コンテナを作り直すと 4 段階は最初からになります。答えが分かっていれば数分で
やり直せますし、永続ボリュームは壊れうるものが 1 つ増えるだけです。

## 誰も代わりに教えてくれない間違い方 3 つ

1. **`d*e` は share ではありません。** 他の 3 項と見た目が同じなだけで、公開スカラーです。畳み込むの
   はちょうど 1 party です。
2. **前処理は沈黙を買いません。** Beaver 乗算 1 回の通信は 0 round ではなく 1 round です。乗算深さ D
   の回路は D round になり、これが MPC の遅延がゲート数ではなく乗算深さで決まる理由です。
3. **row は field の元です。** `X - a` は途中で負になります。`[0, p)` に戻してください。`-1` と
   `p-1` は同じ元で、CLI が受け取るのは範囲内のほうです。

## 次につながるところ

乗算が組めたことで、任意の算術回路が MPC で評価できるようになりました。残るのは「何を公開すると何が
漏れるか」で、それが Week 2 の最後の 2 問です。

## 保証範囲

ローカル実行は**自習用の honor-system 検証**です。マシンも Docker デーモンも image もあなたの管理下に
あるので、image の中身はあなたに対して秘匿されていません。具体的に書きます。

- flag の導出元である `FLAG_SEED` はコンテナの環境変数に入っています。どの段階も通さずに flag は
  計算できます。
- `fixtures/` は image の中にあります (`beaver show` の表示がそこから作られるためです)。そこには
  秘密値も三つ組全体も各 stage の採点基準になる値も入っており、読めば答えはすべて手に入ります。

4 つの段階は解錠すべき鍵ではなく順路であり、飛ばして困るのはあなただけです。`author` stage の分離が
買っているのはもっと狭いことです。解答そのものとそれを採点する suite があなたの動かす image に入って
いないので、問題を解いてしまうファイルから目を逸らす必要がありません。seed が買っているのは本物です。
field も party 数も三つ組も flag もこのデプロイ由来なので、他人の実行結果を暗記しても持ち越せません。
そして判定は特定の 1 文字列との一致ではなく構造的なので、見たことのない正解でも受理します。

これは自習と誠実な練習を支えます。競技順位・試験・修了判定は**支えません**。
それらには participant が管理しない verifier が必要で、
[#271](https://github.com/susumutomita/TenkaCloudChallenge/issues/271) で追跡しています。

## 作問者向け

`make play` は participant image の中でシェルを開きます。portal のターミナルが繋がるのと同じ場所です。
`make test` は公開の自己検査 (インタフェースの性質だけで、答えは含みません) を実行します。

本命は `make reference-test` です。設計が依っている fixture の不変条件を検査し、12 個の seed で
reference の解答を通し、惜しい誤答のカタログを全部拒否し、そのうえで判定器を 1 要件ずつ壊して、その
カタログが壊れた版を全部殺せることを確認します。不変条件のうち 4 つは具体的な失敗のために存在します。
参加者に渡される row から Beaver の等式が実際に `X*Y` へ再構成されること (でなければ row stage は何の
一部でもない数を要求しています)。open される 2 値がどちらも 0 でないこと (`d` か `e` が 0 だと `d*e`
も 0 になり、全員が畳み込む誤りと 1 party だけが畳み込む正解が区別できません)。2 値が等しくないこと
(でなければ `beaver open e,d` の入れ替えが通ります)。そして live 側では参加者が担当 party になること
は決してなく、transfer 側では必ず担当 party になること (どちらの `row` も、もう一方の繰り返しでは
出せません)。
