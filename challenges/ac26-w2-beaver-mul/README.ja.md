## ストーリー

監査人たちは、分割したままの数字を足し、定数倍し、組み合わせられるようになりました。それでも 1 つ
だけ手が出ない操作があります。**両方とも**分割されている 2 つの数の掛け算です。どう試しても「まず
そちらの数を教えてください」に行き着き、それはこの仕組みが避けるために作られたものそのものです。

そこで、面倒な部分は数字に依存しない、と誰かが気づきます。前の週でも、夜中でも、いつでもよいので
先に用意しておけば、当日の会合は短く済みます。

## 構成

c = a*b を満たす前処理済みの三つ組 (a, b, c) を、入力とは無関係に先に share しておきます。

```text
d = x - a        e = y - b              各 party が手元で
open d, open e                          1 round の通信
x*y = c + d*b + e*a + d*e               d と e が公開されたので再び線形
```

4 つの項のうち 3 つは、前問とまったく同じ扱いで済みます。**4 つ目は share ではありません。**

5. 各 checkpoint をそのまま提出する。Portal が現在のファイルと回答を準備して送る。

checkout、ターミナル、ローカルエディタ、別画面、コピペは不要です。code checkpoint は現在の

値は拒否されます。

## 採点

5 つの checkpoint を独立に採点します。誤答は 1 回 10 点減点です。

| Checkpoint | 配点 | 何を検査するか |
|---|---:|---|
| `mask` | 40 | 4 設定で `x - a` へ復元される |
| `open` | 30 | 合同なだけでなく `[0, p)` の正規形の体元を返す |
| `combine` | 65 | `x*y` へ復元される。典型的な誤答を名指しで落とす |
| `protocol` | 30 | 自分で書いた 4 つの部品の通し実行と round 数 |
| `transfer` | 35 | 見たことのない seed での再実行 |

hint は 5 個の checkpoint すべてに 3 段ずつあります (hint1 = 何をしたいのか / hint2 = どう考えるか / hint3 = 読めば解けるウォークスルー)。減点は各 checkpoint の配点の 50% 以内で、15 個すべてを開いても 200 点中 102 点が残ります。

## 他の 3 つと違う項

`c + d*b + e*a` は share に対して線形なので、各 party が自分の行を計算して終わりです。`d*e` だけは
**公開されたスカラー**で、1 party だけが畳み込みます。全員が足すと、share の総和は
`x*y + (n-1)*d*e` になります。

規則としては前問の公開定数の加算とまったく同じです。ただし今度は protocol の途中、しかも本当に
party ごとの計算である 3 項の隣に現れます。ここでの方がはるかに見落としやすい理由がそれです。

隠れ方も巧妙です。

- `n = 1` では正解と**区別できません**。
- `d` か `e` がたまたま 0 なら `d*e` が消えるので、やはり区別できません。

hidden test の fixture が `d ≠ 0` かつ `e ≠ 0` を強制しているのはこのためで、誤答の総和も不等号任せ
にせず名指しで落とします。これらのパラメータは観測可能性のための選択です。実際の protocol は一様な
mask を引き、`d = 0` も許容します。

## なぜ d と e を公開してよいのか

`a` は前処理で作られた一様な値で、誰も clear では持っていません。したがって `d = x - a` は `x` を
one-time mask で隠したものであり、公開しても `x` は漏れません。

三つ組を使い回すとこの性質は失われます。同じ `a` が 2 つの異なる秘密を隠すことになるからです。1 回の
乗算ごとに 1 つの三つ組を消費するのはこのためで、offline のコストは 1 回払って終わりではなく乗算
回数に比例します。

## round 数は 0 ではなく 1

`d` と `e` は同時に open できるので、Beaver 乗算 1 回の通信は **1 round** です。前処理は沈黙を買うの
ではなく、入力に依存しない仕事を offline へ移すだけです。深さ `D` の乗算回路は `D` round になり、
MPC の遅延がゲート数ではなく乗算深さで決まるのはこのためです。

## 次につながるところ

乗算が組めたので、任意の算術回路が MPC で評価できるようになりました。残るのは「何を公開すると何が
漏れるか」で、それが Week 2 の最後の 2 問です。

## 保証範囲

ローカル実行は**自習用の honor-system 検証**です。マシンも Docker デーモンも image も
あなたの管理下にあるので、 image の中身はあなたに対して秘匿されていません。
`reference/` と `tests/hidden/` を bind-mount しないのは、あなたの git checkout に
紛れ込ませないためであって、手が届かなくするためではありません。

verifier が実際に保証するのはもっと狭く、そして本物です。提出コードは verifier を
ハングさせたりクラッシュさせたりできません。 checkpoint は echo した id しか加点できません。
結果は期待値を漏らしません。 fixture はこのデプロイの seed 由来なので、暗記した答えは持ち越せません。

これは自習と誠実な練習を支えます。競技順位・試験・修了判定は**支えません**。
それらには participant が管理しない verifier が必要で、
[#271](https://github.com/susumutomita/TenkaCloudChallenge/issues/271) で追跡しています。
