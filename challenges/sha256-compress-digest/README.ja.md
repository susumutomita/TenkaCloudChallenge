# SHA-256 その 3: 圧縮関数と digest、そしてパスワード保存

1 round の T1 / T2、64 round、digest、そして「64 round は可逆で、最後の足し戻しだけが一方向性を作っている」ことを反例で確かめる。最後にハッシュ関数の性質とパスワード保存を問う。

SHA-256 を自分で追える手続きに変える 3 問シリーズの 3 問目、そして最後。1 問目のパディングと 2 問目のビット演算は `local/given/primitives.py` として与えられているので、この問題は単独で解ける。

Workbench のエディタ (`compress.py`) に 5 つの関数があり、全部が意図的に壊れている。T1 から K[i] を落とす、64 round のかわりに 63 round 回す、最後の足し戻しを省く、逆変換で h を復元せずに 0 で埋める、複数ブロックのうち最初の 1 つだけを圧縮する。最後のものは `abc` の公開テストベクタを通してしまうので、いちばん厄介な種類のバグだ。

採点は 7 checkpoint 独立。round (45) は 1 round、compress (45) は 64 round と足し戻し、feedforward (45) は逆変換、digest (55) は完成した SHA-256、avalanche (40) は 1 bit 違いの 2 つのメッセージの digest が何 bit 違うかの実測、properties (35) はハッシュ関数の性質の真偽判定、storage (35) はパスワード保存の真偽判定。

feedforward がこの問題の核心。64 round は何も捨てていないので状態の置換であり、逆算できる。逆算できるものがハッシュになるのは、最後に入力状態を足し戻す Davies-Meyer の feed-forward があるからだ。checkpoint は逆変換を書かせたうえで、足し戻した後の状態には同じ逆変換が効かないことを確かめる。隠しテストは検査側が計算した順方向を逆算させるので、学習者の順方向と辻褄が合っているだけの逆変換では通らない。

properties と storage は真偽判定だが、暗記できない。文は固定 (seed からまともな主張は生成できない) で、seed が変えるのは順序だ。提出は T と F の並びなので、別のデプロイの答えは役に立たない。

公開テストは意図的に不十分にしてある。使うメッセージが全部 1 ブロックに収まるので、最初のブロックだけを圧縮する実装が FIPS 公開ベクタごと全部通る。mutation suite (local/mutation.py) が 46 変異を kill することを CI で担保する。等価変異 5 種は意図的に除外し、うち 1 種は実際に survived してから外した — round 定数と schedule 語は T1 の中で足されるだけなので、引数を入れ替えても出力は変わらない。

2. `inspect` で deploy 固有の fixture と公開された証拠を読む。

## 学習目標

- 1 round で計算されるのが 8 語のうち 2 語だけであることを説明し、実装できる
- 64 round と足し戻しを分けて実装し、それぞれの役割を述べられる
- 64 round の逆変換を書き、round が情報を捨てていないことを示せる
- 一方向性が feed-forward の足し戻しから来ることを反例で示せる
- 複数ブロックを鎖のように繋いだ SHA-256 を完成させられる
- 1 bit の入力変化が出力の約半分を変えることを実測し、なぜ望ましいかを説明できる
- ハッシュ関数について何が言えて何が言えないかを区別できる
- パスワード保存に汎用ハッシュを使ってはいけない理由と、代わりに何を使うかを説明できる

## 解説

## 何を確認したか

### 1 round は思ったより小さい

1 round で計算されるのは 8 語のうち 2 語だけです。新しい `a` は T1 + T2、新しい `e` は古い `d` + T1。残る 6 語は古い a, b, c と e, f, g がひとつずつずれたもので、古い `d` と `h` は消えます。

T1 = h + Σ1(e) + Ch(e, f, g) + K[i] + W[i]、T2 = Σ0(a) + Maj(a, b, c) です。項が 5 つと 2 つ。1 つ落としても例外は出ず、全入力に対して違う digest が出ます。starter が K[i] を落としているのはそれを一度体験するためです。

### 64 round は可逆で、それがまさに問題

情報を捨てていないので、64 round は状態の置換です。固定された schedule に対して全単射で、逆写像を書けます。書けるということは、digest から中間状態へ逆算できるということでもあります。

逆算を止めているのは最後の 1 行、入力状態の足し戻しです。Davies-Meyer 構成の feed-forward と呼ばれます。足し戻しがあると、出力から入力状態を求めるには「その状態を入れたときの round 出力」を知る必要があり、それには入力状態が要る、という循環になります。

この checkpoint で確かめたのは、一方向性が「64 回混ぜたから」ではなく「混ぜた結果に元を足したから」だという点です。round をいくら増やしても、足し戻しが無ければ可逆なままです。

### digest は鎖

各ブロックの圧縮出力が次のブロックの入力状態になります。最初のブロックだけを圧縮する実装は、55 バイト以下のメッセージでは正解を出し、`abc` の FIPS 公開ベクタも通ります。56 バイトから壊れます。

公開テストベクタで検証するときは、必ず複数ブロックのケースを含めてください。これは SHA-256 に限らず、境界を跨がないテストで安心してしまう一般的な失敗です。

### avalanche

入力を 1 bit 変えると、出力 256 bit のおよそ半分が変わります。「およそ」であって「ちょうど」ではありません。理想的なランダム関数なら期待値が 128 bit で、実測は 100 から 160 くらいの範囲に散ります。あなたの計測値もその範囲に入ったはずです。

半分変わるのが望ましいのは、出力の差分から入力の差分を推測できなくするためです。1 bit 入力を変えて出力が 1 bit しか変わらないハッシュは、差分をたどって入力を復元できてしまいます。

### パスワード保存に SHA-256 を使ってはいけない

ここまで実装してきて分かるとおり、SHA-256 は速いです。それは設計目標であり、パスワード保存では欠点です。汎用 GPU で毎秒数十億回試せる関数の出力を保存すると、漏洩時に総当たりが現実的になります。

ソルトは必要ですが十分ではありません。ソルトが無効化するのは事前計算 (レインボーテーブル) であって、その場での総当たりは止めません。パスワードごとに別のソルトを使うのも必要です。テーブル全体で 1 つを共有すると、1 回の総当たりが全ユーザーに効いてしまいます。

使うべきは意図的に遅く、コストを設定で上げられる関数です。Argon2 (できれば Argon2id)、bcrypt、scrypt、PBKDF2。Argon2id と scrypt は時間だけでなくメモリも要求するので、GPU や ASIC の並列性の優位を削ります。

最後にひとつ。「SHA-256 を数千回繰り返せば PBKDF2 と同じ」ではありません。PBKDF2 は HMAC を鍵付きで反復する定義された構成で、ソルトと反復回数の扱いも規定されています。自分で書いた loop は、その規定のどこかを外していると考えるのが妥当です。暗号の実装で自作の loop に頼らないのは、ここまで 3 問かけて手で書いてきたあとでも (むしろそのあとだからこそ) 正しい判断です。

## 公開テストが通っても終わりではない

この問題の公開テストが使うメッセージは全部 1 ブロックに収まります。最初のブロックだけを圧縮する実装が、FIPS の `abc` ベクタごと全部通ります。

隠しテストは長さ 0・1・55・56・63・64・65・119・120・191・192 と seed 由来の長さ、UTF-8 混在を回し、`digest` だけは既知の答えと突き合わせます。`feedforward` は検査側が計算した順方向を逆算させるので、学習者の順方向と辻褄が合っているだけの逆変換では通りません。

## ここまでで得たもの

SHA-256 の全工程を自分で書きました。バイト列への変換、パディング、ワード分割、message schedule、64 round の圧縮、足し戻し、digest。ライブラリの `sha256()` が何をしているかは、もうブラックボックスではありません。

同じ道具立ては HMAC、PBKDF2、Merkle tree、Bitcoin の proof-of-work にそのまま繋がります。どれも「圧縮関数を何にどう当てるか」の違いでしかありません。
