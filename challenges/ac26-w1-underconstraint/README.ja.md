# 通るのに、守れていない

## 前提

あなたは入場判定の監査担当です。**正常な入力は通るのに、必要な検査が1本抜けています。** **「起動」→「証拠を確認」**で `deployedCircuit`（配られた検査一覧）を開き、下のA・Bのどちらがないか紙で探します。その後 `policy.py` を編集します。

- **信号**は式に入れる変数、**witness（値の組）**は全信号名と値を対応させた辞書です。**制約**は「式を計算して、割った余りが0になる」という検査。**回路**は制約の一覧です。足りない制約のため、意図しない値も通る状態を**アンダー制約**と呼びます。`id` は検査を区別する名前です。
- 割る数は画面の素数 `p`。`a % p` は a を p で割った余り（mod）。例：−1を7で割った余りは6。全信号には0以上p未満の整数を入れます。
- **逆元**は掛けた余りが1になる数。p=7なら3×5=15→余り1で、3の逆元は5。素数pで、`a % p != 0` のときだけ `pow(a, -1, p)` で計算できます。0には逆元がありません。

## 入場ルールを式へ移す

`revoked` は失効回数（0なら未失効）、`issuer_ok` は認められた発行者なら1、違えば0。`ok` は「失効回数が0」の印、`granted` は入場許可なら1です。`inv` は0判定を式にする補助値です。

```text
失効回数 revoked ── A・Bの0判定 ── ok ── × issuer_ok ── granted
A: revoked × inv + ok − 1 = 0
B: revoked × ok          = 0
入場: ok × issuer_ok − granted = 0
0/1の検査: b × (b − 1) = 0  （b は ok と issuer_ok）
```

ここで `= 0` はすべて **pで割った余りが0**。素数pでは、積の余りが0ならどちらかの因子の余りが0です。だからbの検査は0か1に限定します。

**2本が必要な理由**：revoked=0ならAがok=1を決めます。revokedが0以外ならBがok=0を決め、Aがinvを逆元にします。

p=7の小例：revoked=3, inv=5, ok=0ならA=15−1=14→余り0、B=0。Bを外すとinv=0, ok=1でもA=0となり、未失効のふりができます。Aを外すとinv=0, ok=0でもB=0ですが、Aは−1→余り6。この場合は**補助値の不正であり、入場結果まで不正とは限りません**。

## 何を作って提出する？

編集するのは `policy.py` の4関数だけです。辞書の形式はファイルの先頭にあります。**式は検査器へ渡すデータとして返します**。Pythonの `if` は使えますが、その場で計算した真偽値を制約の代わりにはできません。

| 小問 | 入力 → 返すもの | 確認すること |
|---|---|---|
| build | `intended_circuit()` → 本来の5本の制約 | 0判定A・B、2本の0/1検査、入場の掛け算 |
| audit | `audit(circuit)` → 欠けたidの文字列一覧（ソート順） | 完全な回路には空の一覧 |
| exploit | `forge_witness(circuit, params)` → 値の辞書 | 配られた回路は全て0、本来の回路には0でない式がある |
| root-cause | 原因のJSONを直接回答 | ないid、正常な値、変更後の値を報告 |
| repair | `repair(circuit)` → 修復した制約一覧 | 元の制約を変えず、足りない1本だけ追加 |
| mutation-transfer | 同じ `policy.py` を再提出 | 別の数・別の欠落でも同じ4関数が動く |

`forge_witness` では `params` のrevokedとissuer_okを変えず、inv・ok・grantedを組み立てます。`params` は関数に渡る数の辞書です。画面の値を固定して書かず、渡された回路と数を使ってください。

**root-causeの形式**（下は別の変数名による形式見本で、今回の答えではありません）：
```json
{"missingConstraintId":"c-example","manipulatedSignals":[{"signal":"helper","before":3,"after":0}]}
```
`missingConstraintId` は欠けた制約のid。`manipulatedSignals` は変更した信号だけの一覧です。`signal` に信号名、`before` に「証拠を確認」の `honestWitnesses.revokedCredential` の値、`after` に自分の反例の値を書きます。全ての変更を1回ずつ書き、値は0以上p未満の整数。Aが欠けた場合、正しい逆元とは異なる補助値なら1つの固定値に限りません。

5つのコード小問は各「提出」を押すとエディタのソースを送ります。root-causeだけ回答欄へJSONを入力します。各小問は独立採点、誤答は1回−15点、得点は0未満になりません。「公開テストを実行」は正常な値と戻り値の形を確かめます。反例を試さないので、緑だけでは修復の証拠になりません。

## この模型とゼロ知識証明の関係

**ゼロ知識証明（ZK）**は秘密を明かさず主張の正しさを示す技術です。ここで行うのは、その前段となる**式と値の検査**で、ZK証明を生成・検証してはいません。補助値が不正に通ることと、「許可されない人を許可した」という偽の主張は区別します。6小問が通り、反例が修復後に落ち、正常な2種類の値が引き続き通れば完了です。

## 作成者向けの実行と確認

参加者は「起動」→「証拠を確認」→ policy.py の編集 → 公開テスト → 各小問の提出と進みます。5つのコード小問はエディタのソースを送り、root-cause だけJSONを直接入力します。既存の2つのComposeサービスとAPIを維持し、ホストへ公開するのはWorkbenchのループバック接続だけです。実行ごとの入力は内部の採点サービスが作ります。参加者イメージへ生成用seed、fixture、参考解答、非公開テストを含めません。

Linuxの子プロセスは提出関数とその入力、配布した公開の式評価器だけを受け取ります。提出コードの実行前に、ファイルを開く操作、通信の作成、採点親プロセスへの干渉を制限します。親が返されたJSONの値を検査するため、子の正常終了や「失敗なし」という印字だけでは正解になりません。公開テストは正常な値と戻り値の形だけを調べます。OSの制限はコンテナ制限への追加であり、Dockerの所有者から環境自体を秘密にするものではありません。

```bash
make test                 # Compose経由の公開テスト
make reference-test       # 作成者向けの変異検査と実行境界の検査
make verifier-down        # この問題のローカルコンテナを停止
```

6小問の合計300点、誤答時15点の減点を維持しています。各小問に3段、計18個のヒントがあり、減点の合計は80点です。独立読解・実API・実行境界・変異検査の証拠は `local/tests/hidden/READER.md` に記録します。実AWSイベントや第三者の所要時間は検証結果に含めません。

このローカル実行はAWSリソースを作りません。DockerはローカルのCPU・メモリ・ストレージを使うため、使用後はコンテナを停止します。公式Week 1のproof-of-exploit課題と、作成者のWeek 1ノートの両方を参照しました。この教材では独自の入場ルールと信号名を使い、公式課題の解答を写していません。

## ファイル属性操作の隔離追加

Linuxの提出コード用filterで、ファイル・ディレクトリの作成、リンク、名前変更、削除、属性変更も拒否します。ファイルopenだけの禁止では、子の終了後にこれらの変更が残りました。問題内の回帰は実filterを16個の使い捨て子プロセスへ適用し、19操作のEPERMと、親が所有する一時fixtureの内容・一覧・権限・所有者・時刻・拡張属性が変わらないことを確認します。一時fixtureも最後に削除します。API・得点・数学的な正答条件・実行期限は変更せず、既存の正答コードと検査を維持します。before/afterの範囲とコマンドは `local/tests/hidden/READER.md` に記録しています。
