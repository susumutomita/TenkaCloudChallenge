## ストーリー

プライバシーを保った資格確認回路が、production 投入まで 2 日というところで監査から差し戻されました。
派手な指摘ではありません。通常の利用者は正しく判定され、失効済みは拒否され、数値も合っています。
ただ、報告書のどこかに無視できない一文があります。**不正な witness を作れば、条件を丸ごと迂回できる
かもしれない。**

誰かが穴を見つけ、実際に嘘を 1 つ通してそれが実在することを示し、正当な利用者のアクセスを壊さずに
塞がなければなりません。それが今日の午後の仕事です。

## 何がデプロイされるか

コンテナ 1 つだけです。AWS アカウントもクラウドリソースもインストール作業も要りません。コンテナの
中に、このデプロイ専用の回路 (per-deploy の `FLAG_SEED` から導出するので他の人とは違います) と、
それを遊ぶための `circuit` コマンドが入っています。公開されるポートは、提出した flag を platform が
POST するための loopback `/verify` だけで、参加者が触ることはありません。

## 遊び方

portal で問題を起動し、**コンテナのターミナルに接続**してください。すべてそこで、1 行ずつ進みます。
編集するファイルはなく、エディタも clone も要りません。

```bash
circuit                 # コマンド一覧
circuit show            # ポリシー、パラメータ、deploy 済み回路、正常な witness 2 種類
circuit check revoked=<n> inv=<n> ok=<n> issuer_ok=<n> granted=<n>
circuit repair "<式>"
circuit status          # クリア済みの段階
circuit flag            # 2 段階とも通ったら TC{...}
```

`python /problem/circuit.py <command>` でも同じです。

### ポリシー

```text
失効カウンタが 0 であり、かつ発行者が認識済みのときにのみアクセスを許可する
```

回路に比較はなく、除算もありません。「この signal は 0 か」は、prover が供給する補助 signal `inv`
を使って**制約として主張する**もので、必要な制約は 1 本ではなく 2 本です。deploy 済みの回路には
そのうち 1 本しかありません。どちらが欠けているかはデプロイごとに変わります。

### `check` ── 嘘を通す

forged witness は 2 つを同時に満たす必要があります。

1. **deploy 済み回路を充足すること。** production が実際に受理していたはずの witness であること。
2. **ポリシーが偽と呼ぶ主張を運ぶこと。** その witness が主張する `granted` が、ポリシーの言う値と
   食い違うこと。

2 つめを明示するのには理由があります。「intended 回路が拒否する witness を見つけた」は exploit では
ありません。2 本のうち片方が欠けた回路では、正常な witness の `inv` を出鱈目にするだけでそれが作れて
しまい、しかも何ひとつ偽っていないからです。反例に価値があるのは「何かが拒否したから」ではなく
「**嘘が通ったから**」です。

`check` は deploy 済み回路の残差をすべて表示します。拒否されたときは、どの制約に引っかかったかが
そこで分かります。

### `repair` ── 正常系を落とさずに塞ぐ

欠けている制約を、0 にならなければならない残差として、signal 名で書いて提出します。

```bash
circuit repair "a*b + c - 1"
```

引用符で囲んでください。`*` はシェルの glob です。検査は 3 つあります。

- **追加はちょうど 1 本。** 抜かれたのは 1 本なので、戻すのも 1 本です。既にある側も一緒に足すのは
  修復ではなく書き直しですし、制約が 1 本増えるたびに正当な利用者を落とす経路が 1 つ増えます。
- **正常系 2 種類の維持。** 正当な利用者を拒否する修復は障害です。
- **修復後の回路が、ポリシーと同じ witness 集合を受理すること。** 正常系 2 件と自分の反例だけでなく、
  あなたのパラメータの周りに構成した witness 族で検査します。弱すぎれば嘘が残り、強すぎれば正直な
  prover が拒否されます。両方向を見ます。

3 つめが本題です。正常系 2 件を保ち、既知の嘘を全部止めても、まだ間違っている修復があり得ます
── 詳しくは解いたあとの writeup にあります。

## 採点

| | |
|---|---:|
| flag 正解 | **300** |
| 誤答 | 1 回 −15 |
| hint 1 | −60 |
| hint 2 | −90 |

hint を両方開いても 300 点中 150 点が残ります。flag はこのデプロイの seed から導出される `TC{...}`
で、他人の実行結果を暗記しても当て推量でも通りません。

## 進捗はコンテナの中にあります

`circuit status` は `/tmp` 配下のファイルを読みます。コンテナ内で書き込めるのはそこだけです
(他はすべて read-only)。コンテナを作り直すと 2 段階は最初からになります。答えが分かっていれば数秒で
やり直せますし、永続ボリュームは壊れうるものが 1 つ増えるだけです。

## 保証範囲

ローカル実行は**自習用の honor-system 検証**です。マシンも Docker デーモンも image もあなたの管理下に
あるので、image の中身はあなたに対して秘匿されていません。ここではそれが普通より大きいので、具体的に
書きます。

- flag の導出元である `FLAG_SEED` はコンテナの環境変数に入っています。2 段階を通さなくても flag は
  計算できます。
- `fixtures/generate.py` は image の中にあります (`circuit show` の表示がそこから作られるためです)。
  そこにはポリシーが意図する回路が書かれており、それは deploy 済み回路に抜かれた 1 本を足したものです。
  読めば答えは 2 つとも手に入ります。

2 つの段階は解錠すべき鍵ではなく順路であり、飛ばして困るのはあなただけです。`author` stage の分離が
買っているのはもっと狭いことです。解答そのものとそれを採点する suite があなたの動かす image に入って
いないので、問題を解いてしまうファイルから目を逸らす必要がありません。seed が買っているのは本物です。
回路も flag もこのデプロイ由来なので、他人の実行結果を暗記しても持ち越せません。そして判定は特定の 1
文字列との一致ではなく構造的なので、見たことのない正解でも受理します。

これは自習と誠実な練習を支えます。競技順位・試験・修了判定は**支えません**。
それらには participant が管理しない verifier が必要で、
[#271](https://github.com/susumutomita/TenkaCloudChallenge/issues/271) で追跡しています。

## 作問者向け

`make play` は participant image の中でシェルを開きます。portal のターミナルが繋がるのと同じ場所です。
`make test` は公開の自己検査 (インタフェースの性質だけで、答えは含みません) を実行します。

本命は `make reference-test` です。2 通りの欠落を両方カバーする seed 群で reference の解答を通し、
惜しい誤答のカタログを全部拒否し、そのうえで判定器を 1 要件ずつ壊して、そのカタログが壊れた版を全部
殺せることを確認します。カタログのうち 2 件はこの問題そのものの失敗です。deploy 済み回路を充足するが
何も偽っていない witness と、正常系 2 件を保ち嘘も全部止めるのにポリシーが自由にしている signal を
固定してしまう修復です。
