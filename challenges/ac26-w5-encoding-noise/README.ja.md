## この問題を始める前に — FHE という名前はいったん忘れる

まず、秘密の数字 `5` が入った**鍵付きの箱**を想像してください。

普通の暗号が得意なのは「箱に鍵をかけて、中身を見えなくすること」です。

```text
5
↓ 暗号化
[ 5 が入った鍵付きの箱 ]
```

これならクラウドに箱を預けても、クラウドは中身の `5` を読めません。

ところが、クラウドに「その秘密の数字に `3` を足して」と頼みたいとします。
普通の暗号だけなら、計算するには箱を開けて `5` を見る必要があります。
それでは秘密を守ったまま計算を任せられません。

Week 5 が解こうとしているのは、この困りごとです。

```text
[ 5 ] 🔒
   │
   │ 箱を開けずに +3
   ▼
[ 8 ] 🔒
```

計算したクラウドは、途中で `5` も `8` も見ません。
最後に秘密鍵を持つ人だけが箱を開け、`8` を受け取ります。

この「**暗号文を復号せず、暗号文のまま計算する**」考え方を
**準同型暗号（Homomorphic Encryption）** と呼びます。
そして、足し算や掛け算などを十分に組み合わせて一般的な計算を作れるものが
**完全準同型暗号（Fully Homomorphic Encryption / FHE）** です。

ここで重要なのは「FHE は単にもっと強く暗号化する方式」ではないことです。
目的は、**秘密を隠したまま第三者の計算能力を使うこと**です。

### では、なぜ noise を勉強するのか

暗号文のまま計算できれば話は終わりそうですが、実際には計算のたびに暗号文の中の
**noise（小さな誤差）** が増えていきます。

```text
暗号化した直後      noise 小
      ↓ 計算
                    noise 中
      ↓ さらに計算
                    noise 大
      ↓
大きくなりすぎると、元のメッセージを正しく復号できない
```

したがって、FHE を理解する最初の問いは

> **「暗号文は、noise にどこまで押されても元の答えへ戻れるのか？」**

です。

この問題では、まだ本物の LWE や TFHE を実装しません。
まず小さな整数だけを使い、メッセージを離れた点に置いて、そこへ noise を足し、
**どこまでなら正しく復号でき、どこで初めて壊れるのか**を目で見える形にします。

この境界が分かると、このあと Week 5 で出てくる流れが一本につながります。

```text
暗号文のまま計算したい
        ↓
計算すると noise が増える
        ↓
noise が大きすぎると復号が壊れる
        ↓
noise を小さく戻したい
        ↓
Bootstrapping
        ↓
TFHE / Programmable Bootstrapping
```

この問題を解く段階では `Bootstrapping` の仕組みを理解している必要はありません。
まず「**noise には正しく復号できる限界がある**」ことを自分の手で確認できれば十分です。

### 30 秒チェック

先へ進む前に、次の 3 問に答えられるか確認してください。

1. クラウドは計算中に秘密の `5` を見る必要がある？ → **ない**
2. FHE の目的は「暗号を強くすること」だけ？ → **違う。暗号文のまま計算できるようにすること**
3. なぜこの問題で noise の限界を測る？ → **計算で noise が増え、限界を超えると復号が壊れるから**

ここが分かってから、下の toy model に進みます。

## 物語

準同型暗号の暗号文は、メッセージを環の上のどこかに置き、そこから押しずらすことで隠します。
復号は「これはどの点に一番近かったか」です。正しさに関する問いはすべて、
答えが変わるまでにどこまで押せるかに帰着し、その距離は実行前に計算できる数です。

隠していることは何もありません。モデルは 4 行で終わります。

```text
message      m   は [0, p) の範囲
scaling      D   が p 個のメッセージを環全体に広げる
ring         q = p * D
encode       encode(m) = (m * D) mod q
decode       c が一番近い encoding point のメッセージ。同点は切り上げ
```

`p`・`D`・`q` は `params` から来て、checkpoint ごとに変わります。決め打ちしたものはどこかで外れます。

## 本当に難しいのは 3 つ

| | なぜ効くか |
|---|---|
| **同点の扱い** | 2 点のちょうど中間の値は**切り上げ**る。そう決めた時点で、耐えられる noise 区間は対称ではなくなる。どちらの端が 1 点分を失うか、そして `delta` の偶奇でそもそも中間点が存在するかどうかが決まる。 |
| **負の noise** | `e` は負になりうる。 Python の `%` は正の法に対して非負を返すので特別扱いは要らない。 `abs(e)` は別の関数。 |
| **巻き戻り** | 最後のメッセージの次の点はメッセージ p ではなく 0。 p 個のうち 2 個だけがこれに気づく。 |

## 予測してから測る

`success_interval` はパラメータに対して採点され、あなたの decoder に対しては採点されません。
これは意図的です。全 noise 値を試して**測った**区間は decoder が何をしていようとそれに一致するので、
間違った decoder と間違った区間が一緒に通ってしまいます。
hidden test は両方を fixture から計算し、decoder を区間に対して、区間を decoder に対して、別々に検査します。

1. Participant Portal で問題を起動する。同じ画面に問題エディタが表示される。
2. **証拠を調べる**で、この deploy 固有の fixture と公開された証拠を読む。

値は拒否されます。

## 採点

7 つの checkpoint を独立に採点します。誤答は 1 回 10 点。

| Checkpoint | 配点 | 検査内容 |
|---|---:|---|
| `encode` | 25 | 点が相異なり `[0, q)` に入ること、範囲外メッセージの正規化 |
| `noise` | 30 | centered 表現とその往復、負の noise と q を超える noise |
| `decode` | 30 | 環の全値、`decode(encode(m)) = m`、`+q` 不変性、同点の扱い |
| `interval` | 30 | パラメータから予測した区間、`delta` の偶奇の両方 |
| `first-failure` | 30 | 各方向で最初に失敗する noise と、その復号結果 |
| `transfer` | 25 | 見たことのない seed 由来のパラメータで上記すべて |
| `validate` | 30 | 使えない 5 組を reject し、`delta = 1` を含む使える 3 組を通す |

7 つのうち 4 つに hint があり、いずれもその checkpoint の 50% 上限の内側です。

## equivalent mutant について

mutation の候補のうち 2 つは、生き残らせるのではなく**外しました**。どちらも議論ではなく全数検査で確認しています。

- `validate_params` の `delta >= 1` は検出可能な形で壊せません。 `q = p * delta` かつ `q >= 1` かつ
  `p >= 2` の時点で `delta >= 1` は導かれるので、この境界を緩めてもどの入力でも判定が変わりません。
  reference には残していますが、それはエラーメッセージのためであって、判定を担っているからではありません。
- `encode` の `m % p` も検出可能な形では壊せません。 `(m % p) * D` と `m * D` は
  任意の整数 m について `p * D` を法として合同です。この剰余は意図を書いているだけで、
  仕事をしているのは外側の `% q` の方であり、mutation はそちらを壊します。

殺せない mutation を一覧に残すと `SURVIVED` の行を無視してよいと教えることになるので、どちらも残していません。

## これは安全ではないし、安全なふりもしない

`p` と `q` は手で全列挙できる大きさで、境界が見えるのはそのおかげだけです。
実運用のパラメータは格子問題の裏にメッセージを隠しますが、これは何の裏にも隠していません。
toy の正しさと production の安全性は別の主張で、この問題は前者しか主張しません。

同様に、noise は padding ではなく、無料でもありません。安全性が依拠する対象であり、
正しさが消費する対象です。 1 単位足すごとに困難性を買い、余裕を払います。
ここで計算する区間が、 Week 5 の残りが使っていく予算そのものです。

## 保証範囲

ローカル実行は**自習用の honor-system 検証**です。compose stack のすべてのコンテナと
Docker デーモンを管理する人を、中身の閲覧から止める手立てはありません。ここにある境界は
秘匿ではなく誤配送の防止です。build して動かす Workbench コンテナには starter と公開テスト
しか入っておらず、fixture も hidden test も参照解答も verifier 本体も入っていません。
それらは Workbench がネットワーク越しに話す、公開されていない second container と、
`make reference-test` が build する author 専用 image にだけあります。

verifier が実際に保証するのはもっと狭く、そして本物です。提出コードは verifier を
ハングさせたりクラッシュさせたりできません。 checkpoint は echo した id しか加点できません。
結果は期待値を漏らしません。 fixture はこのデプロイの seed 由来なので、暗記した答えは持ち越せません。

これは自習と誠実な練習を支えます。競技順位・試験・修了判定は**支えません**。
それらには participant が管理しない verifier が必要で、
[#271](https://github.com/susumutomita/TenkaCloudChallenge/issues/271) で追跡しています。
