TENKACLOUD / 触ってわかるメモリの話

その箱、もう別の人のもの

使い終わった箱を別の人が使っているのに、前の持ち主が場所を覚えたまま書き換えてしまう。中身が「次にやること」だったら、違う処理が動いてしまいます。

まずは下の 「まず動かしてみる」 を押して、カードの色を見比べてみましょう。あとからつまみを左に戻すと、箱の中身が変わるところを追えます。

これは安全な模型です。実際のメモリ破壊や、話題のCVEを再現したものではありません。

1. どの箱が書き換わる？

届くメモは、どの列も同じ B。左は別の箱を使い、真ん中は使い終わった箱をもう一度使います。右は、これからあなたが考える直し方で試す場所です。最初はまだ直していないので、真ん中と同じ動きになります。

この箱がメモリの領域、場所を覚えたままの受付票が古い参照です。箱が入れ替わったのに気付かず読むと、別の物が見えます。書くと、別の物を変えてしまいます。ここでは A が青、B が黄色のカードを出すだけです。

2. 古い受付票を止めるには？

箱は同じ場所でも、もう別の物かもしれません。「まだ自分が使っていい箱かな？」を、読む前にも書く前にも確かめる条件を作ってみましょう。例えば、受付票と箱の利用番号が違えば、入れ替わったと分かります。

条件の書き方を見る（例つき）

比べたい2つの値と、「同じなら通す」「違えば通す」を選んで書きます。プログラムは {"guards":[[左辺,演算子,右辺], ...]} という JSON です。JSON は、配列を角括弧で、文字列を二重引用符で囲む書き方です。全比較が正しいときだけ読み書きできます。1つでも誤りなら拒否。最大8式です。任意の JavaScript は実行しません。

"==" は値と種類が同じ、"!=" は異なることを検査します。左右には次のフィールド名（値の取り出し先）か true（はい）/ false（いいえ）を指定します。

  • slot.live = 箱が使用中か。slot.generation = 箱の現在の世代。slot.owner = 箱の所有者。slot.kind = 箱の種類。
  • handle.generation / handle.owner / handle.kind = 受付票に記録された世代・所有者・種類。
  • caller.owner / caller.kind = 呼び出した処理の所有者・必要な種類。受付票からではなく、読み書きする処理が渡す値です。

例えば ["slot.live","==",true] は使用中の箱だけを通します。利用番号（コードでは generation、世代と呼びます）は、箱を使い始めるたび1増えます。番号1の受付票と番号2の箱は別の物なので、handle.generation == slot.generation を満たさず拒否すべきです。所有者と種類は、呼び出し元が求める値と一致する必要があります。handle.generation == handle.generation のように同じ値を自分自身と比べても、入れ替わりは検出できません。

目指すのは、今の正しい受付票は使えて、古い受付票は止まること。箱を返したあとや、同じ人が同じ種類の箱を使い直したときも試されます。別の担当や別の種類の箱への読み書きも止めてください。

うまくいったら、書いた JSON 全体を Portal の提出欄に貼り付けます。画面で見える例のほかにも確認するので、ここで青になれば必ず正解、というわけではありません。

補足：コードでは何をしている？
  1. allocate が空き箱を探し、世代を増やして受付票を返す。
  2. release は使用中の印だけを消す。コピーした受付票は残る。
  3. resolve が箱番号で探す。検査なしなら、再利用された別の物も返してしまう。
  4. read は古い受付票から別の物を読み、write はその物の値を変更する。
  5. dispatch が現在の処理選択値を読み、固定の A または B を表示する。B という入力が実行可能コードに変わるわけではない。

補足：実際のメモリ破壊やPHPの話と、どこが似ている？
共通点は、データの誤書き込みが「次に何を実行するか」という制御情報に届くと、意図しない処理が選ばれ得ることです。戻り先アドレスの上書きは、関数から戻る先の情報が変わる例。本模型は解放したヒープ（必要に応じて確保する領域）の物が別の物に入れ替わり、その中の関数ポインタのような情報を誤って書く例に近いものです。ただし箱番号も A/B も単なるラベルで、実CPUのアドレスではありません。
実際には、クラッシュだけで終わったり、型・世代・所有権の検査やOSの保護で止まったりします。メモリ破壊が必ず任意コード実行（RCE）になるわけではありません。本教材はRCEを実装していません。
PHP の公開マニュアルは、アップロード進捗情報がスクリプト実行前にセッションへ記録されると説明しています。ここから「アプリの前にも入力処理が存在する」とは学べますが、それだけで古い参照の存在や CVE の原因は証明できません。PHPは2026年10月21日に原因と修正版を公開しました。本教材は php2shell / CVE-2026-109618、109619 の再現ではありません。公式説明との対応・相違はREADMEに整理しています。ここで扱うのは一般原理の模型です。PHP公式マニュアル
