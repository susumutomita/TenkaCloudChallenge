# SHA-256 その 1: バイト列とパディング

**難易度:** 2 · **想定時間:** 40〜60 分 · **配点:** 100 · **シリーズ:** SHA-256 全 3 問の 1 問目

## ストーリー

`sha256(...)` は何百回も呼んできました。64 文字の hex が返り、相手の計算結果と一致し、すべて動きます。
その経験からは、間に何が起きたのかは何ひとつ分かりません。

これは、ブラックボックスを自分で追える手続きに置き換える 3 問シリーズの 1 問目です。一度に全部は
やりません。この問題は面白い演算が始まる手前で止まります。ここでやるのは、メッセージを SHA-256 が
読める形に整えることだけです。すなわち、512 bit ブロックちょうど何個かに揃え、各ブロックを 32 bit
ワード 16 個として読めるようにします。

事務作業のように聞こえますし、実際おおむねそうです。同時に、初めて自分で書いた SHA-256 が壊れる
典型的な場所でもあります。壊れ方は 4 通りです。バイトではなく文字を数える。長さを間違った倍数に
切り上げる。仕様がビット数を要求している場所にバイト数を書く。バイト順を CPU に任せる。

## 何がデプロイされるか

コンテナが 1 つだけです。クラウドアカウントも、外部ネットワーク面もありません。

```text
local/
├── starter/padding.py    ← 編集するのはこのファイルだけ
├── fixtures/generate.py     全 fixture を deploy ごとの seed から導出する
├── tests/public/            読めるテスト
├── tests/hidden/            verifier が実行するテスト (image 内のみ。bind-mount しない)
├── reference/               解答 (image 内のみ。bind-mount しない。保証範囲を参照)
├── verifier/server.py       POST /verify。127.0.0.1:18091
└── mutation.py              hidden test が誤答を本当に落とせるかを証明する
```

fixture は deploy 時に注入される `FLAG_SEED` から導出されます。同じ seed なら同じ数値なので、自分の
セッションは再現でき、デバッグできます。seed が違えば数値も変わるので、他の人の実行結果から写した値は
役に立ちません。

## 遊び方

```bash
make inspect                  # 自分の文字列・長さ・ブロック・衝突させる対象
make test                     # 公開テスト
make test-one ID=length       # 反復中に 1 つのテストだけ再実行する
make reset                    # starter/padding.py を元に戻す
```

`local/starter/padding.py` を開きます。関数は 2 つで、どちらも意図的に壊してあります。

- `pad_message(message)` は、メッセージを 64 バイトの倍数へ揃えて返します。1 bit を 1 個
  (バイト境界では `0x80` そのもの)、続いて 0 を必要な数だけ、最後に**元の**メッセージ長を**ビット
  単位**で 8 バイトの big-endian 整数として置きます。`b""` を含むどんな入力でも空にはなりません。
- `block_words(block)` は、64 バイトブロックを 32 bit ワード 16 個として、最上位バイトから読みます。
  バイト列 `61 62 63 80` は `0x61626380` になります。

## 採点

6 つの checkpoint を独立に採点します。誤答は 1 回 5 点減点です。

| Checkpoint | 配点 | 提出するもの |
|---|---:|---|
| `byte-length` | 10 | `make inspect` が出す文字列が何**バイト**か |
| `padded-length` | 15 | パディング後の長さ 6 つをカンマ区切りで。走らせる**前**に求める |
| `length-field` | 15 | あるメッセージ長に対する末尾 8 バイトを hex 16 文字で |
| `pad` | 25 | 自分の `padding.py`。見たことのない長さで検証される |
| `words` | 20 | 自分の `padding.py`。見たことのないブロックで検証される |
| `collision` | 15 | 0 埋めだけのパディングが区別できない別のメッセージを hex で |

hint は `byte-length` 以外の全 checkpoint にあります。すべて開いても 100 点中 66 点は残ります。

`byte-length` と `padded-length` について。先にコードを走らせて答えを写せば簡単に取れますし、誰にも
バレません。同時に、この 2 つの checkpoint が測るものは無くなります。間違えるコストが最も安い 2 箇所
なので、ここで間違えておく方が得です。

## 一度は間違えておきたい 4 箇所

**文字とバイトは別物。** `make inspect` が出す文字列にはマルチバイト文字が混ざっているので、文字数と
バイト数が食い違います。SHA-256 が見るのはバイトだけです。ASCII だけで動作確認したコードは、この 2 つ
が偶然一致する範囲しか試していません。

**パディング後の長さは「64 の倍数に切り上げ」ではない。** メッセージ本体のほかに、マーカー 1 バイトと
長さ 8 バイトの置き場所が必要です。つまり `(長さ + 1 + 8)` を 64 の倍数へ切り上げます。55 バイトが
1 ブロックに収まり 56 バイトが収まらない理由も、64 バイトちょうどのメッセージでも 1 ブロック増える
理由も、これです。パディングが空になることはありません。

**末尾の長さフィールドはビット数で、しかも big-endian。** 8 バイトの中に独立した間違いどころが 2 つ
あります。短いメッセージだと先頭は `0x00` が続くので、「何も書かれていない」と見間違えやすいです。

**バイト順を決めるのは仕様で、CPU ではない。** x86 も ARM も little-endian なので、都合のよい読み方が
間違った読み方です。starter の `block_words` は手元のマシンの流儀で読んでいて、それがそのまま欠陥です。

## `collision` checkpoint が本当に訊いていること

`0x80` マーカーと末尾のビット長は取り違えられがちなので、この checkpoint は片方を取り上げて 2 つを
切り分けます。

0 埋めだけで次の 64 の倍数まで伸ばして終わるパディングを想像してください。長さは合います。ブロックも
できます。しかしメッセージがどこで終わったかを何も記録していないので、異なる 2 つのメッセージが
バイト単位で同一のブロックになり得ます。そのパディングの上に作ったハッシュは、圧縮関数がどれだけ
優秀でも衝突します。

その組を 1 つ見つけるのが checkpoint です。これを直すのがマーカーで、単射性の担保はマーカーの仕事です。
末尾のビット長はまったく別のことをしています。Merkle–Damgård strengthening、つまり長さを圧縮対象に
混ぜることで、長さの異なるメッセージ同士の関係を使う攻撃を成立させなくする役割です。仕組みが 2 つ、
目的も 2 つあります。

## 公開テストが通っても終わりではない

この問題の公開テストは 1 つのメッセージ長しか使わず、末尾 8 バイトの**値**を検査しません。ビット長を
一切書かない実装でも全部通ります。それが公開テストを同梱している理由です。答えの形は見せますが、
正しさは証明しません。

隠しテストは長さを 0・55・56・63・64・119・120 と振り、UTF-8 混在のメッセージを足し、さらに `0x80` と
`0x00` だけで作ったメッセージを足します。最後のものは、マーカー位置を走査で決める実装を落とすため
です。検査するのは固定値ではなく性質で、単射性、最小性、そして 16 個のワードを big-endian で繋ぎ直すと
元のブロックに戻ることを見ます。関係の検査なので、1 回の出力を暗記しても通りません。

## 保証範囲

ローカル実行は**自習用の honor-system 検証**です。マシンも Docker デーモンも image もあなたの管理下に
あるので、image の中身はあなたに対して秘匿されていません。`reference/` と `tests/hidden/` を
bind-mount しないのは、あなたの git checkout に紛れ込ませないためであって、手が届かなくするためでは
ありません。

verifier が実際に保証するのはもっと狭く、そして本物です。提出コードは verifier をハングさせたり
クラッシュさせたりできません。checkpoint は echo した id しか加点できません。結果は期待値を漏らし
ません。fixture はこのデプロイの seed 由来なので、暗記した答えは持ち越せません。

これは自習と誠実な練習を支えます。競技順位・試験・修了判定は**支えません**。それらには participant が
管理しない verifier が必要で、
[#271](https://github.com/susumutomita/TenkaCloudChallenge/issues/271) で追跡しています。

## コスト

ゼロです。クラウドアカウントも AWS リソースも使いません。手元のコンテナだけです。

## 作問者向け

`make reference-test` が mutation suite を回します。`pad_message` を 9 通り、`block_words` を 6 通り
壊し、さらに verifier 自身を狙った 8 つ (未知の checkpoint が fail-closed になるかの確認を含む) を
実行します。すべて検出されなければ失敗です。

一見それらしい変異を 2 つ、意図的に一覧から外してあります。`bytearray` への append を
`message + b"\x80"` に書き換えたもの、ビット長を「メッセージをバッファへ複製した後」ではなく
「前」に `len(message)` から読むもの。どちらも出力がバイト単位で同一なので、正しいテストでは区別
できません。一覧に入れると永久に survived が出て、次の作問者が suite を無視するようになります。
詳細は `local/mutation.py` の冒頭コメントにあります。
