# SHA-256 その 1: バイト列とパディング

SHA-256 が最初に見るのは文字列ではなくバイト列。UTF-8 のバイト数、512 bit ブロックへのパディング、末尾 8 バイトのビット長、そして 32 bit ワードのバイト順を、手で数えて実装して確かめる。

SHA-256 を「ライブラリを呼ぶ関数」から「自分で追える手続き」に変える 3 問シリーズの 1 問目。ここでは圧縮関数の手前、メッセージを SHA-256 が食べられる形に整える工程だけを扱う。

扱うのは 4 つの事実。(1) ハッシュ関数は文字を見ない。見るのは UTF-8 バイト列で、日本語 1 文字は 3 バイトになる。(2) パディングは FIPS 180-4 §5.1.1 の 3 段構え、1 bit・0 埋め・64 bit ビット長で、長さは必ず 64 バイトの倍数になり、空にはならない。(3) 末尾 8 バイトはバイト数ではなくビット数で、しかも big-endian。(4) 1 ブロックは 32 bit ワード 16 個として読むが、その読み方も big-endian で、多くの CPU の既定と逆。

採点は 6 checkpoint 独立。byte-length (10) と padded-length (15) は実行前の予測、length-field (15) は `inspect` が出す長さから末尾 8 バイトを組み立てる観察、pad (25) と words (20) は Workbench のエディタ (`padding.py`) の実装を隠しテストで検証する。collision (15) は 0x80 を書かない「0 埋めだけのパディング」に対する反例をひとつ作る問題で、1 bit マーカーが何のために存在するのかを反例で確かめる。

公開テストは意図的に不十分にしてある。1 つのメッセージ長しか使わず、末尾 8 バイトの値も検査しないので、ビット長を書かない実装でも通ってしまう。隠しテストは 0・55・56・63・64・119・120 バイトと UTF-8 混在、さらに 0x80 と 0x00 だけで作ったメッセージを回し、固定の期待値ではなく性質 (単射性・最小性・ワード再構成) を検査する。

隠しテスト自体が有効かどうかは mutation suite (local/mutation.py) が CI で担保する。等価変異は意図的に除外してあり、その理由は mutation.py の冒頭コメントに書いてある。

## ブラウザでの進め方

1. Participant Portal で問題を起動し、**Browser Workbench** を開く。
2. `inspect` で deploy 固有の fixture と公開された証拠を読む。
3. 画面内の starter を編集し、`test` で公開テストを実行する。
4. 表示された直接回答欄を、inspect と実験結果から埋める。
5. `prepare` で全 checkpoint の提出値を作り、Portal へ貼る。

直接回答は `prepare` により現在の deploy seed へ結び付けられます。

## 学習目標

- 文字数とバイト数を区別し、UTF-8 のバイト長を数えられる
- FIPS 180-4 §5.1.1 のパディングを実装し、任意の長さで 64 バイトの倍数に揃えられる
- 55 / 56 バイト境界を含め、パディング後の長さを計算できる
- 末尾 8 バイトがビット数の big-endian であることを説明し、組み立てられる
- 64 バイトブロックを big-endian の 32 bit ワード 16 個として読める
- 1 bit マーカーが無いパディングが単射でないことを、反例を作って示せる

## 解説

## 何を確認したか

### 文字ではなくバイト

`len(text)` は文字数、`len(text.encode("utf-8"))` はバイト数。SHA-256 が見るのは後者だけです。ASCII しか試していないコードは、この 2 つが一致する範囲でしか動作確認できていません。日本語や絵文字が入った瞬間に、長さの前提が崩れます。

### パディングの 3 段構え

FIPS 180-4 §5.1.1 は、メッセージの後に 1 bit を 1 個、0 を必要な数だけ、最後にビット長を 64 bit big-endian で置く、と定めています。バイト境界で扱う限り 1 bit は `0x80` そのものです。

`(長さ + 1 + 8)` を 64 で切り上げる、が計算の全部です。55 バイトはぎりぎり 1 ブロックに収まり、56 バイトは収まりません。「64 の倍数に切り上げる」と覚えていると 56 で間違えます。長さが既に 64 の倍数のときも、1 bit とビット長の置き場所が必要なので、丸ごと 1 ブロック増えます。パディングが空になることはありません。

### 1 bit とビット長は別の仕事をしている

よくある取り違えなので分けて書きます。

- **`0x80` の 1 bit** は、パディングを単射にするためのものです。これが無ければ `m` と `m + 0x00` が同じブロックに潰れます。collision checkpoint がその反例です。
- **末尾 8 バイトのビット長** は Merkle–Damgård strengthening です。長さを圧縮関数の入力に混ぜることで、長さの異なるメッセージ同士の関係を使った攻撃 (fixed point の連結や長さ拡張の一部) を防ぎます。単射性の担保はここではなく `0x80` の仕事です。

ビット長は「バイト数」ではなく「ビット数」で、`0x00...00` から始まる big-endian です。1 メッセージあたり 8 バイトなので、SHA-256 が扱えるメッセージ長は 2^64 bit 未満、という上限もここから来ています。

### big-endian は仕様、little-endian は都合

x86 も ARM も既定は little-endian なので、`int.from_bytes(group)` を何も指定せずに書くと環境依存になり、`"little"` と書くと SHA-256 としては間違いになります。SHA-256 の仕様は最上位バイトが先です。`61 62 63 80` は `0x61626380` です。

このズレは、実装が「動いているのに答えが違う」典型的な原因です。ハッシュ値が公式のテストベクタと一致しないとき、まず疑う場所のひとつがバイト順です。

## 公開テストが通っても終わりではない

この問題の公開テストは、1 つのメッセージ長しか使わず、末尾 8 バイトの値も検査しません。ビット長を一切書かない実装でも全部通ります。それが `misconception.public-tests-are-complete` の実演です。

隠しテストは長さを 0・55・56・63・64・119・120 と振り、UTF-8 混在のメッセージと、`0x80` と `0x00` だけで作ったメッセージも回します。後者は「`0x80` を探してマーカー位置を決める」実装を落とすためのものです。検査するのは固定の期待値ではなく性質で、単射性 (`m` と `m + 0x00` が別の結果になる)、最小性 (余計な 1 ブロックを足していない)、ワードの再構成 (16 個を big-endian で繋ぎ直すと元のブロックに戻る) を見ます。関係の検査なので、1 回の出力を暗記しても通りません。

## 次に何を学ぶか

この問題で作ったブロックが、次の問題の入力になります。16 ワードから 64 ワードへ広げる message schedule、その中で使う ROTR / SHR と σ0 / σ1、そして Ch / Maj / Σ0 / Σ1 が SHA-256 その 2 の範囲です。
