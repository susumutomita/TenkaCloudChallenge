## ストーリー

前回の監査人たちの仕組みは動きました。数字は party ごとの 1 行 (row) に分割され、誰も他人の row を
見ません。次に彼らがやりたいのは、実際に**計算する**ことです。合計、加重合計、移動平均。

心配なのは、一手ごとに全員招集が要るのではないかということです。要りません。やりたいことの大半は、
各 party が自分の row だけで済ませられ、それでも row は正しい答えへ足し合わさります。この性質が
あるからこそ、この仕組みは理論ではなく実用になります。

今朝の数字が狂いました。pipeline は変わっていません。入力も変わっていません。どの手順も線形です。
**あなたはその party の 1 人**で、本来いくつになるはずだったのかを聞かれている側です。

## 何がデプロイされるか

コンテナ 1 つだけです。AWS アカウントもクラウドリソースもインストール作業も要りません。コンテナの
中に、このデプロイ専用の field・party 数・row・公開値 (per-deploy の `FLAG_SEED` から導出するので
他の人とは違います) と、それを遊ぶための `shares` コマンドが入っています。公開されるポートは、提出
した flag を platform が POST するための loopback `/verify` だけで、参加者が触ることはありません。

## この問題で掴むもの

share は数字を変装させたものではありません。**足すと 1 つの数になる row の集まり**です。だから各
party は、自分の 2 つの row を足せば share 同士の加算ができ、自分の row を公開値倍すれば公開定数倍
ができます。どちらの場合も row は正しい値へ足し合わさり、そして誰も口をききません。

**公開定数の加算**は、見た目がまったく同じでありながら、その仲間ではありません。全 party が自分の
row に `c` を足すと、row の総和は `x + n*c` になります。畳み込むのはちょうど 1 party です。

他 party の row は一切表示されません。これは意図的です。画面にあるものだけで stage が答えられたなら、
その答えは 1 行から出たということになる ── それがこの問題の主張そのものだからです。

## 遊び方

portal で問題を起動し、**コンテナのターミナルに接続**してください。すべてそこで、1 行ずつ進みます。
編集するファイルはなく、エディタも clone も要りません。

```bash
shares                     # コマンド一覧
shares show                # field、自分の row、pipeline、desk が publish した総和
shares row 641             # pipeline を正しく回したときの「自分の」row
shares total 2123          # desk が本来 publish すべきだった総和
shares silent e1,e4,e5     # 誰とも話さずに評価できる式
shares transfer row=12 total=345 silent=g1,g3,g7
shares status              # クリア済みの段階
shares flag                # 4 段階とも通ったら TC{...}
```

`python /problem/shares.py <command>` でも同じです。コンテナには python3 が入っているので、計算は
1 行で済ませられます: `python3 -c "print((17 * (984 + 510)) % 4049)"`。この問題が見ているのは推論の
ほうで、掛け算の手計算ではありません。

### `row` ── party になる

`shares show` は、自分の 2 つの row、公開値 `k` と `c`、party 数、自分が何番の party か、そして公開
定数を畳み込む担当が誰かを出します。pipeline を正しく回したときの、自分の row を出してください。

### `total` ── fault を打ち消す

desk は、`addpub` が壊れた状態の run の再構成値を publish しました。何が壊れていたかは `shares show`
が明示します。本来 publish されるべきだった値を答えてください。補正に必要な材料はすべて公開値です。
効いてくるのは、定数が何回畳み込まれたのかを正確に把握しているかどうかだけです。

### `silent` ── 見覚えではなく分類

shared な `x, y, z` と公開の `k, c` を使った 8 本の式が出ます。各 party が自分の row だけで、誰とも
話さずに評価できるものを挙げてください。

不合格のときに返るのは「**何本**が逆側にあるか」だけで、どれが逆かは返りません。これは意図的です。
どれが逆かは「読み違いがどこにあるか」の地図そのもので、その地図を自分で描くことがこの stage だから
です。鍵ではありません ── 1 本ずつ変えれば個数は動くのでスクリプトによる探索は可能ですし、そもそも
これは honor-system のローカル実行です (「保証範囲」を参照)。

### `transfer` ── 見たことのない desk で

上の 3 つを通すと、第 2 の desk が渡されます。素数も party 数も違い、定数は scale の**内側**にあり、
今度はあなたが担当 party の側で、そして fault は逆向きです ── `addpub` が 1 度も走らなかった。だから
第 1 の desk で通った補正は、ここでは値が違うのではなく形が違います。3 つの読みを 1 行でまとめて
提出します。

## 採点

| | |
|---|---:|
| flag 正解 | **200** |
| 誤答 | 1 回 −10 |
| hint 1 | −40 |
| hint 2 | −60 |

hint を両方開いても 200 点中 100 点が残ります。flag はこのデプロイの seed から導出される `TC{...}`
で、他人の実行結果を暗記しても当て推量でも通りません。

## 進捗はコンテナの中にあります

`shares status` は `/tmp` 配下のファイルを読みます。コンテナ内で書き込めるのはそこだけです (他は
すべて read-only)。コンテナを作り直すと 4 段階は最初からになります。答えが分かっていれば数分で
やり直せますし、永続ボリュームは壊れうるものが 1 つ増えるだけです。

## 誰も代わりに教えてくれない間違い方 3 つ

1. **「線形なんだから全員が同じことをすればいい」。** share 同士の加算と公開値倍については正しく、
   公開定数の加算については誤りです。そしてちょうどそこ 1 か所だけが誤りです。
2. **括弧の中の公開値は、shared 値同士の積を消してくれない。** `x*(y + c)` を展開すると
   `x*y + c*x` です。次数を数える前に展開してください。
3. **row は field の元です。** 途中で負になった引き算は、`[0, p)` に戻すまで終わっていません。
   `-1` と `p-1` は同じ元で、CLI が受け取るのは範囲内のほうです。

## 次につながるところ

ここで引いた境界が、次の問題の動機になります。shared 値同士の乗算だけが通信を要するなら、その通信を
前処理へ追い出せないか、という問いが自然に出てきます。それがまさに Beaver triple です。

## 保証範囲

ローカル実行は**自習用の honor-system 検証**です。マシンも Docker デーモンも image もあなたの管理下に
あるので、image の中身はあなたに対して秘匿されていません。具体的に書きます。

- flag の導出元である `FLAG_SEED` はコンテナの環境変数に入っています。どの段階も通さずに flag は
  計算できます。
- `fixtures/` は image の中にあります (`shares show` の表示がそこから作られるためです)。そこには
  desk の秘密値と各 stage の採点基準になる値が入っており、読めば答えはすべて手に入ります。

4 つの段階は解錠すべき鍵ではなく順路であり、飛ばして困るのはあなただけです。`author` stage の分離が
買っているのはもっと狭いことです。解答そのものとそれを採点する suite があなたの動かす image に入って
いないので、問題を解いてしまうファイルから目を逸らす必要がありません。seed が買っているのは本物です。
field も party 数も row も flag もこのデプロイ由来なので、他人の実行結果を暗記しても持ち越せません。
そして判定は特定の 1 文字列との一致ではなく構造的なので、見たことのない正解でも受理します。

これは自習と誠実な練習を支えます。競技順位・試験・修了判定は**支えません**。
それらには participant が管理しない verifier が必要で、
[#271](https://github.com/susumutomita/TenkaCloudChallenge/issues/271) で追跡しています。

## 作問者向け

`make play` は participant image の中でシェルを開きます。portal のターミナルが繋がるのと同じ場所です。
`make test` は公開の自己検査 (インタフェースの性質だけで、答えは含みません) を実行します。

本命は `make reference-test` です。設計が依っている fixture の不変条件を検査し、12 個の seed で
reference の解答を通し、惜しい誤答のカタログを全部拒否し、そのうえで判定器を 1 要件ずつ壊して、その
カタログが壊れた版を全部殺せることを確認します。不変条件のうち 3 つは具体的な失敗のために存在します。
live 側では参加者が担当 party になることは決してなく、transfer 側では必ず担当 party になること
(でなければ転移 stage は数字を変えただけの live stage になります)。2 つの desk の fault は逆向きで、
live の補正式を第 2 の desk に当てると必ず外れること。そして式の locality は表の宣言を信じず、体上で
`f(u+v) - f(u) - f(v) + f(0)` を無作為サンプルして裏を取ること (`x*y - x*y` のような式では構文的な
次数計算が真実とずれ、しかも判定器も答えも同じ宣言から出てくるためです)。
