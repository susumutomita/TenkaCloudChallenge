# 誰とも話さずにできること

share に対する操作のうち、いくつかは誰とも話さずに各自の手元だけでできる。どれがそうで、どれが違うのか。1 つだけ、素直にやると間違える。

Week 2 の 2 問目。 加法的 share に対する線形操作を実装し、 通信が要る操作と要らない操作を区別する。 MPC が実用になるのは線形操作が通信不要だからで、 その境界を手を動かして引く。

4 操作のうち 3 つは素直だが、 add-constant だけは違う。 全 party が自分の share に c を足すと、 総和は x + n*c になる。 この誤りは n=1 では正解と区別できず、 n が大きくても c の倍数だけずれるので、 固定の 1 設定だけを見る test では偶然通り得る。 hidden test は複数設定を回し、 かつ「全 share に足した場合の値」を名指しで落とす。

no-communication checkpoint は round 数の完全一致ではなく 0 か非 0 かで採点する。 乗算プロトコルが何 round かかるかは方式によるが、 通信が要るかどうかは方式によらないため。

## 学習目標

- share 同士の加算が各自の手元だけで完結することを確認できる
- 公開定数倍が通信不要であることを確認できる
- 公開定数の加算で全 share に足すと総和が x + n*c になることを説明できる
- 通信が必要な操作と不要な操作を区別できる
- 線形操作を合成しても正しい share であり続けることを確認できる

## 解説

## 線形操作が通信不要であること

加法的 share では、 share 同士の加算も公開定数倍も、 各 party が自分の share だけを見て実行でき、 結果はそのまま正しい share になる。 MPC が実用になるのはこの性質のおかげで、 通信が要るのは shared 値同士の乗算のように 「和の積が積の和にならない」操作に限られる。

## add-constant だけが違う理由

公開定数 c を足す操作も線形だが、 各 party が自分の share に c を足すと 総和は x + n*c になる。 正しくは 1 party だけが c を畳み込む。 この誤りは n=1 では正解と一致し、 n が大きくても c の倍数だけのずれなので、 固定の 1 設定を見る test では偶然通り得る。 「線形だから全員が同じことをすればよい」という直感が、 ここでちょうど 1 回だけ裏切られる。

## round 数ではなく 0 か非 0 か

no-communication checkpoint が完全一致で採点しないのは、 乗算プロトコルの round 数が方式に依存するのに対し、 通信が要るかどうかは依存しないからだ。 採点は主張が確定している部分にだけ賭ける。

## 次につながるところ

ここで引いた境界がそのまま Beaver triple の動機になる。 乗算だけが通信を要するなら、 その通信を前処理へ追い出せないか、 という問いが次に来る。
