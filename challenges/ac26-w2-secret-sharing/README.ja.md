## ストーリー

5 人の監査人が、互いの帳簿の数字を知られずに合計を出す必要があります。ホワイトボードの計画は単純です。
各数値を人数分に分け、全部を足したときだけ意味を持つようにする、というものです。

分割はもう誰かが書いています。足せば正しく合います。そして、書かれているままでは役に立ちません。
「足せば合う」と「秘密を守る」の差が、この問題のすべてです。

そのあと監査人たちは、この分け方の裏側に気づきます。破片を 1 つ失えば合計は永久に戻らない。最後の
checkpoint は形の違う分け方を求めます —— 3 つのうちどの 2 つでも秘密が戻り、それでも 1 つだけでは
何も分からない分け方です。

## 考え方

`F_p` 上の加法的分散です。秘密 `s` を、和が `s` になる `n` 個の値にします。算術は 3 行で終わります。
これを暗号にしているのは、**そのうち任意の n-1 個が秘密と独立である**という性質のほうで、これは主張
するものではなく、示すものです。

## Participant Portal での進め方

1. Participant Portal で問題を起動する。同じ画面に問題エディタが表示される。
2. **証拠を調べる**で、この deploy 固有の fixture と公開された証拠を読む。
3. Portal のエディタで starter のソースを編集する。
4. **公開テストを実行**を押し、直接回答欄があれば証拠から埋める。
5. 各 checkpoint をそのまま提出する。Portal が現在のファイルと回答を準備して送る。

checkout、ターミナル、ローカルエディタ、別画面、コピペは不要です。code checkpoint は現在の
エディタ内容を使います。直接回答は現在の deploy seed へ結び付くため、別 deploy からコピーした
値は拒否されます。

## 採点

5 つの checkpoint を独立に採点します。誤答は 1 回 10 点減点です。

| Checkpoint | 配点 | 何を検査するか |
|---|---:|---|
| `share-and-reconstruct` | 50 | 4 つの設定での round trip、**および**自明な分割でないこと |
| `hides-the-secret` | 45 | 補完が field の**すべての**秘密に対して成功すること |
| `threshold` | 45 | 必要数と、2 つの証人 |
| `rerandomize` | 30 | 秘密が保たれ、出力が入力と同一でないこと |
| `two-of-three` | 30 | 直線の分け方: 3 点のどの 2 点 (6 通りの順) からも秘密が戻り、各点は単独ではどの秘密とも両立し、未知の p (1 万前後を 2 つ含む) で動くこと |

hint は 5 個の checkpoint すべてに 3 段ずつあります (hint1 = 提出前に自分で回せる検算 / hint2 = 見落としやすい場合分け / hint3 = 読めば解けるウォークスルー)。減点は各 checkpoint の配点の 50% 以内で、15 個すべてを開いても 200 点中 101 点が残ります。

## この問題を支える 3 つの checkpoint

**`hides-the-secret`** は field 全体を走査します。同じ n-1 個を持ったまま、**どの秘密に対しても**
辻褄の合う最後の 1 個を作れるなら、その n-1 個は秘密の証拠になっていません。これが「漏れない」の
実行可能な定義であり、どれだけ文章で説明するより強い証拠です。

**`threshold`** は数字だけでは通りません。必要数**と**、同じ n-1 個と両立する相異なる 2 つの秘密を
提出します。数を当てるのは簡単ですが、2 つの証人を作るのは理解が要ります。

**`two-of-three`** が天井です。`share_line` / `reconstruct_line` は**組**として、参照実装との一致ではなく
性質で採点します。3 点から 2 点を選ぶどの組も、どちらの順でも秘密に戻ること。そして 3 人それぞれの点に
ついて、0..p−1 のどの秘密でもその点を作る傾きが存在すること —— これは参加者自身の `share_line` を呼んで確かめる
ので、直線でなくても正しい構成なら通ります (小さい p では p × p 回の全探索、大きい p では「秘密を固定したとき、
傾きが違えば y も違う」という同値な形を数百通りの傾きで)。p は画面と違い、1 万前後のものが 2 つ含まれます。
本文が与える「割る数に掛けて 1 になる相手を 1 から順に探す」は ~p 歩で 12 秒の制限に収まり、(秘密, 傾き) の
総当たりは ~p² 歩で収まりません。starter は「全員に秘密のコピー」という、つい書きたくなる直し方で出荷されて
います。公開テストは通り、秘密性の性質で落ちます —— checkpoint 1 の教訓の再演です。

## 公開テストが教えてくれないこと

公開テストは round trip と、直線の分け方については 1 組の点だけを見ます。部分集合が何かを隠して
いるかは一度も問いません。そのため自明な分割 (party 0 に秘密をそのまま渡し、残りを 0 にする) は
きれいに通ります。party 0 は最初から全部知っているのにです。starter の「全員にコピー」の `share_line`
も同じく通ります。hidden test はどちらも性質で落とします。

## 保証範囲

ローカル実行は**自習用の honor-system 検証**です。compose stack のすべてのコンテナと
Docker デーモンを管理する人を、中身の閲覧から止める手立てはありません。ここにある境界は
秘匿ではなく誤配送の防止です。build して動かす Workbench コンテナには starter と公開テスト
しか入っておらず、fixture も hidden test も参照解答も verifier 本体も入っていません。
それらは Workbench がネットワーク越しに話す、公開されていない second container と、
`make reference-test` が build する author 専用 image にだけあります。

verifier が実際に保証するのはもっと狭く、そして本物です。提出コードは verifier を
ハングさせたりクラッシュさせたりできません。 checkpoint は echo した id しか加点できません。
結果は期待値を漏らしません。 fixture はこのデプロイの seed 由来なので、暗記した答えは持ち越せません。

これは自習と誠実な練習を支えます。競技順位・試験・修了判定は**支えません**。
それらには participant が管理しない verifier が必要で、
[#271](https://github.com/susumutomita/TenkaCloudChallenge/issues/271) で追跡しています。

## 作問者向け

`make reference-test` が mutation suite を実行します。加法的分散を壊した提出 10 種類、two-of-three の
自己整合な変異 13 種類 (それぞれの `share_line` と `reconstruct_line` は互いに辻褄が合っているので、性質
でしか落とせません)、verifier を狙った検査 3 種類 (証人の無い `threshold` 回答、starter の「全員にコピー」
の直線、(秘密, 傾き) を総当たりする `reconstruct_line`)、そして**通らなければならない**対照 1 つ (本文の
直線ではない 2-of-3 の構成 —— party 2 は傾きだけ、party 1 と 3 は s + r と s + 2r を持つ) があります。対照は
秘密性の検査が本文どおり構成非依存であることを、文言ではなく実行で保つためのものです。総当たりの変異は正しい
実装で、1 万前後の p で verifier の 12 秒の制限を待ち切るので、suite 全体で 16 秒ほどかかります。制限時間は
§15 の message として返します —— 本文が制限時間と「秘密を全部試す作り方は間に合わない」を明記しているから
です。加法的分散の変異のうち 1 つ、`reconstruct` が剰余を忘れる変異は、**hidden test の初版では生き残り
ました**。`check_roundtrip` が比較の前に learner の答えを正規化していたためです。現在は正準元であることを
要求しています。mutation suite が、提出ではなくテストのほうを検査した例です。

復元 (`reconstruct`、`reconstruct_line`) はすべて別のインタプリタで走らせます —— `python -I`、空の作業
ディレクトリ、PATH だけの環境で、提出ソースと JSON 化した引数を stdin から受け取り、結果を JSON で返します。
1 つの検査の呼び出しは 1 つのインタプリタにまとめるので、hidden run 1 回で起動は 2 回、参照実装の hidden
run 全体の実測は 0.2 秒ほどです。初版のようにソースを fresh module に exec し直すだけでは足りませんでした。
2 つのコピーは `builtins`、`sys.modules`、import 済みの全 module を共有したままで、そこに秘密を置く `share`
と、share を読まずにそれを返す `reconstruct` の組が通っていました。この置き場 4 種類 (module 変数、
`builtins`、`sys.modules` の項目、import 済み module の属性) が suite にあり、`reconstruct raised
AttributeError` / `KeyError` で死にます。インタプリタは `PR_SET_PDEATHSIG` 付きで起動するので、verifier が
制限時間で hidden run を kill したときに総当たりが生き残ることもありません。塞げないのはコンテナのファイル
システムです。2 つのインタプリタはこれを共有しているので、絶対パスに秘密を書いて読み戻す提出を止めるには
mount namespace が要り、非 root で capability を全部落とした verifier には作れません。

two-of-three の秘密性の検査は意図的に構成非依存です。小さい p の case では、3 人それぞれの点について、p 通り
の秘密候補ごとに p 通りの傾きを参加者自身の `share_line` で試します (約 10⁵ 回の呼び出しで、参照実装なら
1 秒未満)。1 万前後の p では点ごとに 10⁸ 回になるので、同じ性質を同値な形で検査します: 秘密を固定したとき、
傾き → party i の y が 0..p−1 上の全単射であること (そのとき、どの秘密からもどの y がちょうど 1 つの傾きで
作れるので、1 点は何も除外しない)。case ごとに 2 つの秘密について 300 通りの相異なる傾きで抜き取り、y が
互いに全部違うことを要求します —— 傾きを 5000 通りに畳んでしまう `share_line` でも、衝突する確率は 0.998 を
超えます。これで、初版が通していた近道 —— p < 1000 でだけ直線を作り、それより上では全員に秘密のコピーを
配る —— が落ちます。大きい p の秘密は引き続き体の上半分から引いて、0 から数え上げる総当たりが早く終わらない
ようにしています。failure message は性質 (どちらの検査か、どの party の点か、小さい p か大きい p か) だけを
名指しし、hidden の値は含めません。組の検査の message はどの組かを言わないので、x の差が 2 の組を説明する
有料 hint を先取りしません (AGENTS.md §15)。
