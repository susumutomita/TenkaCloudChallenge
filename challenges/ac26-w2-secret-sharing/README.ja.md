## 仕組みと前提

シェアは1人に渡す秘密の破片です。数は素数pで割った余りとして扱い、Pythonでは `% p` と
書きます。n−1個の乱数を配り、最後に `(secret - sum(先頭の値)) % p` を加えます。
全部足して `% p` すれば復元できます。p=7、秘密4、乱数[5,6]なら[5,6,0]になり、戻すと4です。
足りない最後の値は、候補ごとに `(候補 - sum(partial)) % p` で作れます。

全候補が部分的な並びと矛盾しないことは **両立**の証拠で、確率が変わらない証明そのものでは
ありません。秘密性には、乱数を0からp−1まで均等に、秘密やほかの乱数と独立に選び、分け直す
たびに新しく選ぶ前提が必要です。相手は集めたシェアだけを見て、欠けた担当者の情報や乱数の
一覧を見られません。このとき、同じ部分が見える確率はどの秘密でも同じになり、観察前の秘密の
確率が保たれます。乱数の0は有効です。0が多い1回の出力と、毎回秘密をコピーする規則は別です。

更新では合計0のシェアを足します。この練習は0以外の調整値がある入力で変化も確認しますが、
一般の均等な乱数はすべて0になり、同じ値を返す場合もあります。
Shamir（シャミア）の3人中2人の方式は、**3より大きい素数p**で `y=(secret+r*x) % p` を使い、
x=1,2,3の点を渡します。rも0を含めて独立に均等に選びます。2点なら本文の逆元の手順でx=0へ
戻り、1点が見える確率はどの秘密でも同じです。

秘密分散はMPC（入力を互いに明かさず共同で計算する仕組み）の部品です。これだけで完全な
MPC・署名・ウォレットになるわけではありません。手元での加算、掛け算、誰に結果を明かすかの
取り決めには、別の操作が必要です。

## 実行と保証範囲

Workbench はスターターと公開テストを持ちます。fixture・非公開検査・参照実装は、公開しない
verifier/authorイメージに残します。Composeの両サービスは非root、`init: true`、読取専用
ファイルシステム、メモリ/PID制限、capability削除、no-new-privilegesで動きます。公開ポートは
Workbenchのloopbackだけ。既存のprepare/manualの `tcw1` 形式は変更しません。

公開例の生成と回答の封印に使うseedは監督プロセスが保持します。提出Pythonはそこへimportしません。
別のLinux workerへソースと関数引数だけを渡し、環境変数を空から組み立てます。提出コードを動かす
前に、この問題内のseccompでファイルopen（`/proc` を含む）、network、exec、同じUIDの監督
プロセスへの干渉を拒否します。監督側も `PR_SET_DUMPABLE=0` で保護します。
JSONの戻り値は信用せず、既存の性質の比較はverifier側で行います。復元はシェアと割る数だけを渡す
別workerで動き、分割関数が保存した秘密を引き継ぎません。

採点全体の上限は12秒のままです。固定された引数群をまとめて評価し、Shamirの全探索の戻り値は
上限16MiBの一時ファイルで受け取ります。成功・timeoutの両方でworkerのプロセス群を終了させ、
Composeのinitが孤児になった子孫を回収します。ゾンビPIDが残った状態は回収成功としません。
公開の構文・import・初期化エラーは `sharing.py`、上限付きの行番号、許可した例外型だけを表示します。
非公開検査は性質単位または固定文の説明だけで、提出のstdout、例外本文、期待値、非公開入力は返しません。

これは演習の実行境界であり、形式的な安全性証明や完全なMPCの主張ではありません。Dockerを管理する
人は自分のverifierを閲覧できます。ローカルは自習用です。競技順位や修了判定には参加者が管理しない
verifierが必要で、[#271](https://github.com/susumutomita/TenkaCloudChallenge/issues/271)で追跡します。
