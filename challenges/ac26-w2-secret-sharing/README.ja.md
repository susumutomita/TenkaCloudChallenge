## 物語

5 人の監査人が、互いの帳簿を知られずに合計だけを出したいと考えています。ホワイトボードの計画は
単純です。各人の数値を人数分の断片に割り、断片は足し合わせたときだけ意味を持つ。

分割はすでに誰かが書いています。ちゃんと足せば戻ります。そして書かれたままでは役に立ちません ──
party 0 が合計をそのまま持ち、他の全員が 0 を持つ形だからです。「ちゃんと足せば戻る」と「秘密を
守る」の差が、この問題のすべてです。

## 考え方

`F_p` 上の加法的秘密分散です。秘密 `s` は、和が `s` になる `n` 個の値になります。算術は 3 行です。
これを暗号にしているのは、**そのうちどの n-1 個も秘密と独立している**ことのほうで、それは主張する
ものではなく示すものです。

## 何がデプロイされるか

コンテナが 1 つです。AWS アカウントもクラウドリソースもインストールも要りません。このデプロイの
ledger (デプロイごとの `FLAG_SEED` から導出されるので、他の人とは違う値です) と、遊ぶための
`shares` コマンドが入っています。公開されるポートは platform が flag を POST する loopback の
`/verify` だけで、あなたが触ることはありません。

## 遊び方

portal で問題を起動し、**コンテナのターミナルに接続**してください。すべてそこで、1 行ずつ進みます。
編集するファイルも、開くエディタも、clone するものもありません。

```bash
shares                                  # コマンド一覧
shares show                             # 題材・自分の ledger・次に打つコマンド
shares recover <total>
shares complete "<expression>"
shares refresh <o0>,<o1>,...
shares transfer recover=<n> complete=<n> refresh=<o0>,...
shares status                           # 通した段階
shares flag                             # 4 段階すべて通ると TC{...}
```

`python /problem/shares.py <command>` も同じものです。

`shares show` は「それだけ読めば足りる」ように書いてあります。迷ったら何度でも戻ってください。

### `recover` ── 往復と、その対比

ledger A は全 share が画面に出ています。足して `[0, p)` に戻し、それを出してください。この段階を
易しくしてあるのは意図的です。合計を一意に決める視界と、share が 1 つ欠けただけの視界を、同じ画面
に並べるためにあります。

### `complete` ── 見えていない数値のための 1 行

ledger B は別の合計で、1 人分の share が欠けています。その合計は最後まで表示されません。問われて
いるのは「その合計は何か」では**ありません**。「どんな target が来ても、欠けている share を選んで
必ずそこに着地させられるか」です。

```bash
shares complete "<expression>"
```

名前は `target`、`known`、`modulus`。演算子は `+ - * % ( )` と整数です。クォートしてください ──
`*` はシェルの glob です。採点は `(target, known, modulus)` の**族**との一致で行い、画面の case と
の一致では行いません。画面の case だけなら、その答えを定数で書けば通ってしまうからです。

field のどの target でも成立するなら、その n-1 個は合計について何も絞っていません。これが「漏れ
ない」の実行可能な定義で、どれだけ言葉を尽くすより強いものです。

`known` (可視 share の和) は**簡約せずに**渡されており、modulus より大きい値です。field に戻し忘れ
た式は、族の端の case ではなくあなた自身の数値で落ちます。

### `refresh` ── 同じ秘密を、別の share で

party ごとに 1 つずつ offset を出し、share に足します。要件は 2 つあり、片方だけでは refresh では
ありません。offset の和が 0 であること (合計が動かない) と、**どの offset も 0 でない**こと (すべ
ての share が動く) です。

```bash
shares refresh 3,5,9,84,8
```

### `transfer` ── 見たことのない設定で同じ 3 つ

3 段階を通すと 2 つ目の設定が渡されます。別の modulus、別の人数、別の欠員 ── そして今度は可視
share の和が**前計算されていません**。その 1 枚が転移の本体です。同じ問いから足場を 1 枚外すこと
が転移だからです。

## 進捗はコンテナの中にあります

`shares status` は `/tmp` 配下のファイルを読みます。コンテナ内で書き込めるのはそこだけです
(他はすべて read-only)。コンテナを作り直すと 4 段階は最初からになります。読み方が分かっていれば
数分でやり直せますし、永続ボリュームは壊れうるものが 1 つ増えるだけです。

## 保証範囲

ローカル実行は**自習用の honor-system 検証**です。マシンも Docker デーモンも image もあなたの管理下に
あるので、image の中身はあなたに対して秘匿されていません。具体的に書きます。

- flag の導出元である `FLAG_SEED` はコンテナの環境変数に入っています。どの段階も通さずに flag は
  計算できます。
- `fixtures/generate.py` は image の中にあります (`shares show` の表示がそこから作られるためです)。
  そこで両方の ledger が作られており、読めば各段階が問うている合計が手に入ります。

4 つの段階は解錠すべき鍵ではなく順路であり、飛ばして困るのはあなただけです。`author` stage の分離が
買っているのはもっと狭いことです。reference の解答とそれを採点する suite があなたの動かす image に
入っていないので、問題を解いてしまうファイルから目を逸らす必要がありません。seed が買っているのは
本物です。ledger も設定も flag もこのデプロイ由来なので、他人の実行結果を暗記しても持ち越せません。
そして completion の判定は構造的です ── 族全体で算術と一致する式なら、誰も書いたことのない書き方
でも受理します。

これは自習と誠実な練習を支えます。競技順位・試験・修了判定は**支えません**。
それらには participant が管理しない verifier が必要で、
[#271](https://github.com/susumutomita/TenkaCloudChallenge/issues/271) で追跡しています。

## 作問者向け

この問題はコンテナのターミナルから遊ぶので、参加者が編集するファイルを一切持ちません。
[`TEMPLATE.md`](../../docs/curricula/advanced-cryptography-2026/TEMPLATE.md) の 4 target の参加者
契約には違反しているのではなく、その対象外にいます。Makefile は作問者の道具で、参加者の目に触れる
ことはありません。`make play` は participant image の中でシェルを開きます (portal のターミナルが
繋がるのと同じ場所です)。`make test` は公開の自己検査 (インタフェースの性質だけで、答えは含みません)
を実行します。

本命は `make reference-test` です。8 seed で reference の解答を通し、際どい誤答のカタログを全部
落とし、判定器を 1 要件ずつ壊してカタログがそれを全部殺すことを確認し、120 seed を sweep して
「段階が成立しない設定」が無いことを見て、さらに CLI 経由で transfer の lock と 16 通りの進捗状態
を確認します。

この suite が検査ではなく設計そのものを決めた点が 3 つあります。

- **refresh の要件は `fixtures/` ではなく `lab/judge.py` に置いてあります。** mutation suite が
  壊すのは judge なので、fixtures に置いた要件は suite から到達できず、到達できない要件は何も
  テストされていない要件になります。
- offset の個数についての「分かりやすい誤答」(最後の 1 つを落とす、0 を足す) は、和の検査と 0 の
  検査のほうが先に落としてしまいます。そのため「party 1 人につき offset 1 つ」の要件は、**人数が
  違うだけで完全に正しい zero-sharing** をカタログに 2 つ足すまで生き残っていました。
- 本物に見えて本物でなかった mutation が 1 つありました。`judge_recover` と
  `judge_transfer_completion` は字面の同じ `0 <= claimed < p` を持っており、短いパターンは前者に
  当たっていました (そこでは等価変異です)。今はパターンに次の行まで含めてあります。生き残った
  mutant は、テストの不足と同じくらいの頻度で「狙いを外した mutation」です。
