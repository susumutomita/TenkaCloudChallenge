# SHA-256 その 2: ビット演算とメッセージスケジュール

**難易度:** 3 · **想定時間:** 60〜90 分 · **配点:** 200 · **シリーズ:** SHA-256 全 3 問の 2 問目

## ストーリー

1 問目でブロックができました。512 bit を 32 bit ワード 16 個として読めるようになっています。この問題は、
圧縮ループが回り始める前にそのワードへ起きることの全部です。

小さな関数が 8 つあります。回転 1 つ、それに乗った σ が 4 つ、論理関数が 2 つ、そして 16 ワードを 64
ワードへ広げる漸化式。どれも 3 行以内です。そして 8 つまとめて、自分で書いた SHA-256 が静かに違う
digest を出す場所です。どの関数にも、もっともらしい間違いが 1 つずつ用意されているからです。仕様が
シフトしている所を回転する。Σ0 に Σ1 のずらし量を書く。Maj をパリティで書く。schedule の 4 項を加算では
なく XOR で繋ぐ。

8 つのうち 5 つを、1 行ずつ意図的に壊してあります。

## 何がデプロイされるか

コンテナが 1 つだけです。クラウドアカウントも、外部ネットワーク面もありません。

```text
local/
├── starter/schedule.py   ← 編集するのはこのファイルだけ
├── fixtures/generate.py     全 fixture を deploy ごとの seed から導出する
├── tests/public/            読めるテスト
├── tests/hidden/            verifier が実行するテスト (image 内のみ。bind-mount しない)
├── reference/               解答。`make build` が作る image には入らない
├── verifier/server.py       POST /verify。127.0.0.1:18091
└── mutation.py              hidden test が誤答を本当に落とせるかを証明する
```

`make build` は Dockerfile の `participant` stage を作ります。fixture・両方のテスト・verifier・starter が
入り、`reference/` と `mutation.py` は `make reference-test` が作る `author` stage でだけ追加されます。
つまり「走らせろと言われた image」の中に解答は入っていません。これは誤配の防止であって秘匿ではありません
(保証範囲を参照)。

fixture は deploy 時に注入される `FLAG_SEED` から導出されます。同じ seed なら同じ数値なので、自分の
セッションは再現でき、デバッグできます。seed が違えば数値も変わるので、他の人の実行結果から写した値は
役に立ちません。

## Participant Portal での進め方

1. Participant Portal で問題を起動する。同じ画面に問題エディタが表示される。
2. **証拠を調べる**で、この deploy 固有の fixture と公開された証拠を読む。
3. Portal のエディタで starter のソースを編集する。
4. **公開テストを実行**を押し、直接回答欄があれば証拠から埋める。
5. 各 checkpoint をそのまま提出する。Portal が現在のファイルと回答を準備して送る。

checkout、ターミナル、ローカルエディタ、別画面、コピペは不要です。code checkpoint は現在の
エディタ内容を使います。直接回答は現在の deploy seed へ結び付くため、別 deploy からコピーした
値は拒否されます。

## 採点

6 つの checkpoint を独立に採点します。誤答は 1 回 10 点減点です。

| Checkpoint | 配点 | 提出するもの |
|---|---:|---|
| `rotate` | 20 | 1 語を右回転した結果と右シフトした結果。hex 2 つ、回転が先 |
| `mux` | 25 | fixture の 3 語に対する Ch(e, f, g) を hex で |
| `dependency` | 30 | 入力 1 bit を反転したとき最初に変わる schedule ワードの添字 |
| `sigma` | 45 | 自分の `schedule.py`。`rotr` と σ 4 つを検証される |
| `logic` | 30 | 自分の `schedule.py`。Ch と Maj を検証される |
| `schedule` | 50 | 自分の `schedule.py`。`expand_schedule` を検証される |

hint は全 checkpoint にあります。すべて開いても 200 点中 108 点は残ります。

### コード checkpoint 3 つは本当に独立している

`schedule` が見るのは漸化式の形だけです。`W[i]` がどの 4 語を読み、それを XOR ではなく加算しているか。
期待値は**あなた自身の**σ を使って計算されるので、σ が未完成でも漸化式が正しければ通ります。σ の
正しさは `sigma` の担当です。

これは意図した設計で、mutation suite がそれを仮定ではなく検査しています。σ を壊した変異はすべて
`sigma` で kill され、かつ `schedule` からは見えないこと、両方を assert してあります。そうでないと
1 つの間違いで 2 つの checkpoint を落とし、どちらが原因かも分からなくなります。

## 一度は間違えておきたい 4 箇所

**回転は何も失わない。シフトは失う。** 回転は 32 個の位置の置換なので、立っているビットの数が変わり
ません。自分のコードがどちらをしたか分からないときは、立っているビットを数えてください。

**SHA-256 は両方を使い、どちらかが重要。** σ0 と σ1 は回転 2 つと**シフト**1 つ、Σ0 と Σ1 は回転 3 つ
です。シフトは偶然ではありません。ビットを落とすからこそ message schedule は非可逆になり、64 ワードから
16 ワードを逆算できなくなります。Σ は round の中で状態を撹拌するだけなので、何かを落とす理由が
ありません。

**Ch はマルチプレクサ。** `(e & f) ^ (~e & g)` を 1 bit ずつ読んでください。e が 1 の位置では f の
ビット、0 の位置では g のビットが出ます。セレクタが 32 個並んでいるだけです。多数決ではありませんし、
ワード単位の if/else でもありません。多数決のほうは Maj で、1 bit で見るとパリティ `a ^ b ^ c` と
一致するのは全 0 と全 1 の 2 通りだけです。つまり Maj をパリティで書くと 8 回のうち 6 回は間違い、
それでも雑なテストは通ってしまいます。

**schedule は加算で、XOR は代用にならない。** XOR に桁上がりが無いので、あるビット位置の情報がより上の
位置へ伝わらず、schedule が存在する理由である拡散が起きません。これは主張ではなく検査できます。
回転・シフト・XOR はすべて GF(2) 上で線形なので、全部 XOR の schedule は全体として線形になり、
`expand(a ^ b)` がちょうど `expand(a) ^ expand(b)` になります。加算はそれを壊します。隠しテストは
この性質を直接見ています。

4 つに加えて Python の罠が 1 つ。`value << (32 - amount)` は 32 bit で止まりません。`& 0xFFFFFFFF` を
忘れるとワードは静かに大きくなり、σ が全部おかしくなり、例外は出ません。

## 公開テストが通っても終わりではない

公開テストは σ を仕様のずらし量と突き合わせず、Ch と Maj を混合セレクタで区別せず、展開するブロックは
全ゼロだけです。全ゼロでは XOR と加算が一致するので、schedule の 4 項を XOR する実装でも全部通ります。

隠しテストは境界値 (0、`0xffffffff`、`0x80000000`、`0x55555555`) と seed 由来の語を回し、固定値では
なく関係を検査します。各 σ の XOR に対する線形性、Maj の並べ替えに対する対称性、Ch の「両選択肢が
同じならセレクタは無関係」という性質、そして展開が線形**でない**こと。関係の検査なので、1 回の出力を
暗記しても通りません。

## 保証範囲

ローカル実行は**自習用の honor-system 検証**です。マシンも Docker デーモンも image もあなたの管理下に
あるので、ここには秘匿されているものはありません。`tests/hidden/` を bind-mount せず `reference/` を
participant image に入れないのは、あなたの作業に紛れ込ませないためであって、手が届かなくするためでは
ありません。ソースはどちらにせよこのリポジトリにありますし、`author` stage は自分でビルドできます。

verifier が実際に保証するのはもっと狭く、そして本物です。提出コードは verifier をハングさせたり
クラッシュさせたりできません。checkpoint は echo した id しか加点できません。結果は期待値を漏らし
ません。fixture はこのデプロイの seed 由来なので、暗記した答えは持ち越せません。

これは自習と誠実な練習を支えます。競技順位・試験・修了判定は**支えません**。それらには participant が
管理しない verifier が必要で、
[#271](https://github.com/susumutomita/TenkaCloudChallenge/issues/271) で追跡しています。

## コスト

ゼロです。クラウドアカウントも AWS リソースも使いません。手元のコンテナだけです。

## 作問者向け

`make reference-test` が mutation suite を回します。3 つの suite にまたがる 21 個の壊れた実装、
verifier 自身を狙った 12 個、そして σ の変異が `schedule` suite に漏れていないことを確かめる分離
チェック。すべて検出されなければ失敗です。

一見それらしい変異を 5 つ、意図的に一覧から外してあります。どれも reference と数学的に同値だからです。
Maj を `^` ではなく `|` で書いたもの、Ch で補数をマスクしなかったものも含みます。5 つのうち 2 つは、
実際に survived してから外しました。詳細は `local/mutation.py` の冒頭コメントにあり、そのコメント自体が
この演習の要点です。
