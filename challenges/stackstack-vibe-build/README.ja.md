# AI が書いた検索を、 出荷できる状態にする — StackStack Vibe Build

> 天下クラウド株式会社、 入社 3 日目。 昨日ようやく外から見えるところまで持っていった社内掲示板に、 CTO から次の一手が飛んでくる。
>
> 「過去ログのインポートが終わったので検索を付けてください。 生成 AI に書かせて構いません、 そのほうが速いなら。 要件は仕様書にしてアプリの中に置いてあります」
>
> 書くのは 1 ファイル。 貼るのは 30 秒。 残りの 44 分は、 貼ったものが本当に要件どおりかを確かめる時間だ。

前任者の移行作業で、 板にはアーカイブが残っている。 3 か所に散っていたものを 1 か所に取り込んだものだ。 そこに検索を足すのは関数 1 本の仕事でしかない。 面白いのは、 このアプリが 「検索結果に載せてよい行はどれか」 をコードとして決めたことが一度もない、 という点だ ── そして生成器から返ってくる 20 行も、 それを決めない。

## 何がデプロイされるか

クラウドアカウントには何も作らない。 これは **自分のマシンで動くコンテナ** (TenkaCloud リポジトリで `make local PROBLEM=stackstack-vibe-build`) であり、 本番システムではなくモデルだ。 モデルは小さいので、 何が本物で何を模しているかをここに書いておく。

| 部品 | 実体 |
| --- | --- |
| 掲示板 | StackStack 系が共有する掲示板アプリ (`stackstack-base/`)。 `stackstack-onboarding` と同じもの |
| アーカイブ | インポート済みの行を持つメモリ上の集合。 公開面に一度も出たことのない行も含む |
| あなたの機能 | チェックアウト側の `local/feature/search.mjs`。 読み取り専用でマウントされ、 変わるたびに読み直される |
| `GET /api/search` | JSON 検索。 あなたの `search` を呼び、 返ってきたものをそのまま返す |
| `GET /search` | 検索ページ。 あなたの `renderResults` を呼び、 返ってきた文字列を **エスケープせずに** ページへ置く |
| `GET /api/spec` | 9 項目の要求仕様 R1〜R9。 アプリ自身が持っている |
| `GET /api/selfcheck` | 採点とまったく同じ検査。 いつでも回せて、 「期待した値 / 返ってきた値」 を返す |
| `GET /posture` | 走っているアプリから実測した 5 つの gate と、 緑の gate ごとの受領印 |

公開ポートは 2 つ、 どちらも `127.0.0.1` バインド。 `18080` (板と検索面) と `18081` (プラットフォームが採点を委譲するループバックの `/verify`)。

## 遊びかた

```bash
# 1. 要求を読む
curl -s http://127.0.0.1:18080/api/spec | jq

# 2. 実装する (生成 AI の利用は自由、 むしろ推奨)
open http://127.0.0.1:18080/editor   # エディタで書いて保存。 リポジトリのファイルは書き換わらない

# 3. 使う ── 保存すれば再起動なしで反映される
curl -s 'http://127.0.0.1:18080/api/search?q=板'
open http://127.0.0.1:18080/search?q=板

# 4. 確かめる
curl -s http://127.0.0.1:18080/api/selfcheck | jq

# 5. 提出する ── gate が true のあいだだけ、 チェックポイントごとに受領印が出る
curl -s http://127.0.0.1:18080/posture | jq .tokens
```

`GET /api/feature` は、 ファイルが読み込めたか・何が export されているかを返す。 何も起きないときに最初に見る場所。

## 契約

export する関数は 2 つ。 どちらもリクエストもレスポンスもネットワークも受け取らない。 素のオブジェクトを受け取り、 素の値を返す。

```js
export function search({ query, posts }) {
  //  query: string | null   — ?q= が無いときは null、 有るときはその文字列そのまま
  //  posts: { id, title, author, body, at, visibility }[]
  return { status: 200, body: { /* ... */ } };
}

export function renderResults({ query, matches }) {
  //  query:   trim 済みの検索語
  //  matches: 自分の search が body.matches に入れたものそのまま
  return "<p>…</p>"; // ページへそのまま埋め込まれる HTML
}
```

9 つの規則は `GET /api/spec` にある (走っているアプリから離れないようにするため)。 要約: 検索語が無い・空・空白だけなら `q_required`、 64 文字を超えたら `q_too_long` (64 ちょうどは許可)、 それ以外は `{ query, matches }` を 200 で返す。 entry のキーはちょうど `id` / `title` / `author` / `at`。 一致は `title` と `body` に対する大文字小文字非依存の部分文字列。 返してよいのは `visibility` が `"public"` の行だけ。 `id` の降順に並べてから 10 件で切る。 一致 0 件は 200 と空の `matches`。 そしてページは、 検索語と各 entry の `title` / `author` を **文字として** 表示する ── 1 文字も落とさず、 `&` `<` `>` `"` `'` を実体参照に置き換えて。

## 採点

難易度 3 (中級)、 200 点、 40 点 × 5 チェックポイント。 どれも走っているアプリからの実測で決まる: 作り直したアーカイブ行を一時的に足し、 実際の HTTP で各面に問い合わせ、 終わったら取り除く。

| checkpoint | 実測しているもの |
| --- | --- |
| `search-answers` | 検索語を含む投稿だけが、 仕様どおりの 4 キーで返ること |
| `search-order` | id 降順・上限 10 件・大文字小文字非依存・一致 0 件でも 200 |
| `search-bad-queries` | 4 つの壊れた入力を名前付きで断ること ── ちょうど 64 文字の検索語と普通の検索語は通したまま |
| `drafts-withheld` | 公開してよいものだけが返り、 それ以外がレスポンスのどこにも出ないこと |
| `results-are-text` | 投稿の文字と検索語が、 ページ上に文字として出ること |

提出値はそれぞれの gate の受領印で、 `GET /posture` が gate の true なあいだだけ出す。 提出するとその場でもう一度実測が走る ── 受領印を読んだ時点には存在しなかった行を使って。 だから、 一度緑にしたときの受領印は、 それを稼いだ実装より長生きしない。

ヒントは各チェックポイントに 3 つ (0 / 8 / 12 点)。 問題内の全ヒントを開いても 200 点中 100 点で、 全部読んでも半分は残る。

### 通らない安い直しかた

「機能を正しくせずに採点だけ通す」 やりかたは全部塞いである。 しかもどれも、 先に 「機能が動いていること」 を証明した検査が捕まえる。

- **エンドポイントを消す・export を消す。** どのチェックポイントも 200 と正しい entry を要求する。 gate が 1 つも緑にならないので、 提出する値自体が存在しない。
- **全件返す。** 各バッチには別のタグを持つ行が混ざっていて、 id 集合の完全一致を要求する。
- **何も返さない。** 5 つのチェックポイント全部が、 何かを見る前にまず 「注入した公開行が正しく返ること」 を要求する。 「何も返さなければ何も漏れない」 は、 5 つすべての最初の 1 行で落ちる。
- **全入力を断る。** `search-bad-queries` は正常系 2 本を先に走らせ、 その後で 4 本の 400 を見る。
- **テスト入力を焼き込む / AI に 「テストを通すコード」 を書かせる。** タグも行も id もバッチごとに生成されるので、 コードを書いた時点には存在しない。
- **採点されていることを検出する。** アーカイブには常に生成されたばかりのインポートロットが混ざっているので 「ランダムに見える行」 は合図にならない。 加えて `drafts-withheld` のプローブの 1 本は 16 進数ではなく単語の形をした検索語を使うので、 「grader っぽい入力のときだけ規則を適用する」 実装は残らない。
- **エスケープの代わりに `<` `>` を削除する。** `results-are-text` は、 マークアップが出ていないかを見る前に、 エスケープ済みのタイトルが **1 文字も欠けずに** 出ていることを要求する。 削除実装は前半で落ちる。
- **危なそうな文字列だけ描画をやめる。** 同じ前提条件で落ちる。
- **post をそのまま返す / 「念のため」 フィールドを足す。** entry のキーはちょうど 4 つ。 加えて `drafts-withheld` はレスポンス全文を見るので、 `posts` を入れた 「デバッグ用」 フィールドは `matches` が完璧でも落とす。
- **受領印を控えてから実装を壊す。** どのチェックポイントも比較の前にもう一度実測する。

### なぜページはあなたの HTML をエスケープしないのか

ここでエスケープしてしまうと、 採点対象そのものが消えるからだ。 `GET /search` は `renderResults` が返した文字列をそのまま公開し、 代わりにレスポンスに `Content-Security-Policy: default-src 'none'; sandbox` を付ける ── 中身が何であれ、 ページは何も実行できない。 ポートはループバックから出ず、 動くのは自分が書いた (あるいは自分のツールに書かせた) コードだけ。 参加者の関数は文字列を返すだけでレスポンスに触らないので、 このヘッダを機能ファイル側から外すことはできない。

### あなたのコードはどこで動くか

**空の環境変数で起動した子プロセス** の中。 worker thread ではない。 worker は同一 OS プロセスのスレッドなので `/proc/self/environ` に exec 時の環境が残るし、 アプリと同じプロセスで動くコードは受領印を自作したり採点自身の `fetch` を差し替えたりできてしまう。 別プロセスにはそのどちらもない。

そのうえで、 **この問題が採点に使う値は 1 つも `FLAG_SEED` 由来ではない**。 受領印はアプリが起動時に生成し、 環境変数には一度も置かない秘密から derive される。 これは StackStack 系全体の設計判断だ ── 参加者のコードは意図的にこのコンテナの中で動くのだから、 「何かが起きた」 ことを示す値は、 そのコードが読めるものから計算できてはいけない。

正直に書いておく限界が 2 つ。 あなたのコードはループバックには届くので、 `search` からアプリを呼び返すことはできる。 1 回ごとの時間制限と同時実行数の上限があるので板と `/verify` は答え続けるが、 実測のほうは (ハングではなく) 失敗する。 そして同期の無限ループは時間制限で殺される ── それでもコンテナが重いままなら `make local-down` が復旧経路。

## コスト

ゼロ。 AWS アカウントもクラウドリソースもネットワーク送出もない。 コンテナ 1 つとループバック 2 ポートだけで、 `make local-down` で消える。
