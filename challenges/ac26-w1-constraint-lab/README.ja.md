## ストーリー

新しい policy engine は、アクセスの可否を if 文で決めません。判断を算術回路として表現します。そう
すれば、判断を下したサービスを信用しなくても、あとから誰でも監査できるからです。

素晴らしい設計です。ただし monitor が出す出力は 1 語だけ ── `PASS` か `FAIL` か。今朝ひとつ拒否が
出て、顧客はどの条件で落ちたのかを知りたがっていて、部屋の誰も答えられません。あなたはその監査
ツールを仕上げます。足りていないのは、**なぜ**を言う部分です。

## 何がデプロイされるか

コンテナ 1 つだけです。AWS アカウントもクラウドリソースもインストール作業も要りません。コンテナの
中に、このデプロイ専用の field と回路 (per-deploy の `FLAG_SEED` から導出するので他の人とは違います)
と、それを遊ぶための `audit` コマンドが入っています。公開されるポートは、提出した flag を platform
が POST するための loopback `/verify` だけで、参加者が触ることはありません。

## この問題で掴むもの

回路はプログラムではありません。**すべて 0 にならなければならない式の集合**です。witness とは、各
signal に値を割り当てたものにすぎません。「この witness は回路を満たす」とは residual がすべて 0 で
あるということで、0 でない residual こそが「どの主張が落ちたのか」を教えてくれます。

residual は `F_p` の元です。`-1` と `p-1` は同じ元であり、どちらも 0 ではありません。

## 遊び方

portal で問題を起動し、**コンテナのターミナルに接続**してください。すべてそこで、1 行ずつ進みます。
編集するファイルはなく、エディタも clone も要りません。

```bash
audit                    # コマンド一覧
audit show               # field、回路、それを満たす witness、落ちた witness
audit explain c2         # 制約 1 本の残差を operand 名つきで表示
audit trace 0,3,125,0,0  # 落ちた witness の全 residual を circuit 順に
audit admit "(tier - 3)*(tier - 40)"
audit transfer 0,56,89,0,0,64
audit status             # クリア済みの段階
audit flag               # 3 段階とも通ったら TC{...}
```

`python /problem/audit.py <command>` でも同じです。

### `trace` ── 評価器になる

`audit show` は、回路と、residual がすべて 0 になる witness と、monitor が落とした witness を出します。
落ちたほうについて全制約の residual を自分で計算し、circuit 順に、それぞれ `[0, p)` に正規化して
提出してください。

不合格のときに返るのは「**何個**ずれているか」だけで、どれがずれているかは返りません。これは意図的
です。どれがずれているかは「間違いがどこにあるか」の地図そのもので、その地図を自分で描くことがこの
stage だからです。鍵ではありません ── 1 か所だけ変えれば個数は動くので、スクリプトによる探索は可能
ですし、そもそもこれは honor-system のローカル実行です (「保証範囲」を参照)。答えを漏らさない助けは
`audit explain <id>` のほうです ── 制約 1 本が 0 を要求している式を、operand 名つき・値なしで出します。

### `admit` ── 写すのではなく書く

回路には membership 制約がありません。残差の表にも member の行はありません。それはまだ誰も書いて
いない制約です ── signal `tier` は許可された値のどれかでなければならない。その許可値ちょうどで 0 に
なり、field の他のどの元でも 0 にならない残差を提出してください。

```bash
audit admit "(tier - 3)*(tier - 40)"
```

引用符で囲んでください。`*` はシェルの glob です。判定は**field を全走査**します。許可値だけを試す
のではありません。許可値の先頭だけを固定する gadget は、書けるかぎりの正常系の例をすべて通り、ここで
落ちます。それがこの stage の要点です。

### `transfer` ── 見たことのない回路で

上の 2 つを通すと、別テナントの回路が渡されます。素数も signal 名も違い、制約が 1 本多く、並びも
違います。そして、いま自分で書いた membership gadget が deploy 済みの制約として入っています。読む
というのは、自分が構成したものを評価するということです。コマンドの形は同じで、持ち越せるのは読み方
だけです。

## 採点

| | |
|---|---:|
| flag 正解 | **200** |
| 誤答 | 1 回 −10 |
| hint 1 | −40 |
| hint 2 | −60 |

hint を両方開いても 200 点中 100 点が残ります。flag はこのデプロイの seed から導出される `TC{...}`
で、他人の実行結果を暗記しても当て推量でも通りません。

## 進捗はコンテナの中にあります

`audit status` は `/tmp` 配下のファイルを読みます。コンテナ内で書き込めるのはそこだけです (他は
すべて read-only)。コンテナを作り直すと 3 段階は最初からになります。答えが分かっていれば数分で
やり直せますし、永続ボリュームは壊れうるものが 1 つ増えるだけです。

## 誰も代わりに教えてくれない間違い方 3 つ

1. **`-1` は 0 ではないし、`p-1` も 0 ではない。** 両者は同じ field の元です。途中で負になった残差は、
   `[0, p)` に戻すまで終わっていません。
2. **signal を `flag` と名付けても boolean にはならない。** 値を縛るのは制約だけで、それは
   `flag * (flag - 1) = 0` の 1 本です。無ければ `flag` は field のどの元にもなれます。
3. **正しい witness 1 つでは何も示せない。** 制約が足りない回路でも、正常な witness なら residual は
   全部 0 になります。gadget を field 全体で走査するのはそのためです。

## 公式 Week 1 課題との関係

これは `mechanism` 問題です。公式課題が前提としている読解力を作り、公式課題そのものの手前で意図的に
止まります。公式課題は underconstraint を突きますが、そのためには「どの条件がどの式になったのか」が
見えている必要があり、それがここで作る trace です。講座の式・fixture・solution は一切転載していません
(`GOVERNANCE.md` §2)。

## 保証範囲

ローカル実行は**自習用の honor-system 検証**です。マシンも Docker デーモンも image もあなたの管理下に
あるので、image の中身はあなたに対して秘匿されていません。具体的に書きます。

- flag の導出元である `FLAG_SEED` はコンテナの環境変数に入っています。どの段階も通さずに flag は
  計算できます。
- `fixtures/` は image の中にあります (`audit show` の表示がそこから作られるためです)。そこには各
  stage の採点基準になる評価器が入っており、読めば答えはすべて手に入ります。

3 つの段階は解錠すべき鍵ではなく順路であり、飛ばして困るのはあなただけです。`author` stage の分離が
買っているのはもっと狭いことです。解答そのものとそれを採点する suite があなたの動かす image に入って
いないので、問題を解いてしまうファイルから目を逸らす必要がありません。seed が買っているのは本物です。
field も回路も flag もこのデプロイ由来なので、他人の実行結果を暗記しても持ち越せません。そして判定は
特定の 1 文字列との一致ではなく構造的なので、見たことのない正解でも受理します。

これは自習と誠実な練習を支えます。競技順位・試験・修了判定は**支えません**。
それらには participant が管理しない verifier が必要で、
[#271](https://github.com/susumutomita/TenkaCloudChallenge/issues/271) で追跡しています。

## 作問者向け

`make play` は participant image の中でシェルを開きます。portal のターミナルが繋がるのと同じ場所です。
`make test` は公開の自己検査 (インタフェースの性質だけで、答えは含みません) を実行します。

本命は `make reference-test` です。設計が依っている fixture の不変条件を検査し、両ケースの破壊パターン
を網羅する seed 群で reference の解答を通し、惜しい誤答のカタログを全部拒否し、そのうえで判定器を 1
要件ずつ壊して、そのカタログが壊れた版を全部殺せることを確認します。不変条件のうち 2 つは具体的な
失敗のために存在します。落ちた witness は必ず 2 本以上の制約を破ること (0 が並ぶ中に 0 でない残差が
1 つだけなら、それは trace ではなく当て推量になります)、そして transfer 側の落ちた witness は必ず
`member` か `boolean` の残差を 0 でなくすること (でなければ転移 stage は 0 を書き写すだけで通ります)。
