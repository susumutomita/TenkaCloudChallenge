# 60分で開催する「つながるオフィス」

目的は、普段話さない拠点・職種の人同士が、相談して1つの結果を作ることです。AWSスキルの試験ではありません。操作できたかだけでなく、**全員が役割を持てたか・仲間の言葉が役立ったか**を振り返ります。

## 初回の規模と用意するもの

最初は2〜4チーム、1チーム4人を目安にします。対応容量の上限を検証した数字ではありません。拠点と経験を混ぜて編成し、経験者だけを操作担当に固定しません。

| 用意するもの | 数量・担当 |
| --- | --- |
| 開催責任者・司会 | 1人。開始、終了、障害時の判断を一本化 |
| 環境・問い合わせ担当 | 1人。司会と兼任するなら、障害対応中の進行を止めると決める |
| 会場または通話 | 全体1つ、チームごと1つの会話場所。音声・チャットどちらも使えるようにする |
| PCとブラウザ | 参加者1人1台を推奨。最低チーム1台＋カードを読める別端末。コマンド入力不要 |
| ポータル接続先・チームキー | チームごとに1組。チーム限定の連絡場所で配布 |
| チーム用AWS環境 | 本体の開催手順に従い、各チームに1つの登録済み競技アカウントと問題デプロイ |
| 記録シート | チームごと1枚。下の表をコピー |

費用支援の有無だけで準備完了とはしません。予算上限・利用するアカウント・請求確認担当・撤収期限を責任者が確認します。特定の団体からの支援は前提にしません。

ポータルへ誤った合言葉を出すと、難易度1の標準ルールで5点減点です。問題画面での試行は無料。司会は「コピーして同じ番号のA/B欄へ貼る」を先に実演します。

端末も交代する場合、準備では引き継ぎコード、本戦では最後に得た合言葉（AまたはB）をチーム内で渡します。新しい担当は同じGameUrlの引き継ぎ欄へ貼ります。他チームの控えは拒否されます。同じ端末なら人だけ交代できます。

## いつまでに何をする？

以下は初回の作業量の目安です。実施後に実績へ置き換えます。

| 時期 | 担当・目安 | 完了の目印 |
| --- | --- | --- |
| 2〜4週間前 | 責任者、30分 | 交流の目的、対象者、候補日、人数、予算、会場/通話を1枚にする |
| 2週間前 | 環境担当、60〜120分 | 本体とカタログの参照先を固定し、Lite・テスト2チームを準備。経験の浅い協力者を2〜4人募集 |
| 1週間前 | 司会・環境担当・協力者、60分＋片付け30分 | 下のリハーサル判定を通し、所要時間とつまずきを記録 |
| 前日 | 責任者、30分 | 混成チーム、連絡先、司会台本、役割、欠席時の代役を確定 |
| 当日30分前 | 環境担当、30分 | 全員がログインでき、準備のGameUrlが開き、本戦はロック中。公式競技時間はまだ開始しない |
| 終了後 | 環境担当、30分 | 結果保存、問題デプロイ削除、不要な本体撤収、残存リソースの確認 |
| 翌週 | 責任者、30分 | 振り返りを1枚にし、次回の担当と直す箇所を決める |

## Gateの設定と配布

1. [本体のAWS開催手順](https://github.com/susumutomita/TenkaCloud/blob/main/docs/operations/event-runbook.md)でLiteと競技アカウントを準備。イベントには **office-link-gate と office-link-gameday の2問だけ**を登録し、各チームへ両方デプロイする。
2. イベント詳細の **「進行 / Gate」** を開く。TenantAdminで **「このテナントで Progression Gate 機能を有効化する」** をONにする（既定OFF）。同じテナント内の他イベントへの影響は、そのイベントのGate設定も確認する。
3. **Gate challenge = office-link-gate**、**アンロック対象 = office-link-gameday だけ**、**デフォルト policy = required**、完了ボーナス = 0。全チームのpolicyは継承とし、offの上書きを置かない。保存して再読み込みし、設定を確認する。[event-gate.json](event-gate.json)が同じAPI設定。
4. 公式競技時間は準備20分＋本戦25分を目安に **45分**。全員が準備画面を開けてから開始。最初は準備だけが操作でき、本戦の接続先・回答は既存Gateでロックされる。
5. 準備の4確認を終えると、修了の合言葉を1つ発行。ポータルへ正しく提出して100点＋修了となったチームから、問題一覧を更新して本戦へ。準備途中の加点はない。本戦100点と合わせてイベント合計200点、追加ボーナスなし。
6. ポータルURLとチームキーはチーム限定で配布。本戦のGameUrlを事前配布しない。リハーサルは別イベント・別チームで行い、本番へ試験得点を混ぜない。

既存Gateは単一の準備問題から対象を解放する方式です。複数の本戦を対象にすると同時に解放されます。このセットでは本戦を1つだけ登録し、問題内も操作→解説→次のミッションの順をサーバーで検証します。終えた問題は復習できます。「未完了の課題が一度に1つ」という設計です。別の問題をイベントへ足すと、この設計になりません。


### デプロイする問題の版を固定する

Liteランチャーの既定 `ProblemsRepoRef` は最後に公開したリリースを指すため、この新しいセットを含むとは限りません。リハーサルで使う本体チェックアウトの `release/tenkacloud-release.json` にある `sources.catalog.commit` を控え、ランチャーの **ProblemsRepoRef** へ指定します。本体の **RepoRef** もリハーサルするコミットへ固定してください。公開済みリリースに収録されるまでは候補版での開催準備です。

ローカルから `make deploy` する場合も、本体の `problems` をそのgitlinkへ合わせます。デプロイ前に `challenges/office-link-gate/metadata.json` と `challenges/office-link-gameday/metadata.json` の両方が存在することを確認します。版を変えても既存イベントに問題やGate設定が自動登録されるわけではありません。

## 60分の司会台本

| 開始から | 進め方 |
| --- | --- |
| 0〜5分 | 名前・拠点の紹介。4人の役割と、準備→本戦の流れ、合言葉の提出を実演 |
| 5〜25分 | 準備Challenge。場所・権限・復旧・結果の確認を1問ずつ相談。各問で説明担当を替え、4人全員が一度説明。最後の合言葉を提出すると本戦が開く |
| 25〜50分 | 本戦の配送→共有→復旧を順に進める。操作と解説それぞれを提出。時間配分は目安で、準備修了したチームから本戦に進める。全員同じ終了時刻 |
| 50〜60分 | 公式スコアと同順位の表彰。「仲間の一言で分かったこと」を1人ずつ共有 |

読む人2人＋操作担当＋確認担当の4役を交代します。準備では1人が説明、1人が例を読み、1人が操作、1人が確認。チャット参加も可。発言量で順位をつけません。選択肢の正誤は自動採点できますが、全員が理解したかは説明を聞いて確認します。先に終えた人は仲間に質問し、操作を奪わないようにします。

## 開催を決める前のリハーサル判定

- [ ] 初参加者が5分以内に準備の最初の確認を終えた（目標。未達なら導線を修正）
- [ ] 準備開始前・1〜3段階完了時は本戦のURL・回答がロックされ、URL直打ちでもポータルの回答が拒否される
- [ ] 準備4段階を終えても未提出ならロック継続。修了の合言葉をポータルへ出して100点＋本戦解放
- [ ] 未修了の別チームはロック継続。Feature flagとrequired設定を再読み込みでも確認
- [ ] 2チームで別のGameUrlが配られ、片方の合言葉では他方に加点されない
- [ ] 1Aだけ提出して15点、1Bを提出してさらに15点。操作だけで部分点が付く
- [ ] 同じ回答の再提出で二重加点されない。再読み込み後もポータルの得点が保たれる
- [ ] 本戦6つの提出で100点（準備込み200点）となり、ポータル上部とスコアボードに反映される
- [ ] 英語、必要な端末・回線、役割カード、通話/チャットを試した
- [ ] 誤った選択から修正でき、助け舟を開いても減点されない
- [ ] 全員が少なくとも1回は操作か説明を担当できた
- [ ] 終了後の提出制限、デプロイ削除、残存確認を通した

コードのテスト合格と、この実AWS・複数人リハーサルの完了は別です。初回の効果を確認する前に「初心者全員が60分で完了」「交流が増える」と断定しません。

## 困ったとき

| 症状 | 次の一手 |
| --- | --- |
| 誰も話さない | カードを1人1枚ずつ担当させ、「見えているコード/時刻を1つ伝える」と具体的に頼む |
| 1人がすべて操作 | 次の解説は別の人が操作。詳しい人は30秒待って質問に答える役へ |
| 知識で止まる | 問題画面の無料の助け舟を使う。必要な専門知識を口頭試験にしない |
| 問題は成功、得点は0 | 合言葉がポータルの対応するA/B欄へ提出済みか確認。成功画面だけでは加点されない |
| リロードで控えが消えた | 仲間の引き継ぎコード/最後の合言葉で再開する。控えがなければ解き直す。ポータルで提出済みなら重ねて提出する必要はない |
| GameUrlが開かない | 運営者が元の配布先とデプロイ状態を確認。全体チャットへURLや鍵を貼らない |
| 全チームが不調 | 司会が中断と次の案内時刻を伝える。問題画面だけの模擬点へ切り替えて正式結果と混ぜない |

## 次回へ残す1枚

| 項目 | 記録 |
| --- | --- |
| 日付・目的・形式 | 記入。氏名や鍵は公開資料へ残さない |
| 人数・チーム数・AWS経験 | 記入 |
| 初得点までの時間 / 完了したチェック数 | 計測する。未計測は未計測と書く |
| 全員が役割を担当できたか | はい/一部/いいえ＋理由 |
| 相談が生まれた場面 / 止まった場面 | 具体例を1つずつ |
| 次回直すこと・担当・期限 | 1〜3項目に絞る |
| 実際の準備・運営・撤収時間と費用 | 請求と残存確認後に記入 |

## 共同作問へ進むとき

コミュニティ開催は、まずこの入門版を通し、同じ「手がかりを分ける → 操作 → 説明」の型で身近な困りごとを1つ持ち寄ります。会場・開催日・共同作問者・レビュー担当・AWS費用担当は別々に決めます。3〜4月などの候補月だけでは確定開催として掲載しません。

標準問題と本体は公開OSSとして自社開催に使えます。設計・準備・当日運営の支援や、企業固有のシステムを題材とした非公開問題は、既存の開催支援・個別見積りの窓口へ相談できます。この入門セットの得点を、そのまま採用や社内認定の判定基準にはしません。評価用途では別途、測りたい能力・採点基準・配慮事項を設計します。
