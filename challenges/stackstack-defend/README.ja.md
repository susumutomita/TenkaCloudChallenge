# 止めずに直す — StackStack defend

> TenkaCloud Challenge · `challenges/stackstack-defend` · 難易度 3 · 45〜60 分 · `multi-verify` 採点

板は動いている。 見ていないあいだに 「下書き」 機能が生えていて、 その下書き機能が、
見せてはいけない相手に中身を見せている。 止めることはできない ──
明日の全社発表の原稿を、 いま誰かがその上で書いている。

**AWS 不要**。 自分のマシンで Docker コンテナが 1 つ動くだけで、 クラウドアカウントも
資格情報も要らない。 モデル化しているのは 「見られながら直す」 インシデントだ ──
正常なトラフィックと、 通ってはいけないトラフィックが途切れずに届き、
その両方が毎ラウンド採点される。

## 何がデプロイされるか

| どこに | 何が |
| --- | --- |
| **自分のマシン (Docker)** | StackStack 共有ベースアプリを `SCENARIO=defend` で起動したもの |
| `127.0.0.1:18080/` | `stackstack-onboarding` と同じ板 (変更なし) |
| `127.0.0.1:18080/desk` | 下書きデスク ── アカウント、 token、 追加された経路 |
| `127.0.0.1:18080/api/drill` | 走り続けているトラフィックが実際に測った内訳 |
| `127.0.0.1:18081` | TenkaCloud の採点系が委譲する loopback の `/verify` |
| `127.0.0.1:18080/docs` | API コンソール ── アクセス方針の閲覧・変更・破棄 (`/api/settings`) |

アクセス方針の出発点は読み取り専用でマウントされ、 変更は API 経由でコンテナ内にだけ置かれる。
リポジトリのファイルは何をしても書き換わらない。 板自身の設定 (`/api/config`) は onboarding から変更なし。

image は StackStack 系問題が共有する [`stackstack-base/`](../../stackstack-base) から
ビルドされる。 下書きの id・アカウントの token・漏れている marker は、
デプロイごとにランダムな `FLAG_SEED` からコンテナ内で導出される。 gate の受領証は
起動時に生成される別の秘密から作られる。 答えはリポジトリに 1 つも置かれておらず、
2 つのデプロイが同じ答えを共有することもない。 両ポートとも `127.0.0.1` のみに bind。

### モデルについて正直に書く

ここにクラウドは無い。 WAF も、 2 台目のホストも、 **攻撃側の別マシンも無い**。
「攻撃トラフィック」 は、 同じコンテナの中から同じリスナーへ毎秒数回の実 HTTP を
投げているドリルだ。 ネットワークのふりをしているのではなく、
トラフィックジェネレータであり、 `/api/drill` でもそう名乗っている。

はっきり書いておくべき帰結が 2 つある。

- **送信元アドレスによる遮断はモデル化していないし、 採点もしていない。**
  全 probe が同一プロセスから loopback で届くので、 アドレスに基づく答えはここでは
  表現できない。 試させてもいない防御を 「防いだ」 と採点する代わりに、
  この問題は表現できる 2 つの場当たり ── 機能を止める、 流量で絞る ── を用意して、
  どちらも測定で落ちることを示す。 本物の L3/L7 版は AWS 上の
  [`stackstack`](../../battles/stackstack) Battle の `rate_limited` gate が担当する。
- **方針ファイルはコードではなくデータ。** 書いたものがアプリのプロセスに
  import されることはない。 評価器は scenario 側にあり、 ファイルは JSON として
  parse される。 採点される成果物から、 採点している側へ届く経路は存在しない。

AWS では何に相当するか。

| ここでは | 実際には |
| --- | --- |
| `access.json` の rules | IAM / Cedar のポリシー、 あるいは行レベルセキュリティの述語 |
| id ではなく関係を書いたルール | IAM の principal tag `Condition`、 `USING (owner_id = current_user)` |
| ドリルの正常トラフィック | 直している間も止まってくれない実際の利用者 |
| ドリルの攻撃トラフィック | StackStack Battle の `anonymous-spam` probe |
| `GET /posture` の gate | 修正を通す前に置く昇格ゲート |

## ミッション

5 つのチェックポイント、 合計 200 点。

| チェックポイント | 点 | 何を訊いているか |
| --- | --- | --- |
| 下書きから漏れているものを、 自分の目で確かめる | 30 | 開けてはいけない下書きから実際に取り出した値 |
| 他人の下書きが読める状態を止める | 45 | 通ってはいけない read を見張る gate の受領証 |
| 正規の利用者を 1 人も止めない | 45 | 4 アカウントが仕事を続けられていることを見張る gate の受領証 |
| 公開の経路も閉じる | 40 | 通ってはいけない publish を見張る gate の受領証 |
| 止めずに直したことの合格印 | 40 | 5 つの gate が全部緑になって初めて出る `GET /posture` の合格印 |

## 手順

1. 起動する。

   ```
   make local PROBLEM=stackstack-defend
   ```

2. `http://127.0.0.1:18080/desk` を開く。 4 つのアカウントが並び、 うち 3 つの token が
   出ている。 1 つは意図的に出していない。

3. 調査用のアカウントで実際に見る。

   ```
   curl -s -H "Authorization: Bearer <u-guest の token>" http://127.0.0.1:18080/api/drafts | jq
   curl -s -H "Authorization: Bearer <u-guest の token>" 'http://127.0.0.1:18080/api/draft?id=<id>' | jq
   ```

   返ってきてはいけないものが何か、 自分の目で確かめる。 最初のチェックポイントは
   「答えを言い当てたこと」 ではなく 「実際にこれをやったこと」 を採点する。

4. 採点の基準になっているルールを読む。 前任者が板に残した投稿だ。

   ```
   curl -s http://127.0.0.1:18080/api/board | jq -r '.posts[] | select(.seeded) | .body'
   ```

5. 何が測られているかを見る。

   ```
   curl -s http://127.0.0.1:18080/api/drill | jq '{window, cleanForMs, holdMs}'
   curl -s http://127.0.0.1:18080/api/drill | jq '.lastFailures'
   ```

   `lastFailures` に出るのは症状 ── 誰が止まったか、 何が通ってしまったか ── だけで、
   それを直すルールは出てこない。

6. 原因を直す。

   ```
   curl -s http://127.0.0.1:18080/api/settings | jq          # いまの方針
   # 変更は API コンソール (docs) の PATCH /api/settings から送る
   ```

   評価器が理解する書き方は
   `curl -s http://127.0.0.1:18080/api/policy | jq` の `grammar` に出ている。
   送れば次のリクエストから反映される (再起動は不要)。 通らない変更は理由つきの
   `400` で弾かれて何も変わらず、 黙って動く既定値に差し替わったりはしない。

7. あとは触らずに走らせる。

   ```
   curl -s http://127.0.0.1:18080/posture | jq
   ```

   ```jsonc
   {
     "gates": {
       "policy_loaded": true,
       "service_intact": true,
       "reads_held": true,
       "publishes_held": true,
       "held_under_load": false
     },
     "tokens": { "reads_held": "TC{...}", "...": "..." },
     "ready": false,
     "readyToken": null
   }
   ```

   最後の gate は時間だ。 **既定で 60 秒**、 どこにも悪いラウンドが出ないこと。
   残りは `curl -s http://127.0.0.1:18080/api/drill | jq '{cleanForMs, holdMs}'` で見える。
   1 ラウンドでも崩れると 0 に戻る。

8. 最初の壊れた状態に戻したくなったら、 変更を捨てる。

   ```
   curl -s -X DELETE http://127.0.0.1:18080/api/settings
   ```

   再現より先に方針を直してしまった場合も、 これで最初のチェックポイントを取り戻せる ──
   戻して、 再現して、 もう一度直す。 コンテナを作り直しても同じ状態に戻る。

## この問題が足している経路

| 経路 | 用途 |
| --- | --- |
| `GET /desk` | 下書きデスク (ページ)。 アカウント・token・下書き・経路 |
| `GET /api/drafts` | その資格情報で見てよい下書きの一覧 |
| `GET /api/draft?id=…` | 下書き 1 件 (本文つき) |
| `POST /api/drafts` | 自分の下書きを書く |
| `POST /api/publish?id=…` | 下書きを公開キューに載せる |
| `GET /api/published` | 公開キュー ── タイトルと所有者だけで、 本文は載らない |
| `GET /api/policy` | いま読み込まれている方針と、 受け付ける文法 |
| `GET /api/drill` | 継続測定 ── window、 hold、 直近の症状 |

板自身の経路 (`GET /`、 `/api/board`、 `/api/logs`、 `/posture`、 `/healthz`、
`POST /api/posts`) は stackstack-onboarding から変わっていない。

## なぜこう作られているか

「攻撃を止める」 の場当たりな答えはすべて実行できるようになっていて、
そのすべてが測定で落ちる。 それが罰ではなく、 この問題の中身だ。

- **全部拒否する。** 通ってはいけないものは 1 件も通らず、 攻撃側の gate は本当に
  緑になる ── アプリは受領証も出す。 それでも 1 点も入らない。 対応する
  チェックポイントは同時に `service_intact` を要求し、 4 アカウントは止まっているからだ。
  「攻撃は止めました」 に価値があるのはサービスが動いているときだけ。
- **機能を止める** (`"enabled": false`)。 拒否が `503` になり、 `503` は held に
  数えない ── ドリルは 「方針が判断した」 と 「機能が落ちている」 を区別する。
  同時に正常トラフィックも死ぬ。 採点上も現場と同じく二重の損。
- **流量で絞る** (`readsPerRound`)。 `429` も held には数えない。 しかも件数が多いのは
  正常側なので、 攻撃に刺さるところまで下げると先に 4 人の利用者に刺さる。
- **攻撃していたアカウントを名指しで塞ぐ。** 読みに来るアカウントは毎ラウンド回るし、
  塞いだアカウントは自分の下書きの正規の読者でもある。 `service_intact` を失って、
  漏れは残る。
- **いま見える id を書き出して、 それだけ許可する。** 初期状態は一覧を 1 リクエストで
  全部渡してくるので、 これは本当に誘惑される。 数ラウンドごとに、 表を書いた時点では
  存在しなかった id の下書きが現れ、 見えてよい集合が表の下からずれていく。
  関係で書いた方針は、 触らなくても正しいままでいる。
- **read だけ直して終わる。** 公開は意図的に別採点にしてある ── そこが忘れられる側だから。
  公開のルールには条件が 2 つある。
- **答えを焼き込む。** id も token も marker もデプロイごとの `FLAG_SEED` 由来で、
  受領証は起動時の秘密由来 ── 同じコンテナの再起動をまたいでも同じにならない。
  そのうえ最初のチェックポイントは 「本来渡してはいけない相手に、 アプリが実際に
  marker を渡したこと」 を要求する。 文字列を知っていることと、 それを起こしたことは別だ。

### 採点があなたの環境に対してやらないこと

採点はあなたの板に何もしない。 どのハンドラも状態を読んで値を比べるだけで、
下書きを書いたり公開したり、 何かを回したり、 方針を書き換えたりはしない。
誤答で環境が壊れることはなく、 リトライされた判定が二重に効くこともない。

受領証の 4 チェックポイントには **誤答減点が無い**。 想定される進め方が
「直す → 待つ → 確かめる → 提出する」 である以上、 確かめる行為に課金するのは
問題が要求していることに課金するのと同じだからだ。

### 正直さの限界

判定は、 あなたが動かしているコンテナの中で計算される。 自分のチェックアウトの
`stackstack-base/` を書き換えて image を作り直せば、 ここの検査はすべて無効化できる。
これはこのカタログのコンテナ問題すべてに当てはまる。 `make local` は pin された
`problems/` submodule からビルドする。

ドリルの間隔・window・hold はふつうの環境変数
(`DEFEND_INTERVAL_MS` / `DEFEND_WINDOW_ROUNDS` / `DEFEND_HOLD_MS`) で、
この問題のテストスイートはこれを使って分を秒に縮めている。 自分で設定してもよい。
変わるのは待ち時間だけで、 要求 (window が完全に綺麗であること、 hold のあいだ
1 ラウンドも崩さないこと) は動かない。

## 採点

`multi-verify`、 5 チェックポイント、 合計 200 点 (Medium tier)。 誤答減点の枠
(10 点 = tier の 5 %) は最初のチェックポイントに全部載せてあり、 残る 4 つは
何度出しても減らない。 各チェックポイントにヒントが 2 つあり、 1 つ目は無料、
2 つ目は 14 / 20 / 20 / 18 / 18。 全部開いても 90 点で、 110 点は残る。

## コスト

ゼロ。 クラウドアカウントには何もデプロイされない。 コンテナは自分のマシンで動き、
`make local-down` で消える。 下書きも公開キューも測定結果もすべてコンテナのメモリ上に
あり、 方針の変更もコンテナの中にだけ置かれる。 片付けたあとにチェックアウトへ残るものは
無く、 `git status` は最初から最後まで clean のままだ。

## Battle に持ち越されるもの

[`stackstack`](../../battles/stackstack) Battle は `phased-polling` で採点される
CloudFormation の問題なので、 JavaScript も in-process のリスナーもその境界を越えない。
持ち越されるのは形のほうだ。

- **数字は 1 つではなく 2 つ** ── Battle の `auth_enabled` gate と `anonymous-spam`
  probe は `board_clean` とは別に採点される。 ここの `reads_held` と `service_intact`
  の関係と同じ。
- **拒否は判断から出てこなければならない** ── ターゲットグループが unhealthy なのと、
  認証されたうえで拒否されたのは別の結果で、 Battle 側でも別々に数える。
- **方針は一覧ではなく関係** ── リソース名が全部変わるデプロイをまたいで生き残るのは
  こちらだけ。
