実務ではどう実装する？（完了後の補足）

今回の設定は、実際に動いているサーバの次の判定へつながっています。以下はこの演習の実装・テストからの抜粋です。架空の業務コード例ではありません。

ルール → サーバの判定

「要求者と所有者が同じときだけ許可」は、所有者を要求者と比べる設定 {"ownerIs":"actor"} に変換されます。HTTPを処理するworkerは共通評価器 decide を呼びます。 

// intro/worker.mjs のHTTP処理で呼ぶ判定
// actor: ログイン中の利用者、record: 取得対象の情報
decide(policy, actor, "read", record)

// runtimes/stackstack/app/access-policy.mjs の比較部分
// draft.ownerId: 取得対象の所有者、actor.id: 要求者
if (matcher.ownerIs === "actor") return draft.ownerId === actor.id;

同じIDなら許可、違えば拒否です。修正は「このIDを隠す」ではなく、情報を返すサーバが毎回この関係を確かめることでした。

判定 → 正のテスト・負のテスト

正のテストは「許可すべき利用が成功するか」、負のテストは「許可してはいけない利用が拒否されるか」です。intro/intro.test.mjs では修正後に次の両方を確かめます。 

// 正: Aが自分を読める
assert.equal((await read("self")).status, 200);
// 負: 同じAが他人を読めない
assert.equal((await read("other")).status, 403);

さらにworkerの実HTTP確認で、B本人の成功とB→Aの拒否、新規IDでも同じ結果になること、成功時の本文が正しいことを確かめています。拒否だけをテストすると、全員を止めた不具合を見逃します。

自分の業務で確かめること

  • 確認: どの情報を、誰が、何のために読んだり変更したりするかを一覧にする。所有者・会社やチームへの所属・管理者の例外を明文化する。
  • 設計: 利用者はサーバで認証した情報から決め、画面や送信された利用者IDを信用して権限を与えない。情報を返す直前に認可し、不明な場合は拒否する。この一問には所属や管理者の例外は実装していない。
  • テスト: 本人と他人、同じ所属と別の所属、許可された役割とそれ以外を対で試す。新しいID、一覧・詳細・更新の各APIでも、成功する本文と拒否を確認する。

自分のサービスの「誰が何をできるか」を一行書き、許可と拒否のテストを一つずつ作るところから始められます。この演習の成功が、業務システム全体の安全性を保証するわけではありません。
