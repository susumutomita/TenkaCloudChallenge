# 依頼書から暗号システムを設計する

> このトラックは Advanced Cryptography Program 2026 の非公式・独立した教材です。講座や運営者とは
> 提携しておらず、承認も受けていません。問題文、コード、データ、図は独自に作成しています。
> この教材への問い合わせは TenkaCloud リポジトリへお願いします。

**Track:** `advanced-cryptography-2026` · **Order:** 710 · **Week 7 / Capstone Design**
· **Role:** `synthesis` · **想定時間:** 120〜180 分 · **配点:** 300

## 参加者が作るもの

人、データ、読んでよい相手、必要な動作を書いた依頼書からシステムを設計します。`design.py` を実装し、
条件が変わると道具の組、部品とデータの流れ、攻撃実験の計画、根拠の表を作り直せるようにします。
`participant.lab.PRIMITIVES` の 6 つの道具は支給済みの教材モデルです。暗号アルゴリズムそのものを
実装する問題ではありません。

無料の日英本文に入力の全項目、戻り値、6 つの必要性判定、道具の仮定、利用可能性と最小性のルールを
定義しています。図と小例から読み、まずは次の独立した 2 条件でデータを分類します。

| 知らせてはいけない人がいる | 直接の元データがある | 分類 |
|---|---|---|
| いいえ | いいえ | `public` |
| はい | いいえ | `private` |
| いいえ | はい | `derived-public` |
| はい | はい | `derived-private` |

問題エディタで `classify_assets` を実装し、公開テストの
`PASS test_asset_labels_follow_two_independent_facts` を確認して `assets` を提出します。
後の関数が未完成でもこの 1 項目から進められます。別の直接回答欄は使いません。

## 画面の進め方と得点

**証拠を確認**で自分の依頼書、同じ依頼書の条件変更、支給済みの道具表を読みます。同じ問題画面で
`design.py` を編集し、公開テストを実行して対象項目を提出します。正答は提出した項目 ID と
`correct: true` を返し、得点と Solved 表示は Portal が管理します。コードの誤答では破った公開ルールを
表示し、非公開の依頼書や正解の値は表示しません。

| 項目 | 配点 | 作業と依存する成果物 |
|---|---:|---|
| `assets` | 30 | 全データを所有者つきで分類する |
| `requirements` | 45 | 依頼書から 6 つの真偽値を求める |
| `alternatives` | 30 | 全 6 案を支給表と信頼条件で比較する |
| `selection` | 50 | 使える道具で要求を満たし、1 個でも除くと不足する組を選ぶ |
| `architecture` | 45 | 正しい道具の組から部品とデータの流れを作る |
| `attacks` | 35 | 正しい図の必要性と、配置した道具ごとの信頼仮定を攻撃計画で覆う |
| `matrix` | 35 | 必要な性質を担当部品と同じ性質の実験へ結び付ける |
| `revision` | 30 | 変わった条件から設計と攻撃の根拠を作り直す |

各項目は個別に提出できます。後半では前提となる成果物も検査します。図が不正なまま攻撃の行だけを
そろえても正答にはなりません。各項目に「仕組み → 小例 → エディタの操作」の 3 ヒントがあり、
**24 個 × 2 点 = 合計 48 点**です。誤答はプラットフォームの配点契約で 1 回 15 点減点です。

正解は一意とは限りません。最小性は「1 個でも除くと不足する」という意味で、個数が最少とは限りません。
部品名、配置、順序を参考解へ一致させる必要はありません。最後には変わった依頼書や新しい依頼書に
対応する図・実験・根拠の組を構成します。固定の成果物や依頼書 ID ごとの対応表だけでは完了できません。

## モデルが確認する範囲

- 比較には全 6 案と、支給表にある実際の仮定・対象外の性質を含めます。
- 全データが図に現れ、読めるデータが禁止された相手に届かないことを検査します。部品の信頼先は実在する
  部品で、信頼の循環は許しません。データの辺が同じ部品へ戻ることは許します。
- 信頼仮定への攻撃行は `assumption: {primitive: 道具名, trust: 仮定名}` で対象を指定します。
  同じ道具を複数部品に配置した場合も、異なる道具名・仮定名の組ごとに 1 行以上が必要です。
- 根拠は同じ性質への攻撃 ID を指します。`property_matrix` と採点が計画を再生成するため、同じ依頼書と
  図に対する `attack_plan` の ID は安定させます。
- 検査は構造、必要項目、参照、文章の有無を対象にします。自由記述の科学的な妥当性、攻撃実験の実行、
  `ciphertext` や `proof` というラベルから本物の秘匿性・計算の正しさを証明することは対象外です。
  実際の主張を実験と限界の説明が支えているかは、人が吟味する必要があります。

## 実行構成と保証の境界

既存の 2 サービスの Compose で、Workbench を `127.0.0.1:18119` に公開します。採点サービスは Docker の
内部ネットワークからだけ到達でき、ポートをホストへ公開しません。参加者イメージにはエディタ、starter、
公開テスト、完成済みの道具表を含めます。参考解、データ生成器、非公開テストは verifier/author 側です。

信頼する親プロセスが、制限した Linux 子プロセスから関数の値だけを受け取って採点します。子には採点器や
fixture seed を渡さず、子の出力を判定として扱いません。値の通信でも list/tuple、int/bool、辞書キーの型を
保持します。採点は元の入力と自分の道具表のコピーを保持し、1 提出は合計 12 秒で制限します。Compose は
非 root と init を使い、子孫プロセスを回収します。隔離が使えない環境では正答にしません。禁止された読者の条件を消す提出や、
公開 `PRIMITIVES` を書き換えて `none` だけで全性質を満たす提出を、実例で再現して拒否しています。
これは検証した具体的な保護であり、汎用 Python サンドボックスの安全性証明ではありません。ローカルの
Docker 管理者は author イメージを作って読めるため、ローカル利用は自習用です。独立した試験・順位の
根拠とは区別し、実イベントの得点管理と配置はプラットフォームが担います。

```bash
# リポジトリ直下

make test

FLAG_SEED=local-study docker compose -f local/docker-compose.yml up -d --build --wait
# Workbench: http://127.0.0.1:18119
make verifier-down
```

ローカルコンテナの CPU、メモリ、Docker イメージとビルドキャッシュのストレージを使います。この問題は
AWS リソースやクラウドアカウントを作りません。各サービスのメモリ上限は 1 GiB、学習の目安は 120〜180 分
です。終了時は `make verifier-down` で両サービスを停止します。イメージとキャッシュは削除までディスクに
残り、実行先にクラウド VM を使えばその費用も発生します。

### Supported computation imports / 計算用の標準ライブラリ

Supported computation imports / 計算用に使える標準ライブラリ:
array, base64, binascii, bisect, collections, contextlib, copy, dataclasses, decimal, enum, fractions, functools, hashlib, heapq, hmac, itertools, json, math, operator, random, re, statistics, string, struct, time, typing.
This list covers optional standard-library helpers. Imports already supplied by the starter (including __future__ and problem APIs) are also supported. Other optional imports and file/network access are not supported in grading.
この一覧は追加できる標準ライブラリです。スターターに最初からあるimport（__future__や教材のAPIなど）も、そのまま使えます。それ以外の追加importとファイル・通信操作には採点時は対応しません。
