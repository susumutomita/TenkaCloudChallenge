# 黙っているアプリに口を割らせる — StackStack observability

> TenkaCloud Challenge · `challenges/stackstack-observability` · 難易度 3 · 約 45 分 · `multi-verify` 採点

板は動いています。 ダッシュボードは緑です。 それでも 「書いたはずのものが出てこない」 という声が
止まりません。 これは、 勘で当てるのをやめて、 アプリ自身に何が起きているかを言わせる回です。

**AWS 不要** です。 自分のマシンの Docker コンテナ 1 本だけ、 クラウドアカウントも認証情報も
使いません。 模しているのは、 アプリが当番の人間に対して最低限負っているもの ── **何が** 落ちて
いるかを言う数字、 **なぜ** 落ちているかを言うログ行、 そして条件が読める場所に書いてあって
反論できる死活確認、 の 3 つです。

## 何が立ち上がるか

| どこ | 何 |
| --- | --- |
| **自分のマシン (Docker)** | 共有の **StackStack ベースアプリ** を `SCENARIO=observability` で起動したもの |
| `127.0.0.1:18080/` | 板 ── onboarding から変わっていません |
| `127.0.0.1:18080/relay` | relay のコンソール ── 下流に何が流れていて、 何が流れていないか |
| `127.0.0.1:18080/metrics` | 数字 (Prometheus text format) |
| `127.0.0.1:18080/relay/healthz` | relay の死活確認 |
| `127.0.0.1:18080/archive` | 下流の archive に実際に届いたもの |
| `127.0.0.1:18081` | TenkaCloud の採点が委譲する loopback の `/verify` |
| `127.0.0.1:18080/docs` | API コンソール ── relay 設定の閲覧・変更・破棄 (`/api/settings`) |

relay 設定の出発点は読み取り専用でマウントされ、 変更は API 経由でコンテナ内にだけ置かれます。
リポジトリのファイルは何をしても書き換わりません。 板自身の設定 (`/api/config`) は onboarding から変わっていません。

image は StackStack 系問題が共有する [`stackstack-base/`](../../stackstack-base) から
ビルドされます。 shard の名前、 shard の code、 incident id、 safe-log の値、 relay が下流に
提示する資格情報、 そしてタイトルから shard への写像は、 すべてコンテナ内でデプロイごとの
ランダムな `FLAG_SEED` から導出されます。 答えはこのリポジトリに 1 つも置かれておらず、
2 つのデプロイが同じ答えを持つこともありません。 ポートはどちらも `127.0.0.1` にだけ
バインドされます。

### 模型であることについて正直に

ここに CloudWatch もアラームもロードバランサもありません。 あるのは、 カウンタを公開し、
行を書き、 条件がファイルに書いてある死活確認に答える 1 プロセスだけです。 AWS に移したときの
対応:

| このコンテナ | 現実の対応 |
| --- | --- |
| `GET /metrics` | CloudWatch メトリクス / ロググループのメトリクスフィルタ |
| `relay.json` の `healthCheckProbes` | ALB ターゲットグループのヘルスチェック条件 |
| `GET /relay/healthz` | ターゲットグループが叩くパス |
| `relay.json` の `archiveLogging` | アプリがそもそもログを出すかどうか |
| `relay.json` の `logDetail` | ログのマスキング / 構造化ログのフィールド選択 |
| archive の 4 shard | 下流のパーティション / AZ / シャード |

**「アラームを作って発報させる」 工程は意図的に入れていません。** 自分のノート PC の
コンテナから自分宛にページを飛ばしても学習になりません。 ここで採点しているのは
*このシステムが 「何かが発報できる状態」 になっているか* までで、 発報そのものは、
他人が撃った障害に対する Battle 側の仕事です。

## ミッション

チェックポイント 4 つ、 合計 200 点:

| チェックポイント | 点 | 何を訊いているか |
| --- | --- | --- |
| 届かなかった書き込みを記録に残す | 50 | 届かなかった行に出る incident id |
| 死活確認に本当のことを言わせる | 45 | 死活条件を見ている gate の receipt |
| 調査ログをそのまま渡せる状態にする | 60 | 伏せ字になった行が運ぶ safe-log の値 |
| 落ちている一枚を名指しする | 45 | 書き込みを断っている shard の code |

## 手順

1. 起動する:

   ```
   make local PROBLEM=stackstack-observability
   ```

2. `http://127.0.0.1:18080/relay` を開き、 食い違っている 2 つの面に訊く:

   ```
   curl -s http://127.0.0.1:18080/metrics
   curl -s -w ' [%{http_code}]\n' http://127.0.0.1:18080/relay/healthz
   ```

   片方は依存先が答えていないと言い、 もう片方は全部問題ないと言います。 どちらも、
   自分が訊かれたことについては本当のことを言っています。

3. 違うタイトルで何回か板に書いてから、 もう一度数字を見る:

   ```
   for i in 1 2 3 4 5 6 7 8; do
     curl -s -o /dev/null -X POST -H 'content-type: application/json' \
       -d "{\"author\":\"you\",\"title\":\"note-$i\",\"body\":\"x\"}" \
       http://127.0.0.1:18080/api/posts
   done
   curl -s http://127.0.0.1:18080/metrics
   curl -s http://127.0.0.1:18080/archive | jq '{count, attempted, missing}'
   ```

   投稿はすべて板にあります。 archive にはすべては入っていません。 shard ごとの内訳は
   **その shard に 1 度でも書き込みがあってから** 初めて出ます ── 自分で作っていない
   ものは表示されません。

4. ログを読む:

   ```
   curl -s 'http://127.0.0.1:18080/api/logs?limit=200' | jq -r '.lines[].message'
   ```

   起動の行、 投稿を受け付けた行 ── そして届かなかった書き込みについては 1 行もありません。
   その沈黙は設定です。 いまの設定は

   ```
   curl -s http://127.0.0.1:18080/api/settings | jq
   ```

   が返し、 変更は API コンソール (`docs`) の `PATCH /api/settings` から送ります。
   アプリはリクエストごとに読み直すので、 再起動は要りません。

5. シグナルを出したら、 どこかに貼る前にもう一度自分でログを読み直してください。

6. 実測を見る:

   ```
   curl -s http://127.0.0.1:18080/posture | jq
   ```

   ```jsonc
   {
     "gates": {
       "traffic_seen": true,
       "failures_logged": true,
       "health_honest": true,
       "credential_out_of_logs": true
     },
     "tokens": { "health_honest": "TC{...}", "...": "..." },
     "ready": true
   }
   ```

   false の gate がそのまま次にやることです。 `GET /relay/state` は同じ実測をもう少し
   細かく返します ── 自分が書いた死活条件が gate の見る 3 つの場合を通っているか、
   そして書いたあとに誰かがそれを実際に走らせたか、 も含めて。

7. 最初の壊れた状態に戻したくなったら、 変更を捨てます:

   ```
   curl -s -X DELETE http://127.0.0.1:18080/api/settings
   ```

   コンテナを作り直しても同じ状態に戻ります。

## この問題が足す面

| ルート | 用途 |
| --- | --- |
| `GET /relay` | relay のコンソール (ページ) |
| `GET /relay/state` | 同じ実測を JSON で。 各 gate が何を見ているかも含む |
| `GET /relay/healthz` | relay の死活確認 ── 条件は `relay.json` から来る |
| `GET /metrics` | カウンタとゲージ (Prometheus text format) |
| `GET /archive` | 下流の archive に届いたもの |

板自身のルート (`GET /`, `/api/board`, `/api/logs`, `/posture`, `/healthz`,
`POST /api/posts`) は stackstack-onboarding から変わっていません。 板の `/healthz` は
最後まで 200 のままです ── 壊れているのは板ではありません。

## なぜこう作ってあるか

- **決め打ちの応答はどちらも通りません。** 条件は 3 つの世界で採点され、 それぞれ別の
  答えを落とします: 設定ファイルだけを見る出荷時の条件は一度も赤くならず、 archive だけを
  見る条件は設定ファイルが壊れても緑のままで、 空のリスト ──「常に 503 にしておけば
  見逃さない」── は一度も緑になりません。 3 つ全部で正しい条件はちょうど 1 つです。
- **正しく直した死活確認はここで赤くなり、 それが合格です。** archive は本当に落ちています。
  `/relay/healthz` がそれを見るようになった瞬間、 503 を返し、 503 を返し続けます。
  一度も赤くなったことのない死活確認は 「正しいことが確かめられている」 のではなく、
  「落ちようのないものを見ている」 だけです。 コンテナの `healthcheck:` を relay ではなく
  板の `/healthz` に向けてあるのは、 まさにこの理由です。
- **沈黙は健全さではありません。** エラー表示をいちばん安く消す方法は、 板を閉じることと、
  relay のログを止めることです。 どちらも通りません ── 4 つの checkpoint はどれも
  「失敗が現に起きていて、 それが記録されている」 ことを他の判定より先に要求します。
  「画面にエラーが 1 件も出ていない」 は満点ではなくゼロ点です。
- **ログを止めるのは漏洩の直し方ではありません。** *調査ログをそのまま渡せる状態にする* は、
  不在を見る **前に** 2 つを実測します: いま効いている設定の下で、 届かなかった行と届いた行が
  両方 「実在する」 こと (届いた行があること自体が、 archive への書き込みがいまも成立している
  証跡です)、 そしてその 2 行が shard・code・target・epoch を保っていること。 ログが空だと
  最初の 1 つで落ちるので不在チェックには到達せず、 秘密が残らないところまで行を削れば
  2 つ目で落ちます。
- **末尾を伏せるのはマスクではありません。** `logDetail` には値の後半だけを消して前半を
  残す設定があります ── 見た目は伏せ字になり、 それでも突き合わせはできてしまうので、
  現場で実際に出てくる 「対処」 です。 不在チェックは値の先頭 12 文字で見るので残った前半で
  落ち、 その設定の行には safe-log の値も出ません。 行ごと削る設定は値そのものは本当に
  消えますが、 調査に要るフィールドのほうで落ち、 *届かなかった書き込みを記録に残す* が
  求めている incident の参照も一緒に消えます。 4 つの設定のうち、 値を差し替えたうえで
  記録を残すものはひとつだけです。
- **code はどの shard にも付いています。** *落ちている一枚を名指しする* はコピーではなく
  対応付けです ── 書き込みのあった shard の code は 4 つとも出るので、 別の shard の code を
  出せば誤答です。 さらに、 名指しした shard が **自分の** 書き込みを実際に断っていること、
  そして別の shard が実際に受け入れていることも要求します。 「全部壊れている」 は別の診断です。
- **再起動は損です。** タイトルから shard への写像は seed 由来で状態を持たないので、
  再起動しても同じタイトルが同じように落ちます ── 何も直りません。 直らないかわりに
  カウンタは 0 に戻り log ring は消えるので、 通っていた 3 つの checkpoint が、
  証跡を作り直すまで落ちます。
- **答えを表にする。** incident id、 safe-log の値、 4 つの shard 名、 4 つの code、
  そして写像は、 すべてコンテナ内でデプロイごとの `FLAG_SEED` から導出されます。
  死活確認の receipt は起動時に生成される秘密由来なので、 同じコンテナの再起動でも変わります。

### 漏れたものは漏れたまま

ログの詳細度を下げても、 すでに書かれてしまった行から資格情報が消えることは **ありません**。
行はログに残り、 読めます。 これは意図的です ── 不在チェックが 「いま効いている設定
(epoch) で書かれた行」 だけを見るのは、 設定変更が、 すでに書き出された値に対する対処には
ならないからです。 実際の障害でここが 「資格情報をローテートする」 瞬間です。 ログを編集
したり grep したりすることが対処だと問題側が教えてしまうのは、 単純に誤りです。

### ログに載る資格情報について

relay が下流に提示している値は `FLAG_SEED` 由来で、 何も認証せず、 loopback に束縛された
コンテナの外には出ません。 意図的にログへ書いています ── 「ログにもう入ってしまっていた」
という状況こそが、 他人に見つけられる前に自分で見つける練習の対象だからです。 いまの行から
それを外すことが、 4 つの合格条件のうちの 1 つです。

### 採点があなたに対してしないこと

4 つの checkpoint はどれも読み取りだけです。 投稿もしないし、 `relay.json` にも触らないし、
shard も動かしません。 誤答で環境が壊れることはなく、 再送しても何も変わりません。

### 正直さの限界

判定はあなたが動かしているコンテナの中で計算されます。 自分のチェックアウトの
`stackstack-base/` を書き換えて image を焼き直せば、 ここの検査は全部無効化できます。
このカタログのコンテナ問題すべてに共通することで、 `make local` は pin された `problems/`
submodule からビルドします。 推測不能性も同様に、 プラットフォームが `FLAG_SEED` を
注入することが前提です ── `docker compose up` を直に打つと compose の既定値が使われます。

## 採点

`multi-verify`、 チェックポイント 4 つ、 合計 200 点 (Medium tier)。 誤答は 3 / 2 / 3 / 2 点
(合計 10)。 各チェックポイントにヒントが 2 つあり、 1 つ目は無料、 2 つ目は 20 / 18 / 24 / 18 ──
問題内の全ヒントを開いても 80 点で、 120 点は残ります。

## コスト

ゼロ。 クラウドアカウントには何もデプロイされません。 コンテナは自分のマシンで動き、
`make local-down` で消えます。 relay も archive もカウンタもコンテナのメモリ上だけに
あり、 設定の変更もコンテナの中にだけ置かれます。 片付けたあとにチェックアウトへ残るものは
無く、 `git status` は最初から最後まで clean のままです。

## Battle への引き継ぎ

正直に、 正しい粒度で。 [`stackstack`](../../battles/stackstack) Battle は
`phased-polling` の CloudFormation 問題なので、 この scenario の JavaScript も in-process の
リスナも境界を越えません。 越えるのは形だけです:

- **死活確認の条件** ── 「このチェックは実際に何を見ていて、 いま壊れているものに気づくか」。
  ターゲットグループのヘルスチェックパスと matcher として再表現されます。
- **数字が先、 行が後** ── カウントでコンポーネントを絞り、 ログ行でインスタンスと理由を
  名指しする。 AWS では CloudWatch メトリクス → ロググループの順です。
- **沈黙は健全さではない** ── 観測された可用性で採点されるフェーズは、 「配信をやめたので
  エラー率が 0 になった」 を評価しません。

この `/metrics` のテキストや `relay.json` のキーがそのまま向こうで再利用される、 とは
書きません。 この 2 つの実行基盤の間では成立しません。
