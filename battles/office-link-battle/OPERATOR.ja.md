# 開催ランブック — AWS入門Challengeから復旧Battleへ

[English](OPERATOR.md) · [問題と費用](README.ja.md)

初回は、普段は異なる拠点で働くエンジニアが**同じ会場に集まり、AWSを学びながら交流する**開催を想定します。2〜4チーム、1チーム4人が目安で、容量の保証ではありません。拠点・部署・AWS経験を混ぜてチームを作り、同じ机で相談しながら操作・観察・説明・確認を交代します。全員の理解や発言量を機械で採点しません。

## 時系列と用意するもの

| いつ | 担当・作業量の目安 | 用意するものと完了の目印 |
| --- | --- | --- |
| 2〜4週間前 | 責任者＋協力者、60分 | 学びと交流の目的、AWS経験、人数、日程、会場、予算、撤収責任者を1枚にする |
| 2週間前 | 環境担当、半日を確保 | Lite、テスト2チーム、各チームの競技AWSアカウント、固定した本体/カタログの版、問い合わせ窓口 |
| 1週間前 | 司会＋技術担当＋初心者役、半日 | 下の実AWSリハーサル。準備・反映待ち・復旧・撤収の時間を測り、当日の長さを決める |
| 前日 | 責任者、60分 | 拠点・経験を混ぜた4人チーム、1人1台のPC推奨、4人で囲める机・電源・Wi-Fi、ログイン情報、役割交代表、欠席時の代役 |
| 当日60分前 | 技術担当、30〜60分 | ログイン、チームロール、準備URL、本戦のロック、採点停止状態を確認 |
| 開催 | 司会＋技術担当、90〜120分を仮確保 | 自己紹介・役割決め5分、準備約40分、Battle約30〜45分、振り返り10分。初心者の実測で調整 |
| 終了後 | 技術担当、30〜60分 | 得点保存、デプロイ削除、残存リソースと費用確認。削除失敗は担当・期限を付けて引き継ぐ |
| 翌週 | 全担当、30分 | 実績時間、止まった操作、相談のきっかけ、費用を次回テンプレートへ反映 |

費用支援は主催者が別途確定します。特定団体の無償支援を前提にしません。初回は準備と本戦だけを出し、7つの追加Challengeは別の開催で選びます。

自己紹介では名前・普段の仕事・AWS経験を短く共有します。解説問題は、答えを選ぶ前に理由を仲間へ一言説明する時間にします。最後は「仲間から学んだこと」を1人ずつ共有し、次に話しかけるきっかけを作ります。

## Gateと版の固定

1. 本体の [イベント運用](https://github.com/susumutomita/TenkaCloud/blob/main/docs/operations/event-runbook.md) に従ってLiteと競技アカウントを用意。イベントに `office-link-gate` と `office-link-battle` **だけ**を登録し、各チームに両方をデプロイする。
2. TenantAdminがイベントの「進行 / Gate」を開き、機能をON（既定OFF）。Gateは準備、解放先は本戦だけ、policyはrequired、追加ボーナス0、チーム上書きは継承。保存して再読み込みする。[event-gate.json](event-gate.json) はAPI設定例で、手元のファイルを置くだけでは適用されません。
3. 未修了チームから本戦URL・回答・Endpoint登録がロックされることを確認。準備の途中に公式加点はなく、5段階の実操作＋説明完了後の合言葉を提出して100点になると解放されます。
4. 本体 `release/tenkacloud-release.json` の `sources.catalog.commit` と `problems` のgitlinkを一致させる。ランチャーは本体のRepoRefとカタログのProblemsRepoRefを固定。ローカルからは本体の `make deploy` を使う。リリースに収録されるまでは候補版と明記する。
5. 配布前に `challenges/office-link-gate/metadata.json` と `battles/office-link-battle/metadata.json` を確認。旧ブラウザ模型の `challenges/office-link-battle` を使わない。既存イベントに問題やGateは自動登録されません。

準備中は端末内に進捗を保存します。担当端末を替えるときは画面の引き継ぎコードをチーム内で渡します。本戦の状態は共通のGameUrlから読み直せます。URL・コード・合言葉は他チームに配布しません。

## 個人カードを配る

デプロイ後、非公開の運営用FaultControllerへ `{"operation":"cards"}` を送ると、A〜DのカードURLが4枚返ります。既存の運営用呼出し例でpayloadを置き換え、`umask 077` で保存先を本人だけ読めるようにします。1人に1枚だけ渡し、全員向けチャットや投影画面に一覧を載せず、配布後は手元の保存ファイルを削除します。共通のGameUrlだけでは個人の確認を代行できません。

欠席時は `{"operation":"assist","members":[2]}` でCの確認を補助できます（A=0〜D=3）。画面に運営の補助を表示します。Cが操作・説明の担当になる場合はCのカードを在席者へ再配布してください。補助はactive/review中だけで、AWSの健康状態や得点は変更しません。

別チームの人と合言葉を交換し、双方がポータルから相手の合言葉を送ると各+20点、異なる3組までです。遅れたチームや奇数チームも、達成済みの相手と交換できます。相手が上限なら相手への追加加点はなく、待機減点もありません。公式得点で稼働点が消えずに20点加わることを確認します。

用意したAWS環境の配布には、本体の[参加者セルフサインアップ](https://github.com/susumutomita/TenkaCloud/blob/main/docs/operations/participant-self-registration.md)を使えます。代表者がチームにつき1回だけ申し込みます。AWSアカウントの事前準備は必要です。

## 本戦の開始と障害操作

全チームが準備を終えるまでは、原則、本戦のEndpoint登録・障害開始を待ちます。早く終えたチームは構成を仲間へ説明。準備で得た100点は共通の基礎点、本戦は同じ時間窓で競います。遅れたチームをどう支援するかは開始前に合意し、黙ってGateを解除しません。

本戦ではHealthUrlHintをEndpointへ登録したチームから採点対象になります。採点開始・終了時刻は本体のイベント設定に従います。登録・開始のずれは運営記録へ残し、正式採点に模型の点数を混ぜません。まず健康な1回の加点を全チームで確かめます。

障害は参加者の操作ではなく、運営者が競技アカウントの権限で **FaultControllerName** を指定して開始します。チームロールにInvoke権限を足してはいけません。CLIは運営者のPCで実行します（このリポジトリのCIからは実行しません）。必要な権限は対象関数ARNへの `lambda:InvokeFunction` と、運営が出力を読むための対象スタックの `cloudformation:DescribeStacks`。別アカウントなら既存の運営ロールを利用し、参加者ロールへ広げません。

```bash
# TEAM_FAULT_FUNCTION は運営者が対象チームのCFN出力で確認した名前
aws lambda invoke --region ap-northeast-1 --function-name "$TEAM_FAULT_FUNCTION"   --cli-binary-format raw-in-base64-out --payload '{"operation":"state"}' /tmp/office-state.json
cat /tmp/office-state.json
aws lambda invoke --region ap-northeast-1 --function-name "$TEAM_FAULT_FUNCTION"   --cli-binary-format raw-in-base64-out --payload '{"operation":"start","kind":"gateway"}' /tmp/office-start.json
cat /tmp/office-start.json
```

HTTP200のCLI応答だけで成功としません。`FunctionError` がなく、JSONのphaseがactiveであることを確認。以後 `gateway → route → role → http` の順に、前の説明が終わりphase=idleになったチームへ開始します。異なる障害を重ねられません。公平性のため各回の開始を全チームでそろえる運用を基本にし、進行差は司会が案内します。各回で操作担当を交代します。

10分未復旧ならタイマーが自動復旧を開始。確認は1分周期、失敗時の再試行は重複防止のため最短3分後です。緊急時は同じ呼出しで `{"operation":"restore"}` を指定。復旧中の重複呼出しは待機中の状態を返します。復旧に失敗しても偽の成功へ進まず、restoringが残ります。ログ・権限・資源の状態を調べ、待ち時間後に再実行してください。成功してphase=reviewになったら、チームが理由を確認します。

管理ロールの課題は「ロールが正しく付いたこと」と「開始後の新しいセッション」を検査します。既存セッションが即切断されるとは扱いません。競技用アカウントでは、ロールなしでもSSMを利用できる [Default Host Management Configuration](https://docs.aws.amazon.com/systems-manager/latest/userguide/setup-instance-permissions.html) の設定を事前確認し、この教材に依存しない管理経路を使っていないことをリハーサルで確かめます。共用アカウントの設定を教材から自動変更しません。一時的な認証情報の反映待ちがあるため、ロール変更後の接続可否だけで即断しません。

## リハーサルで確かめること（実AWSは未実施）

- 初参加者が準備の最初のAWS操作へ迷わず進める。途中のヒント・端末交代・英語も確認する。
- 途中段階ではGateが閉じ、最後の100点で自チームだけ本戦が開く。誤flagは5点減点、再提出で二重加点しない。
- 登録前は本戦加点なし。登録後に正常・異常の採点と、スコアボード/上部得点/順位が一致する。
- 各障害が実際に対象資源を変更し、復旧すると実HTTPや新しいSession Manager接続が戻る。採点の8秒以内に健康応答が返る。
- 自動復旧・明示復旧・重複開始拒否・途中削除を確認。他チームの資源は変わらない。
- チーム用SSOで必要なAWS画面が開き、採点関数・秘密・他チームの変更権限がない。
- 全員が操作または説明を担当し、AWS反映待ちを含む実測時間を記録する。
- 終了後に全スタック削除と資源残存確認を行う。準備用と本戦用の2台・2つのIPv4の費用を忘れない。

本番の開幕で初めてAWSを試さず、このリハーサルで時間配分と権限を確認します。実AWSリハーサル未実施はコードの合否と分けて記録します。

## 7つの選択Challenge

S3保存、S3復旧、Lambda実行、ログ調査、DynamoDB引き継ぎ、SQS仕事の受渡し、CloudWatch監視を別々に用意しています。いずれも難易度1・100点・誤flag5点。全てをこの初回イベントへ追加すると同時に見える問題が増えるため、「1つずつ」の設計になりません。別イベントで目的に合うものを選んでください。

## 次回へ残す記録

日付・人数・経験・初操作までの時間・各段階の所要時間・相談が生まれた場面・止まった場面・費用・削除確認・次回の修正担当を1枚にします。開催支援（設計・準備・当日運営）は有償、企業固有の問題は個別見積りという既存方針を維持します。この交流用得点だけで採用や社内認定を判定しません。
