# 端末に結び付けるセッションと、元の端末上の操作

Cookieはブラウザが保存して送る小さなデータ。ログイン済みであることの証拠をCookieへ入れるサービスもある。DBSC（Device Bound Session Credentials）は、短い期限のCookieを更新するとき、元の端末にある秘密鍵を使えることを確かめる仕組みである。秘密鍵＝許可の証明を作るための秘密の値で、公開鍵＝その証明を確認するための値。実装では、秘密鍵を端末の保護された場所に置き、外へコピーされにくくする。Cookieだけを別端末へコピーしても、同じ鍵による更新を続けられない。[Chromeの開発者説明](https://developer.chrome.com/docs/web-platform/device-bound-session-credentials)

ただし「Cookieをコピーした瞬間に、必ず全操作が拒否される」とは限らない。短寿命Cookieがまだ有効な時間、そのサービスの保護対象、そのブラウザと鍵保存の対応、実際のsession登録・更新の強制条件を確認する必要がある。現在の演習はDBSCプロトコルを実装しておらず、短期限の対策だけでDBSCを実装したとも説明しない。

別端末への持ち出しと、元の端末上での操作は異なる。DBSCの非目標には、攻撃者が元の端末にいる間のブラウザsessionへの一時アクセスが含まれる。端末の鍵を外へ持ち出せなくても、元の端末上で署名を行わせたり、ログイン済みの画面を操作されたりする問題は残る。また、DBSCは特定の管理端末の識別や、その端末が健全であることを保証する仕組みではない。[W3Cの非目標](https://w3c.github.io/webappsec-dbsc/#non-goals)

したがって「端末管理をしていなかったから事件が起きた」とも断定しない。管理端末の条件を要求する仕組み、sessionを端末鍵へ結び付ける仕組み、重要操作の本人確認と承認、元の端末上の侵害対策は、それぞれ守る範囲を確認する必要がある。今回の実事件の侵入原因は未特定。この競技は、既に提供された演習用の証拠を使う模型であり、本物の端末侵害・Cookie読取・署名操作は実装しない。
