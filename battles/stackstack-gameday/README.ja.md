# StackStack GameDay — 1 日ぶんを 1 本で

> **status は `draft` です。** 合成そのものは動いていて、 `scripts/stackstack-gameday.test.ts`
> が Docker も AWS も使わずに実アプリを実 HTTP で端から端まで駆動しています。 まだ済んで
> いないのは、 人間による通しのプレイテストと `make local` での実機 1 回です。
> [まだ検証できていないこと](#まだ検証できていないこと)を参照してください。

天下クラウド株式会社、 入社 4 日目の朝。 前任の SRE はもういない。 CTO はコーヒーを持ったまま
席の横に立って、 こう言う ── 「今日は 1 日、 板から手を離さないでほしい」。

社内掲示板に検索を足し、 公開側の入口を開け、 星野デザインにも渡す。 その間ずっと外からの
アクセスは止まらない。 途中で書き込みが下流に届かなくなり、 ダッシュボードは緑のまま鳴らない。
終盤には四半期の署名鍵の入れ替えが予定どおり走る。

測られているのは 2 つだけ。 **止めていないこと**と、 **開いたままにしていないこと**。
片方だけでは満点にならない。

## これは何か

StackStack の単問 7 つ ── onboarding / vibe-build / ship / safe-exposure / defend /
observability / secrets ── を、 **1 つのアプリの上で 1 本の 90 分 (または 120 分) の連続
イベント**として走らせるものです。 物語も時計も 1 本です。

AWS を使わない local-play コンテナとして配信されます (AGENTS.md §13)。 コマンドは 1 つ。

```bash
make local PROBLEM=stackstack-gameday                                  # 90 分
STACKSTACK_GAMEDAY_MINUTES=120 make local PROBLEM=stackstack-gameday   # 120 分
```

イベント卓は <http://127.0.0.1:18080/gameday>、 板そのものは <http://127.0.0.1:18080/> です。

## 再実装ではなく合成

`SCENARIO=gameday` は `runtimes/stackstack/app/scenarios/gameday.mjs` 1 枚で、 単問 6 モジュールを
**import** して routes / postureContext / gates を合成します。

採点対象の述語はすべて、 各モジュールの `gates` から取った**関数オブジェクトそのもの**です。
コピーではありません。 その出所は boot 時に identity 比較で決定され、 `GET /gameday/state` の
`composition.facts` に出ます。

```json
{ "deskReads": "defend.reads_held", "shipRotation": "ship.survives_key_rotation",
  "relayClean": "relay.credential_out_of_logs", "vibeWithheld": "gameday", … }
```

テストがこの map を検証します。 誰かが後で import した述語を 「同じに見える」 手書きの述語に
置き換えたら、 出所が `gameday` に変わって CI が落ちます ── 再利用を主張するコメントには
できないことです。 つまり `defend.mjs` や `ship.mjs` を直せば、 誰も覚えていなくても
GameDay に届きます。

import と一緒に丸ごと来たもののうち、 各単問で一番高価な部分は次の 3 つです。

- `defend.mjs` の **drill** ── 自前のタイマーで毎ラウンド実 loopback HTTP を送り、 非公開の
  `intendedAllow` を基準に判定し、 下書き id を回し続ける。
- `safe-exposure.mjs` の **`handle()`** ── socket からも gate からも通る 1 本の判定路と、
  5 つの probe group。
- `vibe-build.mjs` の**子プロセス harness** ── 参加者のコードは `env: {}` で spawn された
  別プロセスで動き続けるので、 受領証を発行することも `FLAG_SEED` を読むこともできない。
  合成後もその性質が残っているかは、 仮定せずテストで再度固定しています。

### 再表現したものと、その理由

**受領証の層。** `gateToken(name)` は gate 名だけをキーにします。 import した 6 つのうち
3 つが `service_intact` という名前の gate を持っているので、 1 プロセス内では受領証が同じ
文字列になってしまいます。 そこで GameDay は `gameday_*` の名前で自分の受領証を発行し、
単問の受領証の値は一切使いません。 測定はすべて import で、 新しいのは名前だけです。

**述語 1 つ、`vibeWithheld`。** `vibe-build.mjs` は現在 `gates.drafts_withheld` を
`() => true` として export しています。 feature ファイルが何をしていても緑を返します。
これを import すると、 安全性の割合の中心に vacuous pass を置くことになります。 そこで
GameDay は `vibe-build` 自身の `postureContext()` が報告している**実測値**を読みます
(測定は完全にあちらのものです)。 この欠陥はここで直さず上流に報告します ── この scenario は
兄弟を編集しないからです。

### AWS の `battles/stackstack` を拡張しなかった理由

あちらは CloudFormation の `phased-polling` Battle で、 EC2 上のアプリが `/meta` と `/score`
を返し、 プラットフォームの health-check Lambda が probe します。 JavaScript の scenario
module はそこでは動きません。

「単問の attack / verification / scoring ロジックを再利用する」 をあちらで実現すると、
6 つの gate 群と 6 つの probe 群を、 あの host の言語と `vibe-status` スクリプトで書き直す
ことになります。 具体的には gate 6 本の再実装、 probe 6 本の再実装、 実際に共有される行数は
ほぼ 0、 共有テストなし、 どちらかを直した瞬間に乖離、 そして AWS アカウントなしでは何も
検証できない。

**既存の Battle は一切変更していません。** 共有しているのは板という題材と名前の系列だけで、
コードは共有していません。 移植性があるように匂わせるより、 ここにそう書いておきます。

## 7 つの工程

| 工程 | 何が起きるか | 触るファイル | 開く条件 (90 / 120 分) |
| --- | --- | --- | --- |
| **参加** | 板に着き、 投稿の受付を開け、 1 件書く | `local/config/app.json` | t = 0、 常に |
| **作る** | アーカイブ検索が出してよいものだけを返す | `local/feature/search.mjs` | 参加の状態条件、 または 8 / 10 分 |
| **出す** | 公開側の入口が応答し、 リリース記録が片付く | `local/release/release.json` | 作るの gate、 または 20 / 26 分 |
| **公開範囲** | 先方に板を渡し、 渡してよいものだけを渡す | `local/access/access.json` | 出すの gate、 または 30 / 40 分 |
| **攻撃を受けながら** | 下書きの机が継続的な攻撃に耐える | `local/policy/access.json` | 公開範囲の gate、 または 42 / 56 分 |
| **障害** | 落ちている書き込みが見え、 死活確認が本当のことを言う | `local/relay/relay.json` | relay が 1 件落とした、 または 55 / 74 分 |
| **立て直す** | 今日じゅうに開けたものを閉じ直す | `local/ops/ops.json` (+ relay, release) | 70 / 95 分 |

参加以降のすべての工程は、 **条件と時刻の早いほう**で開きます。 速いチームが時計に足を
引っ張られることはなく、 詰まったチームも残りの工程を見られます。

**時刻条件は飾りではありません。** 工程が開くまでその phase gate は false なので、
`/posture` は受領証を出さず、 checkpoint を前倒しで取ることはできません ── 下地の事実が
たまたま緑になっているチームでもです。

## 採点の仕組み

### tick

`TICK_MS` (既定 2000) ごとに 2 つの割合を出します。

**A ── 可用性・通常利用** (6 本の probe):

| probe | どう測っているか |
| --- | --- |
| 板が読める | 実 `GET /api/board`。 自分の serial を返すこと |
| 公開側の入口が応答する | 実 `GET /site/healthz`。 `ship.mjs` 自身の scorer ヘッダを付けて |
| 検索が結果の形を返す | 参加者のコードを通した実 `GET /api/search?q=…` |
| 下書きの机が正規利用者に応えている | `defend` の drill 自身の window カウンタ |
| 夜間ジョブがいまの設定で通る | `secrets` 自身の `digestHealthy` |
| 先方が障害ページを開ける | 参加者の document への `safeExposure.decide` (障害工程から) |

**S ── 安全性** (6 つの事実、 いずれも import した gate): 机の認可 / portal の認証・認可 /
公開アーカイブが出してよい範囲 / ops 資格情報の権限の広さ / このアプリが serve する面に
資格情報が乗っていないこと / リリースが署名鍵の参照を持っているか値のコピーを持っているか。

### A + S ではなく A × S

1 tick の寄与は**積**です。 A = 0 の tick は S が何であっても 0 点 ── サービスが暗い間、
完璧な安全性の価値は文字どおりゼロです。

これは和にはない性質です。 `wA·A + wS·S` なら、 机を止めたチームも毎 tick 安全性の半分を
まるごと稼げるので、 止めることが安全性スコアにとって**合理的な手**になってしまいます。
積ならそれは一度も得になりません。 そして雑な停止手段はそれぞれ個別に測られています ──
机の `enabled: false` は 503 を返し、 drill は `heldByPolicy` ではなく `broken` に数えます。
live release を消せば `/site` は 503 に落ちます。 `healthCheckProbes` を空にすれば
observability の 3 つ目の反実仮想世界で落ちます。

### 「止めて直して戻す」 がそれでも負ける理由

積は暗い間の**報酬**を消しますが、 順位に残る**コスト**は課しません ── 連続点はコンテナの
中の数字で、 プラットフォームが記録するのは 8 つの checkpoint 判定だけだからです。 このままだと
暗くなることは無料の作戦になります。 攻撃圧力のない状態で作業して、 最後の 10 分だけ
きれいにして戻ればいい。

そこで劣化を**単調な 2 つのカウンタとして持ち、 判定時の述語として読み戻します**。

- 一度でも緑になった経路は **commit** されます。 以後 tick ごとに `armedTicks` が増え、
  緑でない tick は `degradedTicks` が増えます。 どちらも減らず、 何をしても消えません。
- `degradedTicks <= 0.05 × armedTicks` が、 **参加以外のすべての phase check と合格印の
  必須条件**です。 再起動でも後からの修復でも戻りません。

20 分から 75 分まで全部 503 を返したチームは、 猶予を持つ時間のおよそ 6 割を劣化状態で
過ごしたことになります (許容は 5%)。 最後どれだけきれいでも、 phase check を 1 つも
通せません。

経路が commit されるのは**一度動いたことが観測されてから**で、 これが公平さの根拠です ──
serve するものが何も無かった最初の 15 分について課金されることはありません。 課金されるのは、
持っていたものを取り上げたことに対してです。

### 「動かしたまま塞がない」 も負ける理由

安全性の事実が 1 つでも欠けると S < 1 になり、 `perfectSince` は始まりません。 合格印は判定時に
「A と S が**両方とも**、 1 tick も途切れずに hold 時間 (90 分設定で 5 分 / 120 分設定で 8 分)
続いたこと」 を測り直します。 1 つ開いたままなら、 タイマーは一度も動きません。

受領証を先に集めて後から壊す、 もできません。 `/posture` は gate が true のあいだしか
その受領証を出しません。

満点には A = S = 1 が**同時に、 かつ継続して**必要です。 それが 「可用性と安全性を同時に保つ」
という言葉の意味で、 README の 1 文ではなくコードの条件として書いてあります。

### 8 つの checkpoint

| id | 点 | 何を採点するか |
| --- | --- | --- |
| `join` | 60 | 板の serial |
| `build` | 140 | 検索が応答する**かつ**出してはいけないものを返さない |
| `ship` | 140 | 入口が実際に応答した**かつ**live なリリースがちょうど 1 件 |
| `expose` | 140 | 管理面が閉じている**かつ**下書きが絞られている**かつ**サービスが無傷 |
| `attack` | 160 | read が持ちこたえた**かつ**publish も**かつ**机が serve し続けている |
| `incident` | 140 | 両方の結果が起きている**かつ**失敗が記録されている**かつ**死活確認が正直 |
| `stabilize` | 160 | 資格情報が閉じている**かつ**権限が狭い**かつ**ジョブが通る**かつ**ログが清潔**かつ**リリースが入れ替えを越える |
| `signoff` | 260 | 上のすべてが同時に、 保持され、 猶予の内側で |

Battle は Challenge のティア配点表の対象外です (SCORING.md §4)。 閉じたことを採点する事実には
必ずそのモジュール自身のサービス事実が対になっています ── 「不在採点の前に正しさの前提を
置く」 という、 あのモジュールたちがすでに守っている規律を import したものです。 何かを止めて
稼げる check は 1 つもありません。

**最初の 1 点は意図的に一番安く置いてあります。** `join` はページを 1 枚開くだけ。 設定の編集も
投稿も要りません。 どのチームも数分で 1 点入ります ── 他のすべてで詰まっているチームも
含めて。 「15 分以内に最初の点」 は平均ではなく下限だからです。

## 3 つの連鎖

連鎖とは、 ある工程で下した判断が後の工程で結果になって返ってくることです。 注入は一切
ありません。 どれも参加者自身が原因です。

### 1. 出す → 立て直す ── 貼った鍵

`release.json` に鍵の値を貼ると health gate は**通ります**。 あの gate は 「候補がいまストアに
ある鍵で署名できるか」 しか見ず、 コピーしたてならできるからです。 `site_serving` は緑になり、
出す工程の checkpoint もそれで取れます ── 意図的にそうしてあります。 そうでないと連鎖が
先行チームには当たらず、 すでに遅れているチームだけを叩くことになるからです。 その間
`survives_key_rotation` は false で、 shipyard コンソールはそれを表示します。 まだ何も
起きていない段階で。

立て直す工程の頭で**予定された四半期の入れ替え**が走ります。 貼った鍵は受理されなくなり、
`/site` は 503 に落ち、 可用性 probe が赤になり、 保持時間は 0 に戻り、 リリースを
`{"fromSecret": "board-signing-key"}` に直して再デプロイするまで猶予が減り続けます。
参照で出していたチームには何も起きません。

入れ替えは板の投稿で 1 分目から、 出す工程のブリーフでも予告されています。 正しいリリースなら
越えられる定期作業であって、 障害注入ではありません。 そして構造的に冪等です ── 立て直す工程が
開いた時点のストアの version を記録し、 まだその version のときにだけ走らせるので、 tick が
再試行されても、 参加者が自分で入れ替えていても、 ストアはちょうど 1 つ進むだけで 2 つ進む
ことはありません。

### 2. 公開範囲 → 障害 ── まだ存在しなかった経路

`access.json` は `/portal` 以下の**すべて**を管轄します ── 書かれた時点で存在しなかった画面も
含めて。 障害工程で、 先方が `GET /portal/incident` を見に来ます。

safe-exposure の probe group はこの経路に一切触れないので、 公開範囲工程の gate からは何も
導かれません。 `admin_sealed` と `drafts_scoped` を満たす最短の形である deny 既定の document は
先方を締め出します。 allow 既定なら鍵なしでも開いたままです。 どちらも逆向きに間違っていて、
どちらも ordered rule 1 本で直ります。

判定は参加者の実ファイルに対する `safeExposure.decide` そのもので、 `GET /portal/incident`
というルートも同じ関数を通ります ── 判定路は 1 本で、 合成された 2 本目はありません。 この
probe は**公開範囲工程から採点せずに表示**され、 公開範囲のブリーフでも 「この設定はまだ
存在しない画面も管轄します」 と名指ししてあるので、 不意打ちにはなりません。 用心深いチームが
先回りして防ぐのは、 連鎖が不発なのではなく、 連鎖が教訓を教え終えたということです。

### 3. 障害 → 立て直す ── 開けざるをえなかったログ

障害工程は relay のログを on にしないと切り分けられません。 そして on にした瞬間、 ログは
資格情報を運び始めます ── 鍵の要らない `GET /api/logs` に。 ある工程のための自分の修正が、
それまで持っていた安全性の事実を 1 つ奪います。

`masked` は通りません。 照合が前方一致なので、 後ろを伏せても回すべき理由には十分な量が
行に残ります。 `minimal` も通りません。 秘密と一緒に調査に要る項目まで消えるからです。 通るのは
1 つだけ。 そしてすでに書かれた行は書かれたままなので、 本当の答えは履歴を編集することでは
なく資格情報のほうを回すことになります。

## 90 分 ↔ 120 分の切り替え

変数 1 つです。

```bash
STACKSTACK_GAMEDAY_MINUTES=120 make local PROBLEM=stackstack-gameday
```

受け付けるのはちょうど `90` か `120` だけで、 それ以外は**起動失敗**です。 120 分のつもりの
イベントが 90 分の予定表で走っていることに 40 分目で気づいた主催者には、 回復する手段が
ないからです。

| | 90 | 120 |
| --- | --- | --- |
| 作る / 出す / 公開範囲 が開く | 8 / 20 / 30 分 | 10 / 26 / 40 分 |
| 攻撃 / 障害 / 立て直す が開く | 42 / 55 / 70 分 | 56 / 74 / 95 分 |
| 合格印の保持時間 | 5 分 | 8 分 |

**変わらないもの: 要求。** gate も probe 群も `A × S` も 5% のエラーバジェットも閾値も
同じです。 120 分は簡単な回ではなく、 切り分けに使える余裕が多く、 定着を示す保持時間が
長い回です。 これは `defend.mjs` が自分の tunable について既に書いている規則そのものです。
参加はどちらの設定でも t = 0 から開いているので、 最初の 1 点の保証は同一です。

リハーサルとテスト用に `STACKSTACK_GAMEDAY_SCALE` (予定表の全区間を割って、 通し 1 本を
数秒で歩ける) と `STACKSTACK_GAMEDAY_TICK_MS` があります。 どちらも `defend.mjs` と同じ形で
clamp してあるので、 敵対的な値を入れてもイベントが簡単になることはなく、 隠さずここに
書いてあります。

## チームごと・工程ごとの結果

`GET /gameday/results` は 1 run について、 各工程がいつ開いたか、 その事実が最初にいつ緑に
なったか、 終了時に緑だったか、 事実ごとの内訳、 probe ごとの commit / 劣化 tick 数、
安全性の事実、 連続点を返します。

これは**運用記録であって不正防止機構ではありません**。 `FLAG_SEED` は環境変数で届き、
参加者は自分のマシンの持ち主なので、 このコンテナが署名したものは偽造できます。 正本は
プラットフォームが記録した `/verify` 判定で、 その受領証は導出不可能な boot 時の別秘密から
作られます。 主催者は終了時にチームごとに 1 つずつ回収します。

## 意図的にやらないこと

- **プラットフォーム側の連続採点。** `endpoints[].default.from` は `cfn-output` のみなので、
  container 問題にはプラットフォームが probe できる URL がありません。 連続点はコンテナ内に
  あり、 外へは 8 つの checkpoint 判定としてだけ出ます。 プラットフォーム可視にするには
  スキーマとプラットフォーム両方の変更が要り、 それはカタログ側 PR の裁量ではありません
  (AGENTS.md 「Extending the platform contract」)。
- **metadata の `phases[]` / `disruptions[]`。** `phases[].effect` は `scorePathOverride` と
  `switchPlatformToDegraded` だけで、 どちらも `phased-polling` に紐づきます。 宣言すれば
  存在しない機構を約束することになります (AGENTS.md §11)。 工程はコンテナが強制し、 鍵の
  入れ替えは予告された定期作業であって障害注入ではありません。
- **チーム横断の集計・ライブのリーダーボード。** local play は 1 人 1 コンテナで中央サーバが
  ありません。
- **8 つを超える checkpoint。** スキーマと local runner が `multi-verify` を 8 で上限にして
  いて、 8 つとも使っています。
- **送信元アドレスによる遮断。** 全 probe が loopback の同一送信元から来るので、 試させて
  いないものを 「防いだ」 と採点しません (`defend.mjs` から継承)。

## まだ検証できていないこと

- **90 分での完走可能性は見積もりであって計測ではありません。** 各工程は starter が
  「1 回の切り分け + 1 回の編集」 で済むように置いてあり、 各工程 8〜12 分、 通しで 70〜85 分の
  見込みです ── 120 分なら余裕、 90 分なら詰まっています。 通しのプレイテストはまだ通って
  いません。 溢れた場合の正直な直し方は工程の要求を下げること (例: 作る工程を
  `drafts_withheld` だけにする) であって、 合格印を緩めることではありません。
- **`make local` での実機 1 回。** テスト一式は Docker も AWS も使わずに Bun 上の実アプリを
  実 HTTP で駆動していますが、 compose ファイル自体は `bun run validate` と local-play の
  manifest 検査までしか通っていません。
- **長時間耐久。** 6 モジュール同居はバックグラウンドタイマー 2 本、 子プロセス 1 つ、
  scorer 自身のループを意味し、 定常でおよそ毎秒 10 数リクエストの loopback が 1 プロセス内で
  最大 2 時間走ります。 テストは圧縮した通し 1 本のあとにプロセスが健全で `faults` が空で、
  relay のログ行が忙しい攻撃工程を生き延びていることを確認していますが、 それは圧縮された
  1 本です。

## コスト

ゼロです。 AWS アカウント不要、 クラウドリソースなし、 外向き通信なし。 コンテナ 1 つ、
両ポートとも `127.0.0.1` にバインドされます。 片付けは `make local-down` です。

## テストの走らせ方

```bash
bun test scripts/stackstack-gameday.test.ts
bun run validate
```

テストは実物の `runtimes/stackstack/app/server.mjs` を `SCENARIO=gameday`、 圧縮した時計、
一時的な参加者ファイルで起動し、 HTTP で駆動します ── 生成、 実行、 「満点にしてはいけない」
2 つの規則、 3 つの連鎖すべて、 工程の受領証withholding、 1 回だけの鍵入れ替え、 終了、 片付け。
